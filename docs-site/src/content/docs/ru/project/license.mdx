Здесь написано, под какими лицензиями можно использовать mcrs, как проект связан с Mojang и какое правило не пускает код игры в репозиторий. Прочитайте страницу перед тем, как форкать проект, встраивать его в продукт или отправлять первый pull request.

## Лицензию выбираете вы: Apache 2.0 или MIT

mcrs распространяется под лицензией [Apache License 2.0](https://github.com/andreypfau/mcrs/blob/main/LICENSE-APACHE) или [MIT](https://github.com/andreypfau/mcrs/blob/main/LICENSE-MIT), на ваш выбор. В `Cargo.toml` workspace указано `license = "MIT OR Apache-2.0"`.

Код, адаптированный из [valence](https://github.com/valence-rs/valence), сохраняет собственное уведомление, [лицензию MIT авторов Valence](https://github.com/andreypfau/mcrs/blob/main/LICENSE-VALENCE-MIT).

## Связи с Mojang и Microsoft нет

mcrs не связан с Mojang или Microsoft. Minecraft - торговая марка Mojang Synergies AB.

## Материал Mojang берется из JAR игры, который есть у игрока

README сообщает, что в репозитории нет графики Mojang. Клиент читает текстуры и модели из официального JAR игры, который есть у игрока. Таблицы данных и отчеты в `assets/` заново генерируются из JAR игры одной командой, поэтому переход на новый снапшот в основном сводится к обновлению данных.

<Aside type="note" title="Это не юридическая консультация">
Страница повторяет то, что репозиторий говорит о себе. Юридического заключения она не дает. Если оно нужно, например для форка или хостинга сервера, обратитесь к юристу.
</Aside>

## Поведение пишут по спецификациям (clean-room)

Новые изменения берут поведение игры из письменных спецификаций по правилу clean-room. Автор спецификации может читать код игры и записывает только поведение. Исполнитель читает спецификации, публичную документацию о том, что видит игрок, артефакты игры и разрешенный правилом код репозитория, но никогда не читает декомпилированный или деобфусцированный код игры.

Имена из кода игры в репозиторий не попадают. Файл правил делает исключение для восьми терминов сообщества: `ResourceKey`, `TagKey`, `BlockPos`, `SectionPos`, `ColumnPos`, `PalettedContainer`, `LootContext` и `NumberProvider`. Еще он разрешает инструменту, который работает внутри игры и управляет ванильным клиентом, например `tools/vanilla-client`, называть классы клиента, которые этот инструмент вызывает.

Для существующего кода генерации мира и его заметок по дизайну есть [описанное исключение](https://github.com/andreypfau/mcrs/blob/main/docs/clean-room.md#exception-world-generation). Новая работа в этих местах следует текущему правилу, а изменение, которое затрагивает имя из кода игры, удаляет это имя.

Если вы читали код игры, чтобы разобраться в каком-то поведении, самому писать реализацию этого поведения нельзя. Но ее можно сдать через ИИ-агента в роли исполнителя: для этого нужно проверить, что спецификация верна, и убедиться, что у агента нет доступа к коду игры ни в файлах, ни в промпте, ни в инструментах. Полное правило лежит в [docs/clean-room.md](https://github.com/andreypfau/mcrs/blob/main/docs/clean-room.md), а роли описаны в разделе [Как внести вклад](/docs/ru/contributing/).

Владелец также может разрешить авторам спецификаций использовать конкретную стороннюю реализацию с открытым кодом как источник. Для компенсации задержки и досягаемости разрешен GrimAC. Разделение ролей остается тем же: исполнители не читают этот код, а его имена, пути и цитаты не попадают в репозиторий. Правила из такого источника получают метку `design`, потому что это решения mcrs.
