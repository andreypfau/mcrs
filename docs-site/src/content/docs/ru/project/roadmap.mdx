## Четыре направления

В проекте нет эпиков в привычном смысле. Эту роль играют четыре открытые issue с заголовком "Direction:". У каждой есть метка `direction:*` и ссылки на работу под ней.

### mcrs как библиотека, от прокси до полного сервера

<Status issue={180} />

Прокси, бот, лобби, мини-игра, карта мира и полный сервер используют разные префиксы одних и тех же слоев, и никто из них не должен платить за слой, которым не пользуется. Issue определяет семь слоев, каждый зависит только от нижних: данные и протокол (wire), сеть, игровые данные, движок, ваниль, рендеринг, приложения. Каждый `pub`-элемент в слоях с 1 по 4 - обязательство перед пользователями.

Что есть сегодня: 122 крейта, 100 из них собираются без Bevy, 9 без `std` в CI, а 11 собираются под `wasm32` (`xtask/src/checks.rs`). Чего нет: крейты не опубликованы (<Status issue={321} />), а примеры библиотеки (веха "Library examples") открыты.

Фасадного или API-крейта нет, и он не планируется. Решение <Status issue={437} /> говорит, что публичная поверхность - это крейты словаря, плагины с их наборами систем и компоненты, ресурсы и сообщения, которыми владеют эти плагины. Для загрузчика плагинов, которые не компилируются в сервер (JAR, wasm, скрипты), решения пока нет.

### Одно измерение на многих узлах для тысяч игроков

<Status issue={181} />

Цель - десять тысяч игроков в одном измерении с немодифицированным клиентом ванили, при этом каждый клиент видит ограниченное число. Схема из issue: клиенты говорят только с граничным узлом (edge), который держит каждое соединение всю сессию. Симуляция делится на шарды, которые владеют связанной работой. Узлы владеют чанками и их шардами. Координатор владеет картой соответствия чанков узлам и глобальным состоянием. Результат не должен зависеть от числа потоков и раскладки шардов.

Что есть сегодня: миры, которые тикают параллельными ячейками за потоком-мультиплексором с общим слоем данных на одной машине (<Status pr={646} state="works" />). Чего нет: конфигурации на нескольких машинах и измеренного числа игроков. Редстоуна нет.

### Геймплей ванили и тесты поведения на этой архитектуре

<Status issue={182} />

Поведение ванили - самый большой объем работы. Issue строит его как съемные плагины поверх движка и требует доказывать каждую механику тестом поведения, ожидаемый результат которого берется с тестового сервера ванили, а не из нашего чтения кода. Точное поведение (протокол, сохранения, движение игрока, генерация мира) сравнивается тик в тик. Смысловое поведение (редстоун, жидкости, обновления соседей) сравнивается по итогу.

Что есть сегодня, описано в [Статусе](/docs/ru/start/status/). У геймплейных вех от "Redstone" до "Advancements and statistics" (их 17) нет ни одной закрытой issue.

### Код библиотеки без разделяемого владения, блокировок, трейт-объектов и аллокаций на горячем пути

<Status issue={566} />

Крейты библиотеки должны работать в прокси, боте, веб-клиенте и тесте без движка. Issue задает цель для слоев с 1 по 4: без `Arc` и `Rc`, без `Mutex`, `RwLock`, `RefCell` и `Cell` в типах данных, без `dyn` и `Any`, без аллокаций на горячих путях. На момент написания issue `Arc` встречался в 119 исходных файлах. Строка README "no Arc, no Mutex" - это цель, а не текущее состояние.

## Как следить

- Следите за четырьмя issue с направлениями выше.
- Читайте страницу [Новости](/docs/ru/project/news/) после каждого тега.
- Фильтруйте issue по меткам: `decision` для решений, `needs-decision` для открытых.
- Эту страницу обновляют вручную при каждом новом теге. Таблицу вех позже будут генерировать (WIP).
