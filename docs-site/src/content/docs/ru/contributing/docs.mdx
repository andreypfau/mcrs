Страницу может добавить или поправить любой. Эта страница - контракт: для чего нужна страница, какие поля в ней обязательны, как пометить то, чего еще нет, и что проверить перед PR. Сайт лежит в `docs-site/`, а как запустить его локально, написано в [README](https://github.com/andreypfau/mcrs/blob/main/docs-site/README.md).

## Три вида документации

| | Канон: `docs/`, `PERF.md`, `DECISIONS.md` | Этот сайт | README и лендинг |
|---|---|---|---|
| Для кого | ИИ-агенты, авторы спецификаций | плагинщики из JVM, контрибьюторы, Rust-разработчики, админы | наблюдатели, игроки, любопытные разработчики |
| Вопрос читателя | Что именно требует правило? | Как сделать X и почему так? | Что это и для меня ли? |
| Глубина | полная | 1-4 экрана, дальше ссылка в канон | экран на секцию |

Что из этого следует:

- Канон не правится ради сайта. Сайт объясняет и ссылается на него.
- Точное правило дается ссылкой, а не копией. Новую идею для новичка пересказывают на 1-2 экрана.
- Причину решения не пересказываем. Ставим ссылку на issue с меткой `decision` и одну строку своими словами.
- У каждого факта один источник: версия игры в `assets/minecraft/version.json`, цифры производительности в `PERF.md`, поведение в `docs/spec/`, решения в issue. Не пишите число по памяти.
- Из документов по генерации мира (`docs/worldgen.md`, `structures.md`, `surface.md`, `scattering.md`, `heightmap.md`, `aquifer.md`) сюда не копируется ничего. В них есть имена кода игры.

## Одна страница, один файл

Основной язык - английский. Страница лежит в `docs-site/src/content/docs/en/<группа>/<slug>.mdx`, русская версия по тому же пути в `ru/`. Группы: `start`, `plugins`, `concepts`, `crates`, `server`, `client`, `reference`, `contributing`, `project`. Сайдбар строится по каталогам, порядок внутри группы задает `sidebar.order`.

### Frontmatter

Схема лежит в `docs-site/src/content.config.ts`. Неверное поле ломает сборку.

```yaml
---
title: Your first plugin
description: One sentence.
sidebar:
  order: 3
kind: explanation        # tutorial | how-to | reference | explanation | landing
audience: [jvm, rust]    # любые из jvm, contributor, rust, admin, player, observer
stability: changing      # stable | changing | wip
tracking: [283, 636]     # номера issue или PR, обязательно если не stable
sources:                 # пути от корня репозитория, issue:N, pr:N
  - crates/mcrs_minecraft_chat_server/src/chat_plugin.rs
  - issue:283
verified:
  snapshot: 26.4-snapshot-7
  commit: 51d45c26a
  date: 2026-11-09
translated_from: 51d45c26a   # только в ru-файлах
---
```

- `kind` говорит, какого типа страница, и он один. Туториал ведет за руку, how-to решает одну задачу, reference перечисляет факты, explanation отвечает на вопрос "почему".
- В `sources` перечислены все файлы репозитория, на которые опирается страница. Страница без `sources` ревью не проходит. Берите пути из файлов, а не из текста старых issue: крейты переименовываются.
- `verified` - снапшот, коммит и дата, когда вы последний раз сверили страницу с кодом. Не копируйте его с другой страницы.
- Баннер стабильности сверху и блок "Источники и проверка" снизу рисуются из frontmatter. Руками их не пишите.

### Компоненты

Импортируйте их сразу после frontmatter:

```mdx
import Status from '~/components/Status.astro';
import StatusRows from '~/components/StatusRows.astro';
import Example from '~/components/Example.astro';
import Demo from '~/components/Demo.astro';
import { Aside, Tabs, TabItem, Card, CardGrid, LinkCard } from '@astrojs/starlight/components';
```

| Компонент | Для чего |
|---|---|
| `<Status issue={78} state="wip" />` | бейдж состояния со ссылкой. `state`: `works`, `partial`, `wip`, `undecided` или `declined`. Без `state` это простая ссылка `#78`. Есть еще `pr={636}` и `doc="docs/spec/login.md"` |
| `<StatusRows areas="network,persistence" />` | строки из `docs-site/src/data/status.yml` для перечисленных id |
| `<Example file="path" lines="10-40" title="..." />` | фрагмент файла репозитория, читается на сборке. Неверный диапазон строк ломает сборку |
| `<Demo src="/docs/demos/cows.html" title="..." height={900} />` | интерактивная страница в iframe |
| `Tabs` с `syncKey="jvm"` | Paper и mcrs рядом |

Код из репозитория в MDX руками не вставляйте: берите `Example`, тогда он не устареет. Код, которого в репозитории нет (например, сниппет Paper), идет в обычный блок с меткой `java`.

Ссылки между страницами абсолютные, с base и слешем в конце: `/docs/en/start/status/`, а в русских файлах `/docs/ru/...`. Файл репозитория: `https://github.com/andreypfau/mcrs/blob/main/<путь>`. Issue и PR пишите через `Status`, а не голым номером.

## Чего еще нет: пишем и помечаем

Владелец решил: возможность, которой еще нет, можно описывать подробно уже сейчас, если у нее есть источник: issue, спецификация, файл в `docs/` или код. Это не обман, потому что пометка говорит, что этого еще нет. Когда возможность появится, текст правят, а пометку снимают.

- Страница целиком получает `stability: wip` и `tracking`.
- Блок внутри стабильной страницы получает `<Aside type="caution" title="WIP">` со ссылкой на issue или бейдж `<Status state="wip" issue={N} />`.
- Не выдумывайте. Опирайтесь на текст issue (`gh issue view N -R andreypfau/mcrs`), спецификацию, файл в `docs/` или код. Нет источника - пишите "решения пока нет" и больше ничего.
- Не превращайте цель в утверждение. Пишите "направление, не обязательство".
- Гайд по установке и запуску короткий: несколько строк, ссылка на Quick start в README и на технические заметки, пометка "подробный гайд появится к альфе". Шаги не прогоняйте и по догадке не записывайте.

Пример честной строки про загрузчик плагинов: "Загрузчика jar, wasm или скриптов нет, и решения про него нет". Решение <Status issue={437} state="declined" /> отклоняет только фасад и Bukkit-подобный API.

## Две оси плашек

Ось A, состояние возможности, выводится в тексте и таблицах через `Status`:

| Состояние | Когда ставить |
|---|---|
| `works` | есть тест, который это запускает, или замер в `PERF.md`. Одного коммита мало |
| `partial` | работает часть, остальное в issue или PR. Ссылка обязательна |
| `wip` | нет в коде или не до конца, и есть issue. "Направление, не обязательство" |
| `undecided` | issue нет или стоит метка `needs-decision` |
| `declined` | только когда закрыт `decision` |

Ось B, стабильность страницы, - это баннер из frontmatter: у `stable` баннера нет, `changing` пишет "Меняется, следите: #N", `wip` пишет, что в коде этого еще нет. Пример сочетания: страница про плагины может быть `changing`, потому что issue еще изменит механизм, а внутри одна строка помечена `works`, другая `wip`.

## Доки в том же PR

Если вы меняете код, на который опирается страница, правьте страницу в том же PR. В шаблоне PR для этого есть чекбокс.

Workflow `docs` запускается на PR, которые трогают `docs-site/`, `crates/`, `docs/`, `tools/`, `PERF.md`, `README.md` или файл версии. Скрипт `docs-site/scripts/check-sources.mjs` сравнивает измененные файлы с `sources` каждой страницы и пишет предупреждение по каждой странице, которую задевает ваш PR. Сборку предупреждение не роняет. Увидели его - откройте страницу, проверьте, поправьте текст и блок `verified` или напишите в PR, почему правки не нужны. Локально: `npm run check-sources` в `docs-site/`.

Проверка читает имена файлов, а не смысл. О смене состояния issue она не знает: изменение issue после даты `verified` не замечается, поэтому раз в месяц владелец обходит [Status](/docs/ru/start/status/).

## Английский и русский

- Русский файл лежит по тому же пути и повторяет структуру и порядок английского. Нового содержания, которого нет в английском, в нем нет.
- В русском файле стоит `translated_from: <коммит>`: коммит английской страницы, с которой вы переводили. Когда английская уходит вперед, русская отстает, и разницу видно в `git log` между двумя коммитами.
- Если русского файла нет, сайт показывает английский с пометкой, что страница не переведена.
- Устоявшиеся англицизмы (тик, чанк, крейт, плагин, снапшот) остаются, при первом упоминании английский термин в скобках.
- Заголовки issue остаются английскими.

## Шаблон объяснялки

У интерактивной объяснялки вроде демки с коровами 12 обязательных частей. Без одной из них ее не публикуют.

1. Одно утверждение: одно предложение о том, что сравнивается.
2. Две стороны на общих часах: ваниль слева, mcrs справа, один индекс кадра, никаких отдельных таймеров. На узком экране они идут друг под другом в том же порядке.
3. Одинаковый вход: один сид, одна сцена, одно число сущностей. Если вход разный, напишите почему.
4. Данные сценария декларативны: кадры в массиве или JSON рядом с файлом. Рендер про сценарий не знает.
5. Плеер: пауза, шаг вперед, шаг назад, сначала, счетчик "шаг N из M", клавиши-стрелки, остановка на последнем кадре.
6. Подпись к кадру: одна-две фразы с номером тика.
7. Таблица отличий: 3-6 строк, после анимации.
8. Мост для JVM: одна строка "в Paper это выглядело бы так: ...".
9. Источник: ссылки на правило спецификации, на `docs/*.md` с разделом и на issue. Механизм в разработке получает бейдж `Status`.
10. Честная сноска: что упрощено, чего в игре сегодня нет (пишите "цель, не готово: #N"), что не замер.
11. Доступность: светлая и темная тема, `prefers-reduced-motion` без автоплея, `aria-label` у SVG, фокус на кнопках, контраст текста не ниже 4.5 к 1.
12. Мета: `lang`, версия снапшота и дата, когда вы сверили объяснялку с кодом.

Цвета сравнения постоянные: ваниль охра `#b8741a`, mcrs бирюза `#1d7a70`.

Правила честности для объяснялки: механизм не равен замеру; показывайте то, что реализовано, а цель помечайте; игрушечная модель называет свои упрощения; ваниль берется из спецификации или оракула, а не из памяти автора.

## Чеклист честности

Пройдите его перед каждым PR, который добавляет или меняет страницу.

1. У каждого числа есть машина, сценарий и ссылка (`PERF.md`, issue). Цифры берутся только из `PERF.md`, рядом машина (M4 Max, macOS) и сценарий.
2. "Работает" только если это показывает тест, коммит или запись в `PERF.md`. Иначе "частично" или "wip".
3. Состояние и цель визуально различаются: бейдж, ярлык или Aside.
4. Каждое "нет" ссылается на issue или решение.
5. Нет чисел, снятых не на тихой машине, и нет сравнений с ванилью, Paper или Horizon в цифрах.
6. Утверждение о чужом проекте имеет источник, иначе его не пишут. Для продакшена называем только Paper, Folia, Minestom и Velocity. Rust-проекты идут одной нейтральной строкой без оценок.
7. Версия игры `26.4-snapshot-7` берется из `assets/minecraft/version.json`, а не из памяти. Так же со счетчиками: 121 крейт, а не на глаз.
8. У страницы с меняющимся содержимым есть дата и коммит последней проверки.
9. "Мы" не относится к большей группе, чем есть на самом деле. Никаких заявлений про "сообщество".
10. Рядом с каждой командой запуска стоит предупреждение о безопасности: у сервера нет аутентификации, не открывайте его порт наружу.
11. Цели и issue подаются как "направление, не обязательство".

Два факта, в которых черновики часто ошибаются. Первое: конфликты между системами Bevy проверяет не компилятор, а планировщик, когда строит граф доступа к данным. Второе: issue <Status issue={437} /> отклоняет только фасад и Bukkit-подобный API. О загрузчике плагинов там ничего нет.

## Clean-room в доках

Действуют те же правила, что и для кода. Не пишите имена классов, методов и полей кода игры, кроме `ResourceKey`, `TagKey`, `BlockPos`, `SectionPos`, `ColumnPos` и `PalettedContainer`. Публичные API Paper, Bukkit, Velocity и Minestom называть можно. Не пишите, что mcrs - порт. См. [Clean-room на практике](/docs/ru/contributing/clean-room/).

## Стиль

- Пишите простым английским для читателя, который не носитель языка. Короткие предложения, активный залог, одна мысль в предложении.
- Конкретика: у утверждения есть ссылка или число.
- Только ASCII-минус, без длинного и среднего тире. Кавычки прямые.
- Без раздутых слов ("groundbreaking", "vibrant", "showcases") и вставок вроде "Of course!" или "I hope this helps".
- Без списков вида "- **Заголовок:** текст". Берите таблицу или обычные предложения.
- Без жесткого переноса: абзац - одна строка.
- Страница занимает 1-4 экрана. Если страница разрослась, разбейте ее или дайте ссылку на канон.
- Русский текст пишется так, как разработчик объяснил бы коллеге: смысл важнее структуры английской фразы, глаголы вместо цепочек существительных, активный залог, без канцелярита ("является", "осуществлять", "данный"), без "вы" там, где фраза обходится без него, после двоеточия строчная буква, заголовки - короткие именные группы. Буква с двумя точками не используется: везде пишем "е".

## Перед PR

1. Frontmatter соответствует схеме, у страниц `wip` и `changing` есть `tracking`.
2. Диапазон строк у каждого `Example` совпадает с файлом.
3. Ссылки ведут на страницы, которые есть в дереве.
4. `npm run build` в `docs-site/` проходит.
5. В странице нет длинных тире, нет буквы с двумя точками и нет имен из кода игры.

<Aside type="caution" title="WIP">
Отчета об отстающих русских страницах и автоматической проверки состояния issue пока нет, issue на них тоже нет. Из автоматики сегодня только предупреждение `check-sources`.
</Aside>
