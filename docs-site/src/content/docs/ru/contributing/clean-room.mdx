mcrs строит поведение игры по описаниям этого поведения и никогда по коду игры.

- Автор спецификации может читать код игры и записывает поведение в `docs/spec/`.
- Исполнитель читает спецификацию и код игры не читает.
- Ни код, ни комментарий, ни тест, ни заметка, ни сообщение коммита, ни issue не называют классы, методы и поля игры. Исключения для общепринятых терминов перечислены в каноне. Инструмент вроде `tools/vanilla-client`, который работает внутри игры и управляет ванильным клиентом, может называть классы клиента, которые вызывает.
- Parity-тест сравнивает наш результат с артефактами, которые выдала игра.

## Сторонние реализации

Владелец может разрешить автору спецификации читать конкретную стороннюю реализацию с открытым кодом. Исполнитель ее не читает, а в репозиторий не попадают имена ее классов, методов, полей и файлов, пути к ним или цитаты кода. Автор описывает поведение своими словами и ставит метку `design`, потому что это выбор mcrs. Для спецификаций компенсации задержки и дальности действия разрешен GrimAC.

Правило записано в [docs/clean-room.md](https://github.com/andreypfau/mcrs/blob/main/docs/clean-room.md). Авторитетен тот файл. Формат спецификаций описан на странице [Спецификации и parity](/docs/ru/contributing/specs-and-parity/).
