Здесь простыми словами пересказан [docs/clean-room.md](https://github.com/andreypfau/mcrs/blob/main/docs/clean-room.md). Правило задает именно тот файл, и если страница с ним расходится, прав файл.

Идея простая. mcrs строит поведение игры по описаниям этого поведения, а не по коду игры. Две работы делают разные люди, поэтому код никогда не вырастает из кода игры.

## Две роли

| | Автор спецификации | Исполнитель |
|---|---|---|
| Результат | файл в `docs/spec/` | код, тесты, заметки по дизайну |
| Может читать | любые исходники, включая код игры | `docs/spec/`, публичную документацию для игроков, артефакты, созданные игрой, код этого репозитория, который разрешают правила |
| Не должен | записывать в спецификацию форму кода игры | читать декомпилированный, деобфусцированный или маппированный код игры |

"Артефакты, созданные игрой" - это датапак, отчеты в `assets/mcrs/reports/`, перехваченные пакеты, сохранения и вывод `tools/vanilla-oracle`. Этот вывод служит доказательством, и parity-тест сравнивает с ним наш результат.

Спецификация описывает поведение: входы, выходы, порядок, время и константы как данные. В ней нет имен классов, методов, полей и переменных и нет структуры функции.

Один человек не берет обе роли для одного и того же поведения. Для одного поведения можно быть автором, а для другого исполнителем.

## Чего в репозитории нет

- Имен классов, методов и полей кода игры: ни в коде, ни в комментариях, тестах, заметках по дизайну, сообщениях коммитов и issue.
- Текста, который называет код портом, транскрипцией или зеркалом кода игры. Не пишите "port of" ни в коммите, ни в документации.
- Теста, инструмента или скрипта, который читает код игры.

Сообщество использует несколько имен из кода игры как общие термины. Их можно писать везде: `ResourceKey`, `TagKey`, `BlockPos`, `SectionPos`, `ColumnPos` и `PalettedContainer`. Новое имя попадает в этот список только после ревью.

Публичные API других проектов, таких как Paper, Bukkit, Velocity и Minestom, называть можно. Это не код игры.

## Происхождение правила

Каждое правило в спецификации несет метку (`docs/spec/registry.md`, раздел 0.3). `source_suggested` значит, что автор читал эталонное поведение и записывает только поведение. Когда эксперимент с игрой подтверждает правило, метка меняется на подтвержденную. По метке читатель понимает, насколько доверять правилу.

## Исключение: генерация мира

Код генерации мира сохраняет свою историю. Исключение действует для крейты `mcrs_minecraft_worldgen*`, `mcrs_minecraft_biome` и `crates/mcrs_minecraft_vanilla_worldgen/` вместе с их заметками по дизайну. Новая работа в этих местах идет по обычным правилам, а изменение, которое затрагивает имя из игры, убирает это имя.

В старых сообщениях коммитов могут быть имена из кода игры. Историю не переписывают: это сломало бы каждый клон. Новые сообщения коммитов следуют правилам.

## Если вы читали код игры

<Aside type="caution" title="Разработчики Paper и Fabric">
Если вы читали код игры про какое-то поведение, реализовать это поведение здесь вы не можете. Напишите вместо этого спецификацию или выберите другое поведение. Если не уверены, скажите об этом в issue. Тогда код по вашей спецификации напишет второй человек.
</Aside>

## Новое поведение по шагам

1. Issue просит спецификацию, и автор пишет ее в `docs/spec/`.
2. Второй issue просит реализацию и ссылается на ID правил.
3. Исполнитель работает по спецификации. Вопрос возвращается автору, а ответ попадает в спецификацию, не в чат.

Подробнее о формате спецификаций: [Спецификации и parity-тесты](/docs/ru/contributing/specs-and-parity/).
