mcrs принимает pull request (PR) со стороны. Здесь описано, какая роль подойдет, чего требует правило clean-room и как изменение проходит путь от issue до слияния.

## Выберите роль

| Роль | Что делать | С чего начать |
|---|---|---|
| Автор спецификации | Описать поведение игры правилами в `docs/spec/`. Читать можно любой источник, в том числе код игры. | [Спецификации и parity-тесты](/docs/ru/contributing/specs-and-parity/) |
| Исполнитель | Написать код на Rust и тесты по спецификации. Код игры читать нельзя никогда. | [Clean-room на практике](/docs/ru/contributing/clean-room/) |
| Parity-тестер | Сравнить наш результат с тем, что выдала игра, и сообщить о расхождении или починить его. | [Спецификации и parity-тесты](/docs/ru/contributing/specs-and-parity/) |
| Документация и перевод | Написать или перевести страницы этого сайта. | [Как писать эту документацию](/docs/ru/contributing/docs/) |

Для разных задач можно брать разные роли. Две роли для одного и того же поведения брать нельзя.

## Clean-room в пяти строках

1. mcrs реализует поведение игры по спецификациям, а не по коду игры.
2. Автор спецификации может читать любой источник. Спецификация описывает только поведение: входы, выходы, порядок, время, константы.
3. Исполнитель читает только `docs/spec/`, публичную документацию о том, что видит игрок, результаты работы игры (артефакты) и код этого репозитория.
4. В репозитории нет имен классов, методов и полей кода игры, кроме терминов сообщества `ResourceKey`, `TagKey`, `BlockPos`, `SectionPos`, `ColumnPos` и `PalettedContainer`.
5. Один человек не берет обе роли для одного поведения.

Полные правила лежат в [docs/clean-room.md](https://github.com/andreypfau/mcrs/blob/main/docs/clean-room.md). Пересказ есть на странице [Clean-room на практике](/docs/ru/contributing/clean-room/).

### Если вы читали код игры

Многие разработчики Paper и Fabric каждый день читают декомпилированный код игры. Это нормально и полезно: для знакомого поведения можно стать автором спецификации. Но у этого есть цена. Если вы читали код игры про некое поведение, реализовать его в этом репозитории нельзя. Код по вашей спецификации должен написать другой человек.

Перед задачей спросите себя: читал ли я код игры про это? Если да, берите issue на спецификацию, а не на реализацию. Если не уверены, напишите об этом в issue. Никто не обидится.

## Путь PR

1. Найдите или откройте issue. Новое поведение игры требует двух: одно просит спецификацию, второе просит реализацию и ссылается на ID правил (`docs/clean-room.md`, раздел "A new behaviour").
2. Напишите спецификацию или реализуйте готовую. Тест называется по ID правила, которое он проверяет.
3. Запустите три команды ниже.
4. Откройте PR. [Шаблон PR](https://github.com/andreypfau/mcrs/blob/main/.github/pull_request_template.md) спрашивает, что и зачем, как проверено и обновлены ли доки.
5. CI запускает `lint`, `clippy`, `test` и `portability`. См. [Сборка и тесты](/docs/ru/contributing/build-and-test/).

```bash
cargo nextest run -p <crate>        # один крейт (crate)
cargo nextest run --workspace       # все, перед коммитом
cargo nextest run --profile full    # плюс исчерпывающие прогоны
```

Это команды из [раздела Development в README](https://github.com/andreypfau/mcrs/blob/main/README.md#development). Первый запуск скачивает клиентский JAR игры ради датапака. Нужен установленный `cargo-nextest`.

## Работа с агентом

Инструкции для агентов, которые пишут код, лежат в репозитории, а не на этом сайте. [AGENTS.md](https://github.com/andreypfau/mcrs/blob/main/AGENTS.md) - общий файл инструкций для любого агента, а `CLAUDE.md` - ссылка на него. В нем правила, которые действуют везде: слои, clean-room, стиль, тесты и путь до `main`.

| Путь | Что там |
|---|---|
| [.agents/skills](https://github.com/andreypfau/mcrs/tree/main/.agents/skills) | скиллы, которые `AGENTS.md` называет словами "Load `<name>`", например `rust-style`, `efficient-testing` и `ship`. `.claude/skills/` ссылается на те же папки |
| [.agents/rules](https://github.com/andreypfau/mcrs/tree/main/.agents/rules) | правила, каждое для своей области: `codec`, `memory`, `rendering` и `simulation`. В заголовке правила перечислены пути крейтов, к которым оно относится. `.claude/rules/` ссылается на них |
| [.claude/agents](https://github.com/andreypfau/mcrs/tree/main/.claude/agents) | роли `implementer`, `spec-author` и `reviewer` |
| [.claude/hooks/cargo-guard.sh](https://github.com/andreypfau/mcrs/blob/main/.claude/hooks/cargo-guard.sh) | хук Claude Code, который не пускает `cargo test`, см. [Сборка и тесты](/docs/ru/contributing/build-and-test/) |

Claude Code сам подгружает скиллы, правила и роли. С другим инструментом читайте `.agents/skills/<name>/SKILL.md` там, где `AGENTS.md` пишет "Load `<name>`", читайте правило области перед правкой одного из ее крейтов и вставляйте текст роли из `.claude/agents/` в бриф агента.

Роли разводят две роли из [Clean-room на практике](/docs/ru/contributing/clean-room/). `spec-author` пишет поведение и не пишет код реализации. `implementer` никогда не читает декомпилированный, деобфусцированный или размапленный код игры.

## Доки идут в том же PR

Если ваше изменение меняет поведение, которое описывает страница сайта, правьте страницу в том же PR. Предупреждение в PR перечислит страницы, у которых вы тронули файлы из `sources`. Слияние оно не блокирует. Как писать страницу, объясняет [Как писать эту документацию](/docs/ru/contributing/docs/).

## Как быстро идет ревью

На 2026-11-09 влито 26 PR от 5 авторов, не считая владельца. Медиана от открытия до слияния около 12 часов. Самый быстрый PR влит за 40 минут, самый долгий за 5 суток. Выборка маленькая, и почти все ревьюит один человек, так что это ориентир, а не обещание.

Чтобы пересчитать: `gh pr list -R andreypfau/mcrs --state merged --limit 300 --json number,author,createdAt,mergedAt`, затем уберите PR `andreypfau`.
