mcrs следует за последним снапшотом Minecraft. Одна команда обновляет репозиторий, а остальное показывают упавшие тесты. Полная процедура описана в [tools/mcrs_minecraft_update/README.md](https://github.com/andreypfau/mcrs/blob/main/tools/mcrs_minecraft_update/README.md). Здесь дана общая картина.

```bash
cargo run -p mcrs_minecraft_update -- <version id>
```

Единственный аргумент - id версии, например `26.4-snapshot-7`. Требования: JDK 25 для Gradle и доступ в сеть к Mojang и к Maven-репозиторию Fabric. Запускайте не больше одного экземпляра сразу. Инструмент не портирует никакой код.

## Что меняет команда

- `assets/minecraft/version.json`: единственное место, где записана версия, скопированное байт в байт из клиентского JAR. Тест падает, если исходник на Rust, TOML или Gradle повторяет одно из его значений.
- `crates/mcrs_minecraft_client_jar/src/release.json`: дескриптор клиентского JAR.
- `assets/mcrs/reports/`: отчеты из игры (`registries.json`, `packets.json`, `datapack.json`, `names.json`).
- `assets/mcrs/block_definition`, `item_definition` и `registry_definition`.
- Сгенерированные исходники ключей реестров. Вручную их не правьте никогда.

Команда печатает три диффа: сдвинувшиеся ID протокола, измененные поля определений и добавленные или убранные имена.

Датафиксера (datafixer) нет. Чанки, сохранения и шаблоны, записанные с другим `DataVersion`, не загрузятся, поэтому миры, записанные между обновлением и следующими за ним портами, хранить не стоит.

## Что делать дальше

1. Прочитайте напечатанные диффы.
2. Запустите `cargo nextest run --workspace`. Упавшие тесты перечисляют, что изменил снапшот. Записи встроенной генерации мира, которые отличаются от файлов игры, падают по имени.
3. Снимите фикстуры заново. Один тест перечисляет каждую фикстуру, у которой запись в `tools/captures.json` указывает не на новую версию:

   ```bash
   cargo run -p mcrs_minecraft_update -- recapture --all
   ```

   Некоторые фикстуры не входят в таблицу и требуют ручного шага. Их перечисляет README.
4. Если изменились протокол или форматы сериализации, выясните по эталонным исходникам игры, как именно. Этот шаг делает только автор спецификации, потому что для него нужно читать код игры. Исполнитель работает по получившейся спецификации. См. [Clean-room на практике](/docs/ru/contributing/clean-room/).
5. Новому снапшоту могут понадобиться правки компиляции в `tools/vanilla-oracle`, прежде чем фикстуры удастся снять заново.

## Чеклист для документации

Документация идет в том же PR, что и обновление.

1. Поищите в документации старую строку версии. Версия в бейджах и в тексте FAQ должна браться из `assets/minecraft/version.json`. Если найдется набранная вручную копия, замените ее.
2. Страницы, у которых изменились `sources`, получают предупреждение в PR. Пройдите по каждой, и если страница все еще верна, обновите ее блок `verified`.
3. Если изменились таблицы пакетов, обновите числа на странице [Status](/docs/ru/start/status/).
4. Если изменился `PERF.md`, проверьте, что машина и сценарий рядом с каждым числом на сайте все еще верны.
5. Переснимите скриншоты и видео, на которых видна версия.
6. Проверьте каждую интерактивную объяснялку: в поле "checked against code" ее меты стоят снапшот и дата.
7. Добавьте строку в [News](/docs/ru/project/news/): версия, что сломалось и что починили.

<Aside type="note">
Предупреждение `check-sources` читает пути файлов, а не смысл. Зеленый прогон не доказывает, что документация верна. Читайте диффы.
</Aside>
