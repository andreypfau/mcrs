Спецификация описывает, что делает игра, а parity-тест проверяет, что наш результат совпадает с результатом, который выдала игра. Здесь показано, как устроено то и другое и как они сходятся в паре issue. Точные правила написания спецификации лежат в [docs/spec/README.md](https://github.com/andreypfau/mcrs/blob/main/docs/spec/README.md), а эта страница только помогает в них сориентироваться.

## Из чего состоит спецификация

Возьмите за образец [docs/spec/whitelist.md](https://github.com/andreypfau/mcrs/blob/main/docs/spec/whitelist.md). Ее раздел 0 содержит соглашения документа, а метки происхождения она берет из раздела 0.3 файла [docs/spec/registry.md](https://github.com/andreypfau/mcrs/blob/main/docs/spec/registry.md).

| Часть | Что в ней |
|---|---|
| Термины (0.1) | Каждый термин домена, определенный один раз. В тексте всегда стоит одно и то же слово. |
| Происхождение и уверенность (0.2) | Откуда взяты метки вроде `black_box_confirmed` и `source_suggested` и какую уверенность дает одно наблюдение. |
| Префиксы ID (0.3) | Короткий префикс на тему, например `WL-JOIN` для проверки белого списка при входе. |
| Границы (0.4) | Что документ описывает, а что оставляет другим документам. |
| Правила | По заголовку на правило: ID вроде `WL-JOIN-002`, поведение, строка происхождения, вид правила и уверенность. |
| Намеренные отклонения | Где mcrs не копирует случайность игры: поведение игры и причина. |
| Нерешенное | Что пока не решено. |

В некоторых спецификациях бывают еще разделы "Известные особенности ванили" и "Эксперименты". Эксперимент описывает шаги и наблюдаемый результат прогона против игры; сырой вывод уходит в тестовую фикстуру. Снятых результатов и логов прогонов, строк статуса, шапки с версией и текста про наш код в спецификации нет.

Правило появляется, только если разницу видит наблюдатель: ванильный клиент, игрок в обычной игре, датапак или файл сохранения либо пользователь библиотеки. Сначала автор записывает поведение, которого ждет игрок, по публичной документации, датапаку и артефактам игры. Потом составляет список вопросов, на которые эти источники не отвечают, и читает код игры только ради ответов на них.

У правила один из семи видов: wire, client agreement, semantic, layout, deviation, quirk или unspecified. Deviation значит, что mcrs намеренно расходится с игрой, и это вид по умолчанию для случайности игры. Quirk - случайность, которую mcrs сохраняет, потому что от нее зависит клиент, датапак или файл сохранения. Решить, что правило относится к виду quirk, может только владелец. Правило вида unspecified parity-тест сравнивать не должен.

Спецификация готова, когда раздел "Нерешенное" в ней пуст и ни у одного правила нет метки `source_suggested`. За неготовую спецификацию исполнитель не берется.

На 2026-11-23 в `docs/spec/` лежат 126 Markdown-файлов, включая README. [Индекс спецификаций](/docs/ru/reference/specs/) перечисляет их по доменам.

Новые спецификации знания клиента и дальности действия показывают, как проверять готовность. Они описывают, как определить, какие изменения применил клиент, и проверить дальность по его картине мира, но эксперименты еще не проведены. Правила с меткой `source_suggested` и эксперименты в разделе "Нерешенное" по правилам спецификаций пока не позволяют начать реализацию. Заметка по дизайну описывает планы, а не работающую систему компенсации задержки.

### ASD-STE100 действует только внутри docs/spec

Спецификации пишутся на упрощенном техническом английском (Simplified Technical English, ASD-STE100): одно слово на одно понятие, короткие предложения, простые времена, активный залог, "must" для требования. На этом сайте такой стиль не применяется. Сайт пишите простым английским, а `docs/spec` - по ASD-STE100.

## Новому поведению нужна пара issue

Новому поведению нужны две issue, как описано в разделе "Новое поведение" файла [docs/clean-room.md](https://github.com/andreypfau/mcrs/blob/main/docs/clean-room.md#a-new-behaviour). Возьмем ломание блока. Его задача просит спецификацию и реализацию двумя шагами, причем второй агент реализует только по `docs/spec/`.[^474] Задача о подтверждении телепорта просит сначала спецификацию, а затем тесты движка на каждое правило.[^623] Роли агентов для такой пары описаны в разделе [Как внести вклад](/docs/ru/contributing/#работа-с-агентом).

Хорошая пара выглядит так:

1. Issue A с меткой `clean-room`: "Описать X". Она готова, когда `docs/spec/x.md` влит и говорит, какие входы, выходы и порядок имеют значение.
2. Issue B: "Реализовать X". Работу по ней начинают, когда спецификация готова. Сама issue готова, когда у каждого правила есть тест, который называет ID этого правила.

PR со спецификацией - это PR с документацией, кода он не трогает. PR с реализацией ссылается на ID правил и спецификацию не меняет. Если спецификация ошибается или молчит, вернитесь к issue A.

<Aside type="caution" title="Правила для конкретной редакции, WIP">
В `docs/spec/README.md` пока нет общего способа пометить, какие правила к какой редакции игры относятся. Раздел "Различия редакций" уже есть в семи спецификациях, среди них спецификации Bedrock и `teleport-confirmation.md`. Общий формат запланирован.[^656]
</Aside>

## Фикстуры снимает с игры оракул

Фикстура - это файл, который выдала игра. Имя фикстуры, задача Gradle, которая ее создает, и папка, куда она попадает, записаны в одном месте, в таблице `tools/fixtures.json`. В ней {fact('fixtures')} записей; 13 из них пишут фикстуры в крейты генерации мира.

Второй файл, `tools/captures.json`, хранит версию игры, на которой снята каждая фикстура. Тест падает поименно для каждой фикстуры, чья версия не совпадает с `assets/minecraft/version.json`, поэтому после обновления снапшота этот тест становится вашим списком дел. Остальное про обновление есть на странице [Переход на новый снапшот](/docs/ru/contributing/new-snapshot/).

Фикстуры снимает инструмент `tools/vanilla-oracle`. Он запускает части игры в проекте Gradle и выгружает их вывод. Большинство задач не запускает ни сервер, ни клиент. Съемка кадров клиента запускает клиент игры, а `recordInventoryE17` запускает client recorder, который поднимает ванильный сервер и ванильный клиент. Одну фикстуру переснимает одна команда:

```bash
cargo run -p mcrs_minecraft_update -- recapture <fixture name>
```

Раздел "Эксперименты" в `docs/spec/README.md` называет еще два инструмента для прогона против игры. `tools/mcrs_minecraft_client_recorder` записывает ванильный клиент, которым играет агент ввода из `tools/vanilla-client`, а `tools/vanilla-server` запускает ванильный сервер по скрипту.

`tools/mcrs_minecraft_probe` проигрывает эксперимент из спецификации как файл сценария, то есть список шагов скриптовых клиентов, например вход, команду или клик в контейнере, и пишет трассу того, что каждый клиент увидел на каждом шаге. Бинарник инструмента записывает трассу на ванильном выделенном сервере с новым плоским миром, как описано в [его README](https://github.com/andreypfau/mcrs/blob/main/tools/mcrs_minecraft_probe/README.md). Тест сервера mcrs проигрывает сценарий банов на встроенном сервере и сравнивает каждый шаг с ванильной трассой. Шаг, который `traces/bans.mcrs.json` называет известным расхождением с причиной, тест сравнивает с результатом из этого файла, поэтому такой шаг тоже падает, если изменится снова.

<Aside type="danger" title="Оракул знает код игры">
Исходники `tools/vanilla-oracle` вызывают код игры напрямую. Исполнителю читать их нельзя. Читайте фикстуру и лежащую рядом процедуру съемки (`*_capture_procedure.md`): в них сказано, что снимается, но не как игра это вычисляет. Автор спецификации оракул читать может.
</Aside>

## Parity-тест сравнивает с фикстурой

Parity-тест лежит в файле `parity.rs` или `*_parity.rs`. Ожидаемые значения он загружает из фикстуры через `mcrs_minecraft_fixtures`, потому что тест заявляет совпадение с игрой, а подтвердить это может только файл, который выдала игра. Проверка `parity` из xtask предупреждает, когда такой тест не загружает фикстуру или сравнивает с литералом. Запускается она командой `scripts/hooks/run-checks commit`.

Чтобы добавить parity-тест, снимите фикстуру оракулом, как описано в его README, загрузите ее в тесте `*_parity.rs` и назовите ID правила в имени теста.

Отчет о правилах, которые не называет ни один тест, запланирован.[^507]

Parity генерации мира - особый случай. Эталонные дампы покрывают выбранные сиды и чанки, поэтому "совпадает с ванилью" там значит "совпадает на этих дампах". Подробнее об этом на странице [Совпадение с ванилью](/docs/ru/concepts/parity/).
