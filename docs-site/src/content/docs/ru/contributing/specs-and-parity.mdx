Спецификация описывает, что делает игра. Parity-тест проверяет, что наш результат совпадает с результатом, который выдала игра. Здесь показано, как устроены обе вещи и как они связаны парой issue.

Точные правила написания спецификации лежат в [docs/spec/README.md](https://github.com/andreypfau/mcrs/blob/main/docs/spec/README.md). Страница - карта, а не копия.

## Анатомия спецификации

Возьмите за образец [docs/spec/whitelist.md](https://github.com/andreypfau/mcrs/blob/main/docs/spec/whitelist.md). Раздел 0 в [docs/spec/registry.md](https://github.com/andreypfau/mcrs/blob/main/docs/spec/registry.md) задает соглашения для всех спецификаций.

| Часть | Что в ней |
|---|---|
| Таблица Field/Value | версия игры и версия протокола, для которых написана спецификация |
| Термины (0.1) | каждый термин предметной области, определенный один раз. В тексте каждый раз то же слово |
| Происхождение (0.2) | метки `black_box_confirmed`, `source_suggested`, `documentation`, `design`, `unresolved` |
| Префиксы ID (0.3) | короткий префикс на предмет, например `WL-JOIN` для проверки белого списка при входе |
| Правила | один заголовок на правило, с ID вроде `WL-JOIN-002`, поведением, строкой происхождения, видом и уверенностью |
| Намеренные отклонения | где мы решили не копировать случайность игры, с причиной |
| Нерешенное | что еще не решено |
| Эксперименты и снятые результаты | как подтвердить каждое правило `source_suggested` и какие результаты уже сняты |

Шесть видов правил: wire, client agreement, semantic, layout, deviation и unspecified. Parity-тест не должен сравнивать правило вида unspecified.

### ASD-STE100 действует только внутри docs/spec

Спецификации пишутся на упрощенном техническом английском (ASD-STE100): одно слово на одно понятие, короткие предложения, простые времена, активный залог, "must" для требования. Этот сайт так не пишется: сайт пишите простым английским, а `docs/spec` - на ASD-STE100.

## Пара issue

Новое поведение требует двух issue, как описывает [Clean-room на практике](/docs/ru/contributing/clean-room/). Пример - ломание блока: <Status issue={474} /> просит спецификацию и реализацию двумя шагами, причем второй агент реализует только по `docs/spec/`. <Status issue={623} /> просит спецификацию подтверждения телепорта, а затем тесты движка на каждое правило. Роли агентов для такой пары описаны в [Как внести вклад](/docs/ru/contributing/#работа-с-агентом).

Хорошая пара:

1. Issue A, метка `clean-room`: "Specify X". Готово, когда `docs/spec/x.md` влит и в нем сказано, какие входы, выходы и порядок важны.
2. Issue B: "Implement X". Готово, когда у каждого правила есть тест, называющий ID этого правила.

PR со спецификацией - это PR с документацией. Он не трогает код. PR с реализацией ссылается на ID правил и не меняет спецификацию. Если спецификация неверна или молчит, возвращайтесь к issue A.

Спецификации пока не помечают, какие правила относятся к какому изданию игры. Это запланировано: <Status issue={656} />.
</Aside>

## Фикстуры и оракул

Фикстура - файл, созданный игрой. Таблица `tools/fixtures.json` - единственное место, где записаны имя фикстуры, задача Gradle, которая ее создает, и папка назначения. В ней 49 записей, и около 14 из них касаются генерации мира. `tools/captures.json` фиксирует, при какой версии игры снята каждая фикстура. Тест падает с именем каждой фикстуры, чья версия не совпадает с версией из `assets/minecraft/version.json`. После обновления снапшота этот тест служит списком дел. См. [Переход на новый снапшот](/docs/ru/contributing/new-snapshot/).

Инструмент, который снимает фикстуры, - `tools/vanilla-oracle`. Он не запускает ни клиент игры, ни сервер: он загружает собственные библиотеки игры и выгружает значения. Одна команда снимает фикстуру заново:

```bash
cargo run -p mcrs_minecraft_update -- recapture <fixture name>
```

<Aside type="danger" title="Оракул знает код игры">
Исходники `tools/vanilla-oracle` напрямую вызывают код игры. Исполнитель не должен их читать. Читайте фикстуру и описание процедуры съемки рядом с ней (`*_capture_procedure.md`): они говорят, что снимается, а не как игра это считает. Автор спецификации оракул читать может.
</Aside>

## Parity-тесты

Parity-тест лежит в файле `parity.rs` или `*_parity.rs`. Ожидаемые значения берутся из фикстуры, загруженной через `mcrs_minecraft_fixtures`, а не из литерала в тесте. Проверка `parity` в xtask предупреждает, если такой тест не загружает фикстуру или сравнивает с литералом. Запустите ее через `scripts/hooks/run-checks commit`.

Чтобы добавить тест: снимите фикстуру оракулом (см. его README), загрузите ее в тесте `*_parity.rs` и назовите ID правила в имени теста.

Parity для генерации мира - особый случай. Эталонные дампы покрывают выбранные сиды и чанки, поэтому "совпадает с ванилью" там значит "совпадает на этих дампах". См. [Parity](/docs/ru/concepts/parity/).
