## Репозиторий на одном экране

| Путь | Что там |
|---|---|
| `crates/` | крейты на Rust, их 122 |
| `tools/` | инструмент обновления снапшота, фикстуры, ванильный оракул, бенчмарки |
| `xtask/` | раннер проверок, который используют CI и локальные хуки |
| `assets/` | файл версии, отчеты из игры, локальные датапаки |
| `docs/` | спецификации и заметки по дизайну. См. [индекс docs](https://github.com/andreypfau/mcrs/blob/main/docs/README.md) |
| `docs-site/` | этот сайт |

## Запуск тестов

```bash
cargo nextest run -p <crate>        # один крейт
cargo nextest run --workspace       # все, перед коммитом
cargo nextest run --profile full    # плюс исчерпывающие прогоны
```

Раннер - [cargo-nextest](https://nexte.st). Версию тулчейна Rust репозиторий закрепляет в `rust-toolchain.toml`, а минимальную версию раннера - в `.config/nextest.toml`. `cargo test` не используйте: он не читает `.config/nextest.toml`, а у большинства крейтов стоит `doctest = false`. Хук Claude Code в репозитории его не пускает.

Каждый профиль сначала запускает setup-скрипт: он ставит клиентский JAR игры и распаковывает его датапак в каталог кеша. Скачивать вручную ничего не нужно. Первому запуску нужен доступ к сети Mojang.

В имени теста есть префикс уровня, и профили фильтруют тесты по нему:

| Профиль | Что запускает |
|---|---|
| `default` | все, кроме тестов `exhaustive::`, `gpu::`, `online::` и `vanilla_server::` |
| `ci` | тот же фильтр, что у `default`, и он не останавливается на первой ошибке |
| `ci-hosted` | фильтр `ci` для задачи `test` на машине GitHub с четырьмя ядрами. Тест может идти 5 минут, весь прогон 30 минут |
| `full` | уровень `default` плюс `exhaustive::` и `online::`. Его использует плановая задача CI |
| `gpu` | только тесты `gpu::`. Нужна машина с GPU Metal |
| `vanilla-server` | только тесты `vanilla_server::`. Они идут через [`vanilla-server/run.sh`](https://github.com/andreypfau/mcrs/blob/main/tools/vanilla-server/run.sh) |

Прогон теста не должен длиться дольше пяти минут, кроме профиля `ci-hosted`. Более медленный тест относится к уровню `exhaustive::`.

## Проверки xtask

CI и локальные хуки вызывают один раннер: `scripts/hooks/run-checks <trigger>`. Он собирает `xtask` и запускает проверки этого триггера. Запустите его сами перед push:

```bash
scripts/hooks/run-checks commit
```

| Триггер | Проверки |
|---|---|
| `commit`, `push` | `parity`, `fmt` |
| `lint` | `parity`, `fmt`, `keys` |
| `clippy` | `clippy` |
| `test` | тесты измененных крейтов и тех, что от них зависят |
| `portability` | `no-bevy`, `layers`, `wasm32`, `no-std` |

Что значат проверки:

- `parity`: тест, который заявляет ванильное поведение, должен загружать фикстуру, созданную игрой. Сравнение с литералом дает предупреждение. См. [Спецификации и parity-тесты](/docs/ru/contributing/specs-and-parity/).
- `keys`: сгенерированные исходники ключей реестров должны совпадать с тем, что генератор пишет из сохраненных отчетов. Сгенерированные файлы вручную не правьте никогда.
- `no-bevy`: 100 пакетов должны собираться без Bevy. `no-std`: 9 пакетов должны собираться под цель без std. `wasm32`: 11 пакетов должны собираться под wasm32. Списки лежат в `xtask/src/checks.rs`.
- `layers`: крейты протокола и сети не должны линковать игровые данные, чтобы прокси или бот могли использовать только их.

Запустите `scripts/hooks/run-checks` без аргумента, чтобы увидеть все триггеры.

## MCRS_BLESS

Некоторые тесты сравнивают сгенерированный файл с закоммиченной копией, например запеченные ассеты сущностей и таблицу полей шейдера. Когда копия устарела, тест падает и сообщает об этом. Перезапишите копию с помощью переменной окружения, которую называет сообщение:

```bash
MCRS_BLESS=1 cargo nextest run -p <crate>
```

Прочитайте дифф до коммита. Blessed-файл, изменившийся без причины, - ошибка в изменении, а не в тесте. Тесты, которые читают эту переменную, лежат в `crates/mcrs_minecraft_mesh/src/pack.rs` и `crates/mcrs_minecraft_entity_model/tests/it/mob_assets.rs`.

## CI

Workflow `.github/workflows/checks.yml` запускается на каждом pull request в `main` и на каждом push в `main`. Первая задача, `changes`, читает список файлов pull request. Если все файлы лежат в `docs/`, это Markdown-файлы в корне репозитория или файлы `LICENSE-*`, остальные задачи не запускаются и проверка проходит. Правка в `docs-site/` запускает полный набор.

Набор задач зависит от того, откуда пришел pull request:

| Откуда | Задачи |
|---|---|
| Ветка этого репозитория | `lint` на машине `ubuntu-24.04` в GitHub. Одна задача `self-hosted` на собственном раннере проекта запускает триггеры `clippy`, `test` и `portability` одновременно |
| Форк | `lint`, `clippy`, `test` и `portability`, каждая на машине `ubuntu-24.04` в GitHub. Они стартуют с кешей сборки, которые сохраняет каждый push в `main` |
| Push в `main` | оба набора |

Финальная задача `checks` падает, если не прошла хотя бы одна из задач, которые относятся к этому запуску.

- На машине GitHub триггер `test` берет профиль `ci-hosted`, а Cargo собирает features только для выбранных пакетов.
- В CI тесты пропускают каждый крейт, который зависит от wgpu, и все, что выше по зависимостям. Эти тесты идут только локально, поэтому при правках клиента или рендерера запускайте их сами.
- Второй workflow, `docs`, предупреждает о страницах этого сайта, у которых изменились sources. См. [Как писать эту документацию](/docs/ru/contributing/docs/).
