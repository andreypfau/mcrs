Эта страница помогает добиться зеленых тестов на своей машине и объясняет, что CI запускает на вашем pull request. Как поставить Rust и драйвер GPU, здесь не описано.

Подробного гайда по сборке пока нет. Он появится к альфе для игроков. Пока пользуйтесь [Quick start в README](https://github.com/andreypfau/mcrs/blob/main/README.md#quick-start). Автор этой страницы ничего из нее не запускал: команды взяты из файлов репозитория, названных в источниках.

## Что где лежит в репозитории

| Путь | Что там лежит |
|---|---|
| `crates/` | Крейты на Rust, всего {fact('crates')}. |
| `tools/` | Инструмент обновления снапшота, фикстуры, ванильный оракул и бенчмарки. |
| `xtask/` | Запускалка проверок, которой пользуются CI и локальные хуки. |
| `assets/` | Файл версии, отчеты из игры и локальные датапаки. |
| `docs/` | Спецификации и заметки по дизайну. Их перечисляет [индекс docs](https://github.com/andreypfau/mcrs/blob/main/docs/README.md). |
| `docs-site/` | Этот сайт. |

## Запустите тесты

```bash
cargo nextest run -p <crate>        # один крейт
cargo nextest run --workspace       # все, перед push
cargo nextest run --profile full    # плюс исчерпывающие прогоны
```

Тесты запускает [cargo-nextest](https://nexte.st). Версию тулчейна Rust репозиторий фиксирует в `rust-toolchain.toml`, а минимальную версию раннера - в `.config/nextest.toml`. Не пользуйтесь `cargo test`, потому что он не читает `.config/nextest.toml`, а в большинстве крейтов стоит `doctest = false`. Хук Claude Code в репозитории его отклоняет.

Тесты читают датапак игры, поэтому каждый профиль сначала запускает setup-скрипт, который ставит клиентский jar игры и распаковывает его датапак в ваш каталог кеша. Руками ничего скачивать не нужно, но первому запуску нужен доступ в сеть к Mojang.

В имени теста есть префикс уровня, например `exhaustive::` или `gpu::`, и каждый профиль отбирает тесты по этому префиксу.

| Профиль | Что запускает |
|---|---|
| `default` | Все, кроме тестов `exhaustive::`, `gpu::`, `online::` и `vanilla_server::`. |
| `ci` | Тот же фильтр, что у `default`, и прогон не останавливается на первом падении. |
| `ci-hosted` | Фильтр как у `ci`, для job `test` на машине GitHub. Один тест может идти 5 минут, весь прогон 30 минут. |
| `full` | Уровень default плюс `exhaustive::` и `online::`. Им пользуются job CI по расписанию и job `worldgen-full`. |
| `gpu` | Только тесты `gpu::`. Им нужна машина с Metal GPU. |
| `vanilla-server` | Только тесты `vanilla_server::`. Они запускаются через [`vanilla-server/run.sh`](https://github.com/andreypfau/mcrs/blob/main/tools/vanilla-server/run.sh). |

У профиля default весь прогон ограничен пятью минутами, а отдельный тест останавливается после четырех периодов по 15 секунд. Профили `full`, `gpu` и `vanilla-server` допускают пять периодов по 60 секунд на тест; `ci-hosted` также допускает 30 минут на весь прогон. Дорогие переборы помещают в `exhaustive::`, чтобы обычный прогон их пропускал.

## Запустите проверки xtask перед push

CI и локальные хуки вызывают одну и ту же запускалку, `scripts/hooks/run-checks <trigger>`. Она собирает `xtask` и выполняет проверки, которые относятся к триггеру. Те же проверки можно запустить самому перед push:

```bash
scripts/hooks/run-checks commit
```

У каждого триггера свой постоянный набор проверок. Чтобы увидеть все триггеры, запустите `scripts/hooks/run-checks` без аргументов.

| Триггер | Проверки |
|---|---|
| `commit`, `push` | `comments`, `parity`, `fmt` |
| `lint` | `comments`, `parity`, `fmt`, `keys` |
| `clippy` | `clippy` |
| `test` | Тесты измененных крейтов и тех, что от них зависят, а также doctest, если выбраны core, resource или voxel. |
| `portability` | `no-bevy`, `layers`, `example-dependencies`, `wasm32`, `no-std` |

`fmt` и `clippy` запускают одноименные команды Cargo. Остальные проверки написаны для mcrs, а списки пакетов, по которым они идут, лежат в `xtask/src/checks.rs`.

| Проверка | Что она требует |
|---|---|
| `comments` | Никаких комментариев в исходниках и конфигах вне `examples/`, кроме заметки `// SAFETY:` при `unsafe`-коде. Команда `cargo run -p xtask -- strip-comments` удаляет их все. |
| `parity` | Тест, который заявляет ванильное поведение, должен загружать фикстуру, выданную игрой. За сравнение с литералом проверка выдает предупреждение. О parity-тестах рассказывает страница [Спецификации и parity-тесты](/docs/ru/contributing/specs-and-parity/). |
| `keys` | Сгенерированные исходники ключей реестров должны совпадать с тем, что генератор пишет по сохраненным отчетам. Никогда не правьте сгенерированный файл руками. |
| `no-bevy` | {fact('crates_no_bevy')} пакета должны собираться без Bevy. |
| `no-std` | {fact('crates_no_std')} пакетов должны собираться под таргет без std. |
| `wasm32` | {fact('crates_wasm32')} пакетов должны собираться под wasm32. |
| `example-dependencies` | Пакеты в `examples/` соблюдают ограничения обычных зависимостей из `examples/dependencies.json`. При ошибке выводится цепочка зависимостей. |
| `layers` | Крейты уровней wire и network не должны линковать игровые данные, чтобы прокси или бот могли взять только их. Крейты запекания моделей, значков предметов и рендера сущностей не должны линковать сеть, клиент или сервер, чтобы просмотрщик работал без подключения. Крейт play-пакетов не должен линковать раскладку или правила инвентаря. Крейт игровой логики инвентаря не должен зависеть от пакетной границы. Крейты инвентаря, которыми пользуется клиент (`mcrs_minecraft_engine_item`, `mcrs_minecraft_player_holders` и `mcrs_minecraft_inventory_client`), не должны линковать крейты сервера. |

## Перезапишите устаревший blessed-файл через MCRS_BLESS

Некоторые тесты сравнивают сгенерированный файл с копией в репозитории, ее называют blessed-файлом. Так проверяются запеченные ассеты сущностей и сгенерированные раскладки шейдеров. Когда копия устарела, тест падает, а в его сообщении названа переменная окружения. Запустите тест еще раз с этой переменной, и он перезапишет копию:

```bash
MCRS_BLESS=1 cargo nextest run -p <crate>
```

Перед коммитом прочитайте diff. Если blessed-файл изменился, а вы не можете сказать почему, ошибка в вашем изменении, и тест упал правильно. Переменную читают тесты в `crates/mcrs_minecraft_mesh/src/pack.rs`, `crates/mcrs_minecraft_render/src/shader_layout_emit.rs`, `crates/mcrs_minecraft_entity_model/tests/it/mob_assets.rs` и `crates/mcrs_minecraft_entity_animation/tests/it/mob_assets.rs`.

## Что CI запускает на вашем pull request

Workflow `.github/workflows/checks.yml` запускается на каждом pull request в `main` и на каждом push в `main`. Его первый job, `changes`, читает список файлов pull request. Если все файлы относятся к документации, инструкциям для агентов или формам GitHub, job на Rust не запускаются. Это файлы в `docs/`, `docs-site/`, `.agents/` и `.claude/`, а также формы issue, шаблон pull request, `CODEOWNERS`, `.coderabbit.yaml`, Markdown-файлы в корне репозитория и файлы `LICENSE-*`.

Job `issue-link` запускается на каждом pull request. Он падает, если в описании pull request нет строки `Closes #N`, `Fixes #N`, `Resolves #N` или `Refs #N`, а метки `no-issue` у pull request нет. Строка внутри HTML-комментария не считается, потому что по ней GitHub ничего не закрывает. Исправив описание, перезапустите упавшие job.

Какие job на Rust запустятся, зависит от того, откуда пришел pull request.

| Источник | Job |
|---|---|
| Ветка этого репозитория | `lint` на машине GitHub `ubuntu-24.04`. Один job `self-hosted` на собственном раннере проекта запускает триггеры `clippy`, `test` и `portability` одновременно. |
| Форк | `lint`, `clippy`, `test` и `portability`, каждый на машине GitHub `ubuntu-24.04`. Они стартуют с кешей сборки, которые сохраняет каждый push в `main`. |
| Push в `main` | Оба набора. |

Если pull request из ветки этого репозитория меняет крейт генерации мира, крейт шума или биомов либо оракул блочных сущностей, запускается еще и job `worldgen-full`. На собственном раннере проекта он гоняет профиль `full` для каждого измененного крейта из этой группы и для крейтов группы, которые от него зависят.

Последний job, `checks`, падает, если не прошел хотя бы один из job, которые должны были запуститься.

На машине GitHub триггер `test` берет профиль `ci-hosted`, и Cargo разрешает feature-флаги только для выбранных пакетов. В CI тесты пропускают каждый крейт, который зависит от wgpu, и все, что стоит выше него. Эти тесты идут только локально, поэтому запускайте их сами, когда трогаете клиент или рендерер.

Второй workflow, `docs`, предупреждает о страницах этого сайта, у которых изменились источники. Он описан на странице [Как писать эту документацию](/docs/ru/contributing/docs/).
