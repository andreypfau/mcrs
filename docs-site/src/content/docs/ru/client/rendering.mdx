Рисуют два крейта. `mcrs_minecraft_render` рисует ландшафт и небо, а `mcrs_minecraft_entity_render` - мобов. Рендерер относится к слою 6 в [карте крейтов](/docs/ru/crates/overview/), поэтому он работает с данными нижних слоев и не содержит сетевого, клиентского или серверного кода.

## Ландшафт лежит в нескольких больших буферах GPU

Рендерер записывает меши чанков в три больших буфера геометрии, их называют аренами. В них лежат квады, модели и грани. Аллокатор упаковывает блоки к нулевому смещению, а арена растет шагами с запасом по мере поступления геометрии.

Кадр собирает цепочка систем рендера, которые идут в постоянном порядке. Они загружают изменившуюся геометрию, запускают отсечение, рисуют небо в изображение мира, а непрозрачный ландшафт - в gbuffer, набор изображений, где для каждого пикселя хранится его поверхность. Потом идут тест окклюзии со вторым непрозрачным проходом, мобы, освещение gbuffer одним проходом и прямой (forward) проход с облаками и ландшафтом со смешиванием. Последний проход выводит изображение мира в окно.

## Что рисовать, выбирает GPU

Отсечение (culling) отбрасывает геометрию, которую камера не видит. На полном пути вычислительный проход на GPU проверяет каждую группу квадов относительно вида и записывает аргументы отрисовки.

Это полный путь (full). Рендерер идет по нему, когда у устройства есть compute-шейдеры, непрямые вызовы отрисовки и storage-буферы. В WebGL2 ничего из этого нет, поэтому там рендерер идет по минимальному пути. Шейдеры остаются теми же, массивы, которые они читают, становятся текстурами, а рисуется каждая загруженная группа, потому что отсекать их некому.

## Окклюзия проверяется по глубине прошлого кадра

Группа может попадать в вид и все равно прятаться за холмом. Тест окклюзии убирает треугольники, которые за ландшафтом. Он работает по пирамиде глубины, построенной из прошлого кадра, и идет в два прохода.

Первое отсечение скрывает то, что скрывает старая пирамида, и оставляет кандидатами группы, которые скрыл только этот тест. Затем рендерер перестраивает пирамиду из глубины текущего кадра, и второе отсечение возвращает кандидатов, которые все-таки видны, во второй набор вызовов отрисовки. Благодаря второму проходу ничего не появляется с опозданием на кадр.

Проход окклюзии стоит времени, даже когда рисовать нечего, поэтому он запускается, только когда в памяти есть группы. Его можно выключить через `MCRS_OCCLUSION=0` и увидеть, что он дает.

## Позы мобов считает и рисует GPU

Дизайн в `docs/entity-render.md` рассчитан на 100 000 мобов в одном мире без просадки кадра. Это цель заметки, измеренного результата за ней пока нет. В заметке есть раздел про стресс-сцены и пороги, а числа для каждого размера лежат в `docs/entity-render-budget.md`.

ECS хранит состояние каждого моба, а GPU держит проекцию этого состояния в постоянном слоте. CPU пишет в слот, только когда что-то меняется, то есть приходит пакет, проходит тик или меняется ввод скрипта. Остальное делает GPU, причем только для видимых мобов: он отсекает, считает позы, расширяет грани и рисует. Позы задает Molang, язык выражений, на котором написаны определения клиентских сущностей, а `mcrs_molang_wgsl` переводит каналы Molang в шейдерный код WGSL.

Заметка описывает три пути выполнения для мобов, под графические адаптеры с разными возможностями.

| Путь | Что ему нужно |
|---|---|
| Full | Compute-шейдеры и vertex storage |
| Compatibility | Режим совместимости WebGPU |
| Minimal | Без compute, для WebGL2 |

Для мобов построен только полный путь. Рендерер запускает проходы сущностей, когда устройство идет по полному пути ландшафта и проходы укладываются в его лимиты. Каждый проход привязывает не больше 8 storage-буферов, а это лимит WebGPU в браузере, поэтому браузер на Chromium рисует мобов через WebGPU. На WebGL2 клиент мобов не рисует. Устойчивый кадр веб-клиента еще не измерен.[^344]

## Далекие мобы - плоские картинки

Далекому мобу не нужен полный риг, то есть набор костей, который задает позу модели. Для каждой пары из модели и текстуры рендерер запекает небольшой набор видов. В наборе 16 поворотов по yaw и 9 углов возвышения по 64 на 64 текселя, и он занимает около 4,7 МБ. Далекий моб после этого рисуется как импостор, то есть одним квадом, который показывает ближайший вид. Набор запекается лениво, когда модель и текстура впервые появляются на активном мобе. У полных ригов есть лимит, а у импосторов его нет. Заметка фиксирует цену каждого шага и решения, которые не помогли.

Игрок рисуется теми же проходами. Его скин занимает слой текстур сущностей, и рендерер пишет этот слой, когда скин приходит, поэтому новый скин не требует пересборки. Игрок со скином на любом расстоянии рисуется полным ригом, потому что запеченный вид сохранил бы старый скин. Сервер присылает позу каждого игрока, и клиент рисует другого игрока крадущимся, плывущим, ползущим, спящим, в полете на элитрах или во вращательной атаке с анимациями из `assets/mcrs/entity/animations/player.animation.json`. Камера и луч, который находит целевой блок, следуют высоте глаз в позе локального игрока.[^970] Программа без сервера, например просмотрщик мира, добавляет игрока через `host_living_entity` из `mcrs_minecraft_entity_visual`, двигает его через компонент `Motion` и задает модель компонентом `PlayerModel`, а скин компонентом `PlayerSkin`. Правила лежат в `docs/spec/client-player-render.md`.

Экран инвентаря в режиме выживания рисует локального игрока теми же проходами. Отсечение, поза и расширение граней запускаются второй раз для этого вида фигурки, а `FigureDraw` рисует ее грани в проход рендера хоста.

## Имена над сущностями и текст табличек

Имена над игроками и именованными мобами повернуты к камере. `NameTag`, заданный хостом, приоритетнее имени из данных сущности; если ни того ни другого нет, берется имя профиля игрока. Для моба также нужен `SyncedData.name_visible`. Подписи видны на расстоянии меньше 64 блоков, а при крадущемся движении - меньше 32. У невидимых сущностей и сущностей с `CameraEntity` подписи нет. Обычная подпись рисуется полупрозрачно сквозь блоки и непрозрачно с проверкой глубины, а подпись крадущейся сущности - один раз с проверкой глубины.[^1062]

`ClientTerrainPlugin` включает `NameTagPlugin` из `mcrs_minecraft_client::name_tag`. Хост может добавить его после плагинов рендерера и сущностей, задать сущности `NameTag` и пометить сущность камеры через `CameraEntity`. Клиент пока не передает в проверку видимости цель под прицелом, состояние скрытого HUD и наличие пассажиров, поэтому эти правила на подписи еще не влияют. Правил видимости по командам и строки счета под именем тоже нет. Текстовый проход работает на минимальном пути WebGL2, хотя модели сущностей этот путь не рисует.[^1062]

Таблички используют тот же шрифт и атлас глифов, что и имена над сущностями. На стоящих и настенных табличках текст каждой стороны виден только спереди от ее плоскости, поэтому изнутри таблички больше не видно зеркального текста дальней стороны. Исправление действует на обоих путях рендеринга.[^1056]

## Плагины GUI для здоровья и смерти

`HealthHudPlugin` каждый кадр строит сердца и полоску еды по `Vitals`, `FoodLevel` и атрибуту максимального здоровья локального игрока. `DeathScreenPlugin` реагирует на `PlayerKilled` и отправляет `RequestRespawn` по нажатию кнопки. Оба плагина GUI можно убрать; нативная точка входа добавляет их, а браузерная пока нет. [Клиент сегодня](/docs/ru/client/overview/#здоровье-смерть-и-клиент-без-gui) описывает ограничения отображения и API без GUI; правила HUD лежат в [спецификации здоровья на HUD](https://github.com/andreypfau/mcrs/blob/main/docs/spec/client-health-hud.md).[^1085]
