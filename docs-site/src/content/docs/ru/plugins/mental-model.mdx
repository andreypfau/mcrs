mcrs построен на Bevy ECS (entity component system). Для тех, кто пришел из Paper или Minestom, три вещи здесь устроены иначе. Дело не в новом синтаксисе, а в другом способе мыслить.

## 1. Данные вместо объектов

Объекта `Player` с методами нет. Есть `Entity`, то есть просто id. К нему прикреплены данные в виде компонентов, а поведение живет в системах - обычных функциях.

Удобно думать о базе данных. Сущность - строка, компонент - колонка, система - запрос по всем строкам, где есть нужные колонки.

| Java | ECS в mcrs |
|---|---|
| `class Player extends LivingEntity` | id `Entity` плюс компоненты `Player`, `GameProfile`, `PlayerGameMode` |
| Поле `player.gameMode` | Компонент `PlayerGameMode` на этой сущности |
| Метод `player.fly()` | Система, которая читает и пишет `PlayerFlying` |
| `for (Player p : world.getPlayers())` | `Query<(&GameProfile, &PlayerGameMode), With<Player>>` |
| Ссылка на игрока в поле | Хранить id `Entity`, а не ссылку |
| `Bukkit.getServer()` | Параметры системы: `Res<T>`, `Query<..>`, `Commands` |
| Метод `Listener` | Наблюдатель (observer), то есть функция `fn(e: On<Event>)`, или система |
| `runTaskTimer` | Система в `FixedUpdate`, 20 тиков в секунду |

Запрос из таблицы читается как `SELECT profile, mode FROM entities WHERE has(Player)`. Три компонента способностей находятся в [ability.rs](https://github.com/andreypfau/mcrs/blob/main/crates/mcrs_minecraft_engine/src/ability.rs).

## 2. Нет глобального сервера

Статической точки входа нет. Система объявляет в параметрах, что ей нужно, а планировщик Bevy подставляет это сам. Это внедрение зависимостей: конструктор - сигнатура функции, контейнер - планировщик. По сигнатуре видно, что система читает и что пишет.

## 3. Нет главного потока, параллельность по доступу к данным

Две системы, которые не трогают одни и те же данные, работают одновременно, и писать для этого ничего не нужно. Конфликтующие системы нужно упорядочить самому через `.before()` или `.after()`. Конфликты доступа проверяет не компилятор, а планировщик Bevy, когда строит граф.

Поэтому `Bukkit.getScheduler().runTask(...)` для возврата "в главный поток" не нужен: главного потока в смысле Bukkit нет. Это и не Folia: регионов нет, работа делится по тому, к каким данным она обращается, а не по месту (README, "Parallel by what the work touches").

Измерения тикают параллельно как отдельные миры. Общие данные (время, погода, правила) пишет один владелец, остальные читают снапшоты, см. <Status issue={357} state="works" />. Измерения обмениваются сообщениями.

<Aside type="caution" title="Ловушка с измерениями">
Измерение - отдельный мир со своим sub-app. Плагин, который должен видеть игроков и блоки, добавляйте через `add_dimension_plugin`, а не через `app.add_plugins`. Плагин должен быть `Clone`. Подробнее - в статье [Rust для Java-разработчика](/docs/ru/plugins/rust-for-java/) и в туториале по первому плагину.
</Aside>

## Детерминизм

Одни и те же входные данные дают один результат при любом числе потоков. Конфликт двух сущностей решается по стабильному ключу, например по порядку прибытия или id сущности. Решение <Status issue={367} state="works" /> задает три уровня:

| Уровень | Что | Примеры |
|---|---|---|
| Точно | Как в эталоне | Генерация мира, порядок блочных обновлений, арифметика движения игрока |
| Не зависит от планировщика | Те же входы, тот же тик, любой порядок потоков | Почти все остальное |
| Свободно | Сущности и системы, не делящие записываемые данные | Порядок не важен |

Для автора плагина правило короткое: не полагайтесь на порядок систем, если он не задан через `.before()` или `.after()`. CI запускает симуляционные расписания с ошибкой при неоднозначности порядка, поэтому неупорядоченный конфликт ломает тест (<Status issue={323} state="works" />). См. [tick_determinism.rs](https://github.com/andreypfau/mcrs/blob/main/crates/mcrs_minecraft_server/tests/it/tick_determinism.rs) и [schedule_ambiguity.rs](https://github.com/andreypfau/mcrs/blob/main/crates/mcrs_minecraft_server/tests/it/schedule_ambiguity.rs).

Случайные последовательности эталона вне точного уровня не воспроизводятся: сравниваются только распределения.

## Что это значит для плагина

- Держите данные в компонентах и ресурсах, а не в полях большого объекта.
- Храните id `Entity`, а не ссылки на данные игрока.
- Упорядочивайте конфликтующие системы сами.
- Паника в системе попадает в лог и не останавливает сервер: сервер ставит запасной обработчик ошибок ([src/main.rs](https://github.com/andreypfau/mcrs/blob/main/src/main.rs)). Относитесь к ней как к исключению в хендлере, которое не роняет сервер.
