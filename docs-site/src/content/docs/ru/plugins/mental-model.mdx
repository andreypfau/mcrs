mcrs построен на Bevy ECS (entity component system). Если вы писали плагины для Paper или Minestom, почти все, что вы знаете о Minecraft, пригодится и здесь. Отвыкать придется от трех привычек, и эта страница разбирает их по очереди.

## Игрок - это строка в таблице

В Paper игрок - объект. Вы держите `Player`, читаете его поля и вызываете методы:

```java
for (Player p : world.getPlayers()) {
    if (p.getGameMode() == GameMode.CREATIVE) {
        log.info(p.getName());
    }
}
```

В mcrs объекта игрока нет. Игрок - это `Entity`, а `Entity` - всего лишь id. Все, что сервер знает об игроке, лежит в компонентах, привязанных к этому id: в `GameProfile` хранятся имя и UUID, в `PlayerGameMode` - режим игры. С компонентами работает обычная функция, ее называют системой. Тот же цикл в виде системы выглядит так (это набросок, чтобы показать форму; в туториалах код взят из репозитория):

```rust
// Система - обычная функция, Bevy вызывает ее сам и передает результат запроса.
fn log_creative_players(
    // Сущности с GameProfile и PlayerGameMode; With<Player> оставляет только игроков.
    players: Query<(&GameProfile, &PlayerGameMode), With<Player>>,
) {
    // profile и mode - произвольные имена переменных, а не части GameProfile или PlayerGameMode.
    for (profile, mode) in &players {
        // mode.0 - первое поле PlayerGameMode, примерно как PlayerGameMode[0].
        if mode.0 == GameMode::Creative {
            info!("{}", profile.username);
        }
    }
}
```

`Player` - пустая структура без полей (`pub struct Player;`), метка "эта сущность - игрок". `mode` - ссылка на отдельный компонент `PlayerGameMode`, который лежит на той же сущности. Для каждой сущности, где есть все три компонента, запрос отдает ссылки на `GameProfile` и `PlayerGameMode`. `Player` запрос только проверяет и в выдачу не кладет.

```text
Сущность #42
  ├─ Player            (метка, данных нет)
  ├─ GameProfile       { username, uuid, ... }
  └─ PlayerGameMode    (GameMode::Creative)
```

`mode` - произвольное имя переменной, его придумал автор функции. Это не поле и не часть `PlayerGameMode`. Цикл раскладывает пару из запроса по порядку, как в `Query<(&GameProfile, &PlayerGameMode), ...>`: первый элемент получает имя `profile`, второй - `mode`. Если написать `for (p, gm) in &players`, в теле будут `p.username` и `gm.0`, и код будет работать так же.

А `.0` уже не произвольное. `PlayerGameMode` объявлен как `PlayerGameMode(pub GameMode)`: у структуры одно поле без имени, и Rust обращается к нему по номеру. `mode.0` можно читать как `PlayerGameMode[0]`, то есть первое поле `PlayerGameMode`, в котором лежит `GameMode`. Скобки здесь только для наглядности, в Rust пишут `.0`.

Проще всего представить базу данных. Сущность - строка, компонент - колонка, а система - запрос по всем строкам, где есть нужные ей колонки. `Query` из примера читается почти как `SELECT profile, mode FROM entities WHERE has(Player)`.

В таблице ниже слева то, к чему вы привыкли в Java, справа - ближайший родственник в mcrs. Это аналогии для старта. Полная таблица соответствий есть на странице [Paper и Minestom в терминах mcrs](/docs/ru/plugins/paper-to-mcrs/).

| Java | ECS в mcrs |
|---|---|
| `class Player extends LivingEntity` | id `Entity` с компонентами `Player`, `GameProfile`, `PlayerGameMode` и другими |
| Поле `player.gameMode` | Компонент `PlayerGameMode` на этой сущности |
| Метод `player.fly()` | Система, которая читает и пишет `PlayerFlying` |
| `for (Player p : world.getPlayers())` | `Query<Entity, With<Player>>`: id всех сущностей с меткой `Player` |
| `p.getName()` и `p.getGameMode()` внутри цикла | Компоненты, перечисленные в запросе: `Query<(&GameProfile, &PlayerGameMode), With<Player>>` |
| Ссылка на игрока в поле класса | id `Entity` в компоненте или ресурсе |
| `Bukkit.getServer()` | Параметры системы: `Res<T>`, `Query<..>`, `Commands` |
| Метод `Listener` | Наблюдатель (observer), функция вида `fn(e: On<Event>)`, или система |
| `runTaskTimer` | Система в `FixedUpdate`, она выполняется 20 раз в секунду |

Данные вашего плагина живут по тому же правилу. Кладите их в компоненты и ресурсы, а если нужно запомнить игрока, сохраните id `Entity` и найдите игрока заново, когда он понадобится. Компоненты режима игры, полета и уровня оператора лежат в [ability.rs](https://github.com/andreypfau/mcrs/blob/main/crates/mcrs_minecraft_engine/src/ability.rs).

## `Bukkit.getServer()` здесь нет

В mcrs нет статической точки входа. Система перечисляет в параметрах все, что ей нужно, и Bevy передает эти значения при каждом запуске: `Res<T>` для общего ресурса, `Query<..>` для сущностей, `Commands` для их создания и изменения.

Если вы работали с внедрением зависимостей, схема вам знакома. Сигнатура функции играет роль конструктора, а планировщик Bevy - роль контейнера. Заодно по сигнатуре и вам, и Bevy точно видно, что система читает и что пишет. На этом держится следующий раздел.

## Главного потока тоже нет

Bevy сравнивает сигнатуры ваших систем. Если две системы работают с разными данными, они выполняются одновременно, и писать для этого ничего не надо. Если две системы пишут в одни и те же данные, возникает конфликт, и вы сами указываете, какая из них идет первой, через `.before()` или `.after()`. Bevy находит такие конфликты, когда строит расписание при запуске. Компилятор Rust их не ловит.

Вызывать `Bukkit.getScheduler().runTask(...)`, чтобы вернуться в главный поток, не придется, потому что такого потока нет. От Folia эта модель тоже отличается. Folia делит мир на регионы по координатам, а mcrs делит работу по данным, с которыми работает каждая система.

Каждое измерение - отдельный мир, и измерения тикают параллельно. Время, погода и игровые правила у них общие, поэтому эти данные пишет один владелец, а каждое измерение читает их снапшот.[^357] Когда одному измерению что-то нужно от другого, оно отправляет сообщение.

<Aside type="caution" title="Плагины измерений добавляйте через add_dimension_plugin">
Плагин, которому нужны игроки и блоки, должен работать внутри измерения. Добавляйте его через `add_dimension_plugin`. Если добавить его через `app.add_plugins`, он попадет в главное приложение, где нет ни игроков, ни блоков. Тип плагина должен реализовать `Clone`, потому что каждое измерение получает свою копию. Вся настройка показана в туториале [Первый плагин](/docs/ru/plugins/first-plugin/).
</Aside>

## Одинаковый вход дает одинаковый результат

К параллельному коду обычно один вопрос: не получатся ли из двух запусков два разных мира? В mcrs результат тика не зависит от того, сколько потоков его считало. Когда две сущности претендуют на одно и то же, победителя определяет стабильный ключ, например порядок прибытия или id сущности, и расклад по потокам на исход не влияет.

Насколько строга гарантия, зависит от части игры. В проекте три уровня:[^367]

| Уровень | Гарантия | Примеры |
|---|---|---|
| Точный | Результат совпадает с эталонной игрой | Генерация мира, порядок блочных обновлений, арифметика движения игрока |
| Не зависит от планировщика | Одни и те же входные данные дают один и тот же тик при любом порядке потоков | Почти все остальное |
| Свободный | Порядок ни на что не влияет, потому что общих записываемых данных нет | Сущности и системы, которые пишут только в свои данные |

За пределами точного уровня mcrs повторяет распределения случайных чисел эталонной игры, но сами последовательности не воспроизводит.

Для плагина из этого следует одно правило. Если одна ваша система должна выполняться раньше другой, задайте это через `.before()` или `.after()` и не полагайтесь на порядок, который случайно увидели при запуске. CI запускает расписания симуляции так, что неоднозначный порядок считается ошибкой, поэтому неупорядоченный конфликт роняет тест.[^323] Тесты лежат в [tick_determinism.rs](https://github.com/andreypfau/mcrs/blob/main/crates/mcrs_minecraft_server/tests/it/tick_determinism.rs) и [schedule_ambiguity.rs](https://github.com/andreypfau/mcrs/blob/main/crates/mcrs_minecraft_server/tests/it/schedule_ambiguity.rs).

## Паника не останавливает сервер

Сервер ставит запасной обработчик ошибок в [src/main.rs](https://github.com/andreypfau/mcrs/blob/main/src/main.rs). Когда система паникует, обработчик пишет панику в лог, а сервер работает дальше. Это похоже на непойманное исключение в обработчике событий Bukkit.
