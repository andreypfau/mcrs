В Paper работа начинается с готового сервера, к которому добавляют плагины. В mcrs наоборот: берут группу плагинов и убирают из нее лишнее. Лобби может работать без генерации мира, а тест - без освещения. Примеры взяты из файлов репозитория, вне репозиторных тестов мы их не запускали.

## Группа

`MinecraftServerPlugins` - это `PluginGroup` из Bevy. Четыре ее поля задают части, которые принимают настройки. Остальной ванильный сервер добавляет `build()`.

<Example file="crates/mcrs_minecraft_server/src/lib.rs" from="pub struct MinecraftServerPlugins {" title="Поля группы" />

<Status issue={279} /> Члены группы в том порядке, в каком их добавляет `build()`: ядро сервера, реестры генерации мира, ванильный набор команд, ванильные команды, команды мира, миры измерений, чат, физика сущностей, мозги мобов, генерация мира, освещение и сеть.

<Example file="crates/mcrs_minecraft_server/src/lib.rs" from="impl PluginGroup for MinecraftServerPlugins" title="Члены группы" />

Любого члена можно отключить или заменить, не трогая крейт сервера. Если члену нужен другой плагин, которого нет, группа паникует при сборке и называет недостающий плагин. Ошибка видна на старте, а не как отсутствующий ресурс на первом тике.

<Status issue={282} /> Ванильный геймплей живет в плагинах над движком. Каждый можно убрать отдельно, а в каждый мир измерения они попадают через `add_dimension_plugin`.

## Как отключить плагин из группы

`disable::<T>()` - метод билдера группы плагинов Bevy. Бинарник с его помощью выключает ИИ мобов, а тест запускает сервер без генерации мира и освещения:

## Настройки - это поля плагинов

<Status issue={278} /> Библиотечный крейт не читает ради своих настроек ни переменные окружения, ни файлы. Каждая настройка - поле плагина, который ее использует. Окружение читает только бинарник и переводит его в поля. Обе стороны видны в `src/main.rs`:

<Example file="src/main.rs" from="let settings = ServerSettings::read(" to=".build();" title="src/main.rs: от настроек к полям плагинов" />

Переменные окружения бинарника соответствуют полям `ServerSettings`: имя поля совпадает с именем переменной `MCRS_` без префикса. Полный список лежит в [исходном файле](https://github.com/andreypfau/mcrs/blob/main/crates/mcrs_minecraft_server_settings/src/server_settings.rs). В собственной программе `ServerSettings` можно не использовать и заполнять поля плагинов самому. Тогда встроенный сервер в тесте стартует с явными настройками, что бы ни экспортировал шелл.

## Свой источник чанков

<Aside type="caution" title="WIP">
Этого пока нет, план описан в <Status issue={281} />. Сегодня чанки измерения берутся из фиксированной схемы внутри сервера: генерация рельефа по шуму плюс сохраненные колонки из папки мира. Лобби, арена или тест не могут передать серверу свои чанки. Issue предлагает источник чанков на каждое измерение: по позиции колонки он отдает колонку или сообщает, что ее нет, причем вне тика, на пуле задач. Сервер поставлял бы три источника: генератор с сохранением перед ним, пустой источник и плоский источник из списка слоев. Собственный источник был бы типом, который реализует тот же трейт. Измерение на пустом источнике не тянуло бы крейты генерации мира. В issue есть и тест для этого: одно измерение на пустом источнике, другое на плоском, к каждому подключается клиент, а в дереве зависимостей нет крейтов генерации мира. Это направление, а не обещание. Сохранение чанков на диск - отдельная тема: <Status issue={78} />.
</Aside>
