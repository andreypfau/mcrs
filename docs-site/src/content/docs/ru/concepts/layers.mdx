mcrs - репозиторий из 122 крейтов. Они разложены по семи слоям, и каждый слой должен зависеть только от слоев ниже. Цель простая: берешь нужные слои и не платишь за то, что выше. Прокси хватит двух нижних слоев, полному серверу нужны первые пять. Направление описано в <Status issue={180} />.

## Семь слоев

| # | Слой | Что в нем |
|---|---|---|
| 1 | Протокол | идентификаторы, позиции, NBT, текст, ключи; трейты кодеков; фрейминг, сжатие, шифрование; пакеты handshake, status, login и configuration |
| 2 | Сеть | конечный автомат соединения, вход с обеих сторон, аутентификация, проксирование, фреймы, которые кодируются один раз на рассылку |
| 3 | Игровые данные и правила | реестры, собранные из датапака, блоки, предметы, сущности, чанки, сохранения Anvil и их пакеты; ядра без Bevy для освещения, генерации мира и симуляции блоков |
| 4 | Движок | плагины Bevy для миров, измерений, источников чанков, игроков, событий и команд, а также драйверы ядер; по умолчанию без поведения из ванили |
| 5 | Ваниль | что делают блоки, предметы и мобы, генерация мира и освещение, в виде отключаемых плагинов |
| 6 | Рендеринг | построение мешей и пайплайны поверх данных слоя 3; без сети, клиента и сервера |
| 7 | Приложения | бинарник сервера, клиент и инструменты |

Каждый крейт называется `mcrs_minecraft_<name>` и лежит в [`crates/`](https://github.com/andreypfau/mcrs/tree/main/crates). У крейтов ядра движка свой префикс: `mcrs_engine_cell`, `mcrs_engine_link`, `mcrs_engine_muxer` и `mcrs_engine_store`. Список всех крейтов со слоями есть в разделе [Обзор крейтов](/docs/ru/crates/overview/).

Два правила о зависимостях:

- Ниже слоя 4 Bevy подключается как необязательная feature. Ниже слоя 2 необязателен и tokio: с tokio работает только сетевой слой.
- Сейчас несколько крейтов нарушают это направление. В README так и сказано: крейты протокола и сети все еще обращаются к игровым данным. Исправить это - часть <Status issue={180} />.

## Ядра и драйверы

Правило "в слое 3 нет Bevy" работает благодаря одному разделению в дизайне. **Ядро** (kernel) - обычный Rust-код: оно хранит правила одной области (обновления блоков, освещение, генерация мира, движение сущностей) и не зависит ни от Bevy, ни от tokio. Шаг ядра - вызов функции: на вход идут состояние и представление мира, на выходе записи и сообщения в буферы, которыми владеет вызывающий. Одинаковые входы дают одинаковые выходы.

**Драйвер** (driver) запускает ядро. В слое 4 драйвер - плагин Bevy: он читает мир, вызывает ядро и записывает результат обратно. Между системами планировщиком остается Bevy, собственного планировщика в mcrs нет (решение в [заметке о дизайне шардирования](https://github.com/andreypfau/mcrs/blob/main/docs/minecraft-bevy-sharding-architecture.md), раздел 13). Без Bevy драйвер - это просто цикл. Поэтому бот, инструмент для карт или тест могут использовать ядро напрямую.

Для тех, кто пришел из Paper: ядро похоже на логику ванильной системы, из которой убрали объект сервера, так что ее можно вызвать откуда угодно. Драйвер - та часть, которая знает о тиках.

## Что сегодня значит "набор деталей"

Обещание звучит как "Minecraft как набор крейтов". Вот что верно на 2026-11-10:

- 100 пакетов собираются без Bevy. Проверка в `xtask/src/checks.rs` падает, если крейт ниже слоя 4 требует Bevy. 9 пакетов собираются еще и без std (`wasm32v1-none`), 11 - для браузера (`wasm32-unknown-unknown`).
- Крейты не опубликованы на crates.io. Мешают две вещи: некоторые крейты встраивают файлы из-за пределов своей папки, а API протокола и сети возвращают ошибки `anyhow`. См. <Status issue={321} />. Зависимость через git работает.
- Примеров использования как библиотеки пока нет: ни прокси, ни бота, ни лобби, ни рендерера карт. Первые три запланированных примера (`hello_server`, `lobby`, `arena`) отслеживаются в <Status issue={287} />.
- Публичный API слоев с 1 по 4 нестабилен. Каждый `pub`-элемент там станет обязательством, поэтому его сначала пересматривают.
