mcrs - репозиторий из {fact('crates')} крейта, разложенных по семи слоям. Каждый слой должен зависеть только от слоев ниже, поэтому вы берете нужные слои и не платите за то, что выше. Прокси хватит двух нижних слоев, а полному серверу нужны первые пять.[^180]

## Семь слоев

| # | Слой | Что в нем |
|---|---|---|
| 1 | Протокол | id, позиции, NBT, текст, ключи; трейты кодеков; фрейминг, сжатие, шифрование; пакеты handshake, status, login и configuration |
| 2 | Сеть | конечный автомат соединения, вход с обеих сторон, аутентификация, проксирование, фреймы, которые кодируются один раз на рассылку |
| 3 | Игровые данные и правила | реестры, собранные из датапака, блоки, предметы, сущности, чанки, сохранения Anvil и их пакеты; ядра без Bevy для освещения, генерации мира и симуляции блоков |
| 4 | Движок | плагины Bevy для миров, измерений, источников чанков, игроков, событий и команд, а также драйверы ядер; ванильного поведения по умолчанию нет |
| 5 | Ваниль | что делают блоки, предметы и мобы, генерация мира и освещение в виде отключаемых плагинов |
| 6 | Рендеринг | построение мешей и пайплайны над данными слоя 3; без сети, клиента и сервера |
| 7 | Приложения | бинарник сервера, клиент, примеры и инструменты |

Крейты лежат в [`crates/`](https://github.com/andreypfau/mcrs/tree/main/crates). Крейт, привязанный к игре, называется `mcrs_minecraft_<name>`. Крейт для понятия, которое от игры не зависит, называется `mcrs_<name>`, например крейты ядра движка `mcrs_engine_cell`, `mcrs_engine_link`, `mcrs_engine_muxer` и `mcrs_engine_store` или `mcrs_molang` и `mcrs_voxel`. Все крейты с их слоями перечислены на [карте крейтов](/docs/ru/crates/overview/).

Ниже слоя 4 Bevy подключается необязательной фичей, а ниже слоя 2 необязателен и tokio, потому что с tokio работает только сетевой слой. Часть границ проверяет CI. Проверка `layers` в `xtask/src/checks.rs` падает, если `mcrs_minecraft_protocol` или `mcrs_minecraft_network` тянет крейт игровых данных, если запекание моделей или рендерер сущностей тянет сеть, клиент или сервер, а также если крейт инвентаря, которым пользуется клиент, например `mcrs_minecraft_inventory_client`, тянет крейт сервера.

## Ядра хранят правила, драйверы их запускают

Слой 3 обходится без Bevy, потому что правила игры и код, который их планирует, разнесены по разным частям.

Ядро (kernel) - обычный Rust, которому принадлежат правила одной области: обновления блоков, освещение, генерация мира или движение сущностей. Bevy и tokio оно не использует. Один шаг ядра - это вызов функции. На вход идут состояние и представление мира, на выходе получаются записи и сообщения в буферах, которыми владеет вызывающий код. Одинаковые входные данные дают одинаковый результат.

Драйвер запускает ядро. В слое 4 драйвер - плагин Bevy, который читает мир, вызывает ядро и записывает результат обратно. Планировщиком между системами остается Bevy, и своего планировщика между ними mcrs не добавляет. Это решение записано в разделе 13 [заметки о шардировании](https://github.com/andreypfau/mcrs/blob/main/docs/minecraft-bevy-sharding-architecture.md). Без Bevy драйвер превращается в обычный цикл, поэтому бот, инструмент для карт или тест могут использовать ядро напрямую.

Если вы пришли из Paper, представьте ядро как логику ванильной системы, из которой убрали объект сервера, так что ее можно вызвать откуда угодно. Драйвер - та часть, которая знает о тиках.

## Что сегодня значит "набор деталей"

Проект обещает "Minecraft как набор крейтов". Вот насколько это выполняется на 2026-11-18.

В CI без Bevy собираются {fact('crates_no_bevy')} пакетов, и проверка в `xtask/src/checks.rs` падает, если крейт ниже слоя 4 требует Bevy. Еще и без std, под цель `wasm32v1-none`, собираются {fact('crates_no_std')} пакетов, а для браузера, под цель `wasm32-unknown-unknown`, - {fact('crates_wasm32')}.

На crates.io крейты не опубликованы. Мешают две вещи: часть крейтов встраивает файлы из-за пределов своей папки, а API протокола и сети возвращают ошибки `anyhow`.[^321] Зависимость через git работает, и этот способ описан на странице [Использование крейтов в своем проекте](/docs/ru/crates/use-as-library/).

Первые примеры использования библиотеки лежат в [`examples/`](https://github.com/andreypfau/mcrs/tree/main/examples). Каждый пример - отдельный пакет workspace, а в `examples/dependencies.json` для него записан список крейтов, которые ему тянуть нельзя. CI падает, если такой крейт попал в дерево зависимостей примера.[^288]

| Пример | Что показывает |
|---|---|
| `status_ping` | запрашивает статус сервера без Bevy |
| `inventory_save_viewer` | читает файл игрока без Bevy |
| `player_attributes` | выводит и меняет атрибуты в файле игрока без Bevy и движка |
| `loot_validate` | проверяет таблицы лута датапака без движка |
| `inventory_minigame` | запускает плагины инвентаря без его пакетной части |
| `inventory_bot_click` | заходит на сервер как бот без окна, рендерера и крейтов GUI и кликает в меню своего инвентаря |

Готового прокси, лобби или рендерера карт, с которого можно начать, пока нет, а единственный бот, `inventory_bot_click`, только выполняет заданный сценарий кликов в инвентаре. Запланированные `hello_server`, `lobby` и `arena` - самые маленькие серверы, которые запускают движок без ванильного поведения.[^287]

Публичный API слоев 1-4 нестабилен. Каждый `pub`-элемент там станет обязательством перед пользователями, поэтому сначала API проходит ревью.
