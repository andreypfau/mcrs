Ванильный сервер выполняет игровой тик в одном потоке: по очереди обходит мир и каждую сущность. Java-форки выносят из этого потока отдельные задачи. mcrs для каждого куска работы спрашивает другое: что он читает и что пишет? Работа, которая не трогает одни и те же данные, идет одновременно. Ниже описано, как это устроено и что уже работает параллельно.

## Один цикл или системы над данными

В ECS поведение - это набор систем. Каждая система выполняет одно преобразование над всеми сущностями, у которых есть нужные ей данные. Bevy запускает две системы одновременно, если их доступ к данным не пересекается. Такие конфликты проверяет планировщик Bevy при построении графа расписания, а не компилятор. Поэтому блокировки писать не нужно.

Порядок между группами систем задают наборы систем (system sets), а расписание проект проверяет на неоднозначность (заметка о шардировании, раздел 13). Тик разбит на несколько фаз с небольшим числом точек синхронизации (<Status issue={364} state="partial" />).

## Тайлы и замороженный снапшот

Внутри одной системы сущностей все равно много. Для сущностей mcrs использует такую модель (`docs/physics-architecture.md`, раздел 3):

1. В начале тика движок замораживает снапшот состояния, которое видят другие сущности: блоки в том виде, какими они были в конце прошлого тика, сетку тел и таблицу позиций.
2. Пространство режется на тайлы из колонок. Каждый тайл - задача над строками сущностей, которые в нем находятся.
3. Каждая сущность читает только снапшот и пишет только в свою строку. Эффекты на другие сущности (толчок, подбор предмета) собираются и применяются позже, в фиксированном порядке.

Поскольку в одном проходе никакая сущность не читает новое состояние другой, задачи не ждут друг друга и блокировки не нужны. В заметке эта схема называется Jacobi: каждая строка считается по старому состоянию. Задача стартует, когда завершены задачи, из которых она читает. Это отслеживают небольшие счетчики зависимостей на вычислительном пуле Bevy.

## Один результат при любом числе потоков

Фиксированный порядок делает результат независимым от машины. Эффекты сливаются по стабильному ключу: сохраняемому UUID сущности, а не сетевому id. Равенство между сущностями разрешается по этому же ключу. Правило записано в <Status issue={367} state="works" />, где детерминизм разделен на три уровня:

- точный, как эталон: генерация мира, арифметика движения игрока, все, что выбирается случайно по seed, сохраненному в мире;
- не зависящий от планировщика: все остальное. Одни и те же входные данные дают один и тот же тик независимо от порядка потоков;
- свободный: сущности и системы, которые не пишут в общие данные, могут выполняться в любом порядке.

Сейчас это подтверждают две проверки. Тест `tick_determinism.rs` прогоняет мир из двух ячеек 60 тиков: один раз со всеми мирами в одном потоке, другой раз с потоками. После каждого тика он хеширует все состояние симуляции и падает на первом тике, где хеши различаются.

## Попробовать самому

В крейте физики есть пример, который печатает хеш эталонной сцены (50 000 ходоков и 50 000 предметов на тайлах 32 x 32) после N тиков:

```sh
cargo run --release -p mcrs_minecraft_engine_physics --example state_hash -- <threads> <ticks>
```

Запустите его с 1 потоком и с 8 потоками: хеш в конце строки совпадет. Пример печатает и архитектуру, так что можно сравнить две машины. Код короткий:

## Что параллельно сегодня и какая цель

| Область | Состояние |
|---|---|
| Проход по сущностям над тайлами с замороженным снапшотом, хеш одинаков при любом числе потоков | есть в коде, покрыто примером и тестами выше |
| Ячейки одного мира тикают одновременно с обменом halo | есть в коде, покрыто `tick_determinism.rs` |
| Освещение и генерация мира в своих потоках, результат применяется на границе тика | есть в коде |
| Симуляция блоков: отложенные тики, обновления блоков, шарды | частично: ядра есть, шарды со слиянием и разделением - <Status issue={160} state="wip" /> |
| Редстоун | не начат: <Status issue={190} state="wip" /> |
| Одно измерение на многих машинах | цель: <Status issue={181} state="wip" /> |

<Aside type="caution" title="WIP">
Редстоун и раскладка на много узлов - направления, а не готовые возможности. В <Status issue={190} state="wip" /> сказано, что редстоун сначала будет семантическим (результаты и задержки совпадают с ванилью, порядок внутри тика может отличаться), а точный порядок придет позже сменой одной политики упорядочивания. Фермы под него пока не планируйте. Сейчас в проекте редстоуна нет вообще.
</Aside>

## Работа пропорциональна изменениям

Вторая идея рядом с параллелизмом: то, что не меняется, ничего не стоит. Покоящаяся сущность ждет события, а не проверяется каждый тик, а ячейка, которой нечего тикать, пропускается. Это решение из <Status issue={365} state="partial" />: редкие изменения в большой популяции идут через явную очередь работы. ИИ мобов использует ожидания вместо проверок на каждом тике.

Пока не измерены стоимость тика простаивающего сервера (<Status issue={320} state="wip" />) и память на секцию (<Status issue={324} state="wip" />). Чисел бенчмарков по мобам проект на этой странице не публикует. Что есть в PERF.md, с машиной и сценарием рядом с каждым числом, смотрите в разделе [Производительность](/docs/ru/project/performance/).
