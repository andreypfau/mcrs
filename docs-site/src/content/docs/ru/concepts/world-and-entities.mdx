Страница короткая намеренно. Раскладка для блоков устоялась, а для сущностей и API доступа к миру еще меняется. Для знающих Paper главное отличие в том, что "чанк" здесь означает две разные вещи, а моб - не объект.

## Три уровня

| Уровень | Размер | Для чего нужен |
|---|---|---|
| Секция | 16 x 16 x 16 блоков | единица хранения блоков, света и сжатия палитры |
| Колонка | 16 x высота x 16 блоков | вертикальная стопка секций; владеет картами высот |
| Измерение | без границ | верхний контейнер; владеет индексом колонок и индексом секций |

В движке каждый из них - сущность ECS с компонентом-маркером (`Section`, `Column`, `Dimension` в `mcrs_minecraft_engine_world`). mcrs говорит "секция" и "колонка" и избегает голого "чанка", потому что по слову "чанк" не понять, какое из двух имеется в виду. Типы позиций `BlockPos`, `SectionPos` и `ColumnPos` - обычная математика координат в `mcrs_minecraft_core`, без состояния ECS. Данные блоков внутри секции хранятся в палитре в стиле `PalettedContainer`, как в игре.

Каждое измерение - отдельный мир Bevy, поэтому у него и собственный тик. На этом строятся [Ячейки и путь к многим узлам](/docs/ru/concepts/scaling/) и плагины измерений, которые пишутся в разделе [Измерения - отдельные миры](/docs/ru/plugins/dimensions/).

## Билеты решают, что горячее

Пространство тикает, только если его покрывает билет (ticket): область симуляции игрока, область спавна, загрузчик чанков. Код держит билеты загрузки на колонках, трехмерные области симуляции игроков и стадию каждой секции (`lifecycle/` в модуле мира). Холодное пространство - это данные, которые не тикают. Благодаря этому нетронутая секция ничего не стоит.

## Один API для чтения мира: volume

Сегодня блоки читают несколько путей кода, и каждый через свое представление: крейт чанков, генератор мира, движок освещения, построитель мешей, клиент. Каждый по-своему отвечает на "секция не загружена". <Status issue={486} state="partial" /> (миграция по шагам) заменяет их одним крейтом слоя 3, `mcrs_minecraft_volume`:

- у volume есть границы, и для каждой секции он сообщает, можно ли ее записывать, она только для чтения, принадлежит другому владельцу, не загружена или находится снаружи;
- возможности вынесены в отдельные трейты (блоки, биомы, высоты, свет, блок-сущности и изменяемые формы), обобщенные, без динамической диспетчеризации на каждый блок;
- основной путь идет по секциям и палитрам, а доступ по одному блоку - курсор поверх него;
- при доступе ничего не загружается, а ошибки - типы, по которым можно делать match.

Крейт есть и экспортирует эти типы. Вызывающий код переводят на него за семь шагов, перечисленных в issue (представление измерения в движке, высоты и биомы, снапшоты и свет, построение мешей и клиентское хранилище и так далее), поэтому часть кода еще использует старые представления.

API volume - это направление. Миграция идет, и трейты еще могут измениться: <Status issue={486} state="partial" />.
</Aside>

## Мобы - это строки, а не сущности

Сущность Bevy на каждого моба была бы гибкой, но дорогой. Для сущностей, которые симулирует сервер, mcrs держит строки в хранилище по тайлам (`mcrs_minecraft_entity_rows`) с плотной колонкой горячего состояния для мобов. Предметы и сферы опыта - только строки. Игроки тоже строки. На каждом тике один проход параллельно по тайлам обновляет каждую строку по замороженному снапшоту. Почему это дает один результат при любом числе потоков, объясняет страница [Как тик работает параллельно](/docs/ru/concepts/parallel-tick/).

Холодное состояние моба (компоненты, которые может понадобиться читать из обычной системы) остается в ECS. В заметке о дизайне такое разделение называется "гибридным": горячее состояние в строках, холодное в компонентах. В ядре хранилища нет Bevy, а feature `bevy` превращает его в ресурс.

Что не решено: точная форма API, чтобы читать и менять эти строки из собственного плагина. Решения по нему пока нет, поэтому описать его на стабильной странице нельзя. Стоимость памяти на секцию и на компонент сущности тоже не измерена: <Status issue={324} state="wip" />.
