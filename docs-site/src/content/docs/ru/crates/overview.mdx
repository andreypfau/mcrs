mcrs состоит из {fact('crates')} крейтов в `crates/`, и брать их можно по одному. Здесь они перечислены по слоям, и у каждого отмечено, собирает ли его CI без Bevy, без `std` или под wasm32. По этой странице удобно найти нужный крейт и понять, что он тянет за собой.

Таблицы крейтов поддерживаются вручную по манифестам пакетов и трем спискам в [`xtask/src/checks.rs`](https://github.com/andreypfau/mcrs/blob/main/xtask/src/checks.rs). Генератор, который будет пересобирать их при каждой сборке документации, запланирован. Пока его нет, таблицы могут устареть, поэтому смотрите дату проверки внизу страницы.

## Как читать таблицы

Крейты разложены по слоям из [AGENTS.md](https://github.com/andreypfau/mcrs/blob/main/AGENTS.md#layers). CI проверяет только некоторые части правила слоев. Крейты wire и сети не должны линковать игровые данные. Крейты, которые запекают модели, вычисляют значки предметов или рисуют сущности, не должны линковать сеть, клиент или сервер, чтобы просмотрщик работал без соединения. Play-пакеты в `mcrs_minecraft_protocol_game` не должны линковать раскладку инвентаря и правила кликов, слотов игрока и транзакций; ключи меню они берут из `mcrs_minecraft_menu_key`. `mcrs_minecraft_vanilla_inventory` не должен зависеть от пакетной границы инвентаря. `mcrs_minecraft_engine_item`, `mcrs_minecraft_player_holders` и `mcrs_minecraft_inventory_client` не должны линковать серверные крейты `mcrs_minecraft_engine`, `mcrs_minecraft_engine_server`, `mcrs_minecraft_save` и `mcrs_minecraft_server`, чтобы ими мог пользоваться клиент.

Слой крейта нигде не хранится в коде. Его назначили вручную по списку слоев в AGENTS.md и описанию крейта, и никакая проверка его не подтверждает, так что считайте его ориентиром.

Во всех таблицах одни и те же пять столбцов. Имя крейта совпадает с именем пакета, а остальные четыре берутся отсюда:

| Столбец | Откуда берется |
|---|---|
| Описание | Основано на `description` в `Cargo.toml` каждого крейта, проверено и дополнено по исходникам. В пяти манифестах описания нет или в нем стоит только имя крейта |
| Без Bevy | `NO_BEVY_PACKAGES` в [`checks.rs`](https://github.com/andreypfau/mcrs/blob/main/xtask/src/checks.rs). CI запускает для этих крейтов `cargo check --no-default-features` и падает, если какому-то нужен Bevy |
| no_std | `NO_STD_PACKAGES` в том же файле. CI собирает эти крейты под `wasm32v1-none` без `std` |
| wasm32 | `WASM32_PACKAGES` в том же файле. CI собирает эти крейты под `wasm32-unknown-unknown` |

В списке "без Bevy" {fact('crates_no_bevy')} пакета. В списке no_std {fact('crates_no_std')} крейтов, в списке wasm32 - {fact('crates_wasm32')}. Прочерк значит только, что крейта нет в списке CI. Собраться в таком режиме он все равно может.

## С каких крейтов начать

В таблице ниже названы крейты, с которых стоит начать в пяти видах проектов. Для версии из репозитория используйте git-зависимость, как описано на странице [Использование крейтов в своем проекте](/docs/ru/crates/use-as-library/). В [`examples/`](https://github.com/andreypfau/mcrs/tree/main/examples) лежат шесть небольших программ на этих крейтах. `status_ping` опрашивает сервер через крейты протокола и сети без Bevy, `inventory_save_viewer` и `player_attributes` читают файл игрока, `loot_validate` проверяет таблицы лута датапака, `inventory_minigame` запускает плагины инвентаря без их пакетной границы, а `inventory_bot_click` - бот без окна и рендерера, который заходит на сервер и кликает в меню своего инвентаря. CI проверяет, что в дереве зависимостей каждого примера нет запрещенных для него крейтов.[^288] Первый туториал - [разбор SNBT](/docs/ru/crates/hello-nbt/). Примеры минимального сервера, лобби и арены запланированы.[^287]

| Что вы пишете | С чего начать | Состояние |
|---|---|---|
| Прокси | `mcrs_minecraft_protocol` и `mcrs_minecraft_network`. Оба в списке "без Bevy", и `xtask` проверяет, что они не линкуют игровые данные | Крейты есть. Саму библиотеку прокси с маршрутизацией и пересылкой отслеживает <Status issue={296} />, онлайн-режим - <Status issue={82} /> |
| Бот | Те же два крейта и `mcrs_minecraft_client_world`, который хранит состояние мира клиента без окна и рендерера. В списке "без Bevy" его нет. Для инвентаря добавьте `mcrs_minecraft_inventory_client`, который применяет пакеты инвентаря и предсказывает и отправляет клики, и `mcrs_minecraft_container_click`, который описывает вид клика, кнопку и запись меню | Состояние клиента отделено от рендеринга (<Status issue={301} />). Бота-ходока отслеживает <Status issue={302} /> |
| Карта или просмотрщик мира | `mcrs_minecraft_anvil` для регионов (он есть и в списке wasm32), `mcrs_minecraft_chunk` и `mcrs_minecraft_block` для данных, `mcrs_minecraft_mesh` для мешей | Крейты есть. Тайлы вида сверху без окна отслеживает <Status issue={297} />, просмотрщик моделей - <Status issue={298} /> |
| Инструмент для NBT, команд или датапаков | `mcrs_minecraft_nbt`, `mcrs_minecraft_snbt`, `mcrs_minecraft_nbt_path`, `mcrs_command`, `mcrs_minecraft_datapack` | Крейты есть. `mcrs_command` и `mcrs_minecraft_snbt` читают и пишут то же, что читает и пишет игра. `mcrs_minecraft_nbt_path` разбирает путь NBT, выбирает, создает и записывает теги, но тестов, которые сравнивают его с игрой, пока нет |
| Предпросмотр генерации мира | `mcrs_minecraft_worldgen_generator` и крейты `mcrs_minecraft_worldgen_*` | Предпросмотр по сиду через публичный API отслеживает <Status issue={299} />. Сам генератор совпадает с ванилью в parity-тестах на эталонных сидах |

"Крейты есть" значит, что они собираются в этом репозитории. Стабильный API ни один из них не обещает, а README есть только у четырех крейтов.

Для собственного GUI `CreativeContent::build` из `mcrs_minecraft_creative_content` строит списки вкладок и поиска без Bevy, а `SearchQuery` фильтрует их. `append_tooltip_parts` из `mcrs_minecraft_item_tooltip` добавляет текстовые части в буфер вызывающего кода. В слое рендеринга `resolve` из `mcrs_minecraft_item_icon` возвращает значение `ItemIcon` по стеку, а `IconMeshes` хранит меши для его отрисовки. Эти крейты не зависят от клиента или сервера.

## Зачем некоторым крейтам Bevy

Правила слоев делают Bevy необязательным ниже слоя 4, а tokio - ниже слоя 2. Адаптеры движка, ванильные плагины, клиент и сервер используют Bevy, а общие крейты движка могут работать без него. Для типов данных и чистых правил начните со слоев с 1 по 3 и проверьте нужные feature-флаги по манифесту и колонкам CI. Слои 4 и 5 разобраны на странице [Слои](/docs/ru/concepts/layers/).
