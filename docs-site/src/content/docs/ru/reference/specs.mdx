<Aside type="note" title="Написано для ИИ-агентов и авторов спецификаций">
Файлы в `docs/spec/` написаны для ИИ-агентов и для людей, которые пишут спецификации. Они следуют правилам ASD-STE100 Simplified Technical English, как сказано в `docs/spec/README.md`. Поэтому они точные и сухие. Найдите нужный файл по этой странице и дальше читайте уже его.
</Aside>

Каждый файл в [docs/spec](https://github.com/andreypfau/mcrs/tree/main/docs/spec) описывает поведение одного домена в виде данных, то есть его входы, выходы, порядок, тайминги и константы. Устройство игрового кода спецификация не описывает никогда. Кроме того, по [правилу clean-room](https://github.com/andreypfau/mcrs/blob/main/docs/clean-room.md) исполнитель вправе узнавать игровое поведение для правила только из спецификаций.

В заголовках некоторых спецификаций версией игры все еще названа `26.4-snapshot-4`. Проект следует за <code dir="auto">{fact('snapshot')}</code>, эта версия задана в `assets/minecraft/version.json`.

## Файлы по доменам

Id правила, например `CMD-TP-013`, состоит из префикса домена, темы и номера. По этим id на правила ссылаются тесты и issue. В таблице `*` заменяет часть с темой.

| Домен | Файлы в `docs/spec/` | Префикс id |
|---|---|---|
| Вход, статус, сжатие | `login.md`, `status.md`, `compression.md` | `LOGIN`, `STATUS`, `FRAME` |
| Whitelist и баны | `whitelist.md`, `bans.md` | `WL`, `BAN` |
| Команды: парсер, дерево, права | `command-parser.md`, `commands-packet.md`, `command-permissions.md`, `argument-*.md` (block, coordinates, entity, keywords, resource) | `CMD`, `CMDP`, `PERM`, `ARG-*` |

Большинство спецификаций перечисляют свои префиксы id в таблице ближе к началу. Если та таблица расходится с этой страницей, полным списком считайте таблицу в файле.

В папке `docs` рядом со спецификациями лежат и заметки, например [docs/command-dimensions.md](https://github.com/andreypfau/mcrs/blob/main/docs/command-dimensions.md) и [docs/entity-render.md](https://github.com/andreypfau/mcrs/blob/main/docs/entity-render.md). Это рабочие заметки, а не спецификации.

## Как читать правило

У правила есть заголовок с id, раздел поведения и строка происхождения (provenance):

```text
Provenance: source_suggested. Kind: semantic. Confidence: medium. Experiment: ...
```

Происхождение говорит, откуда взято правило. Метки определены в разделе 0.3 файла `docs/spec/registry.md`.

| Метка | Значение |
|---|---|
| `black_box_confirmed` | Подтверждено артефактом, который произвела игра, с указанием пути. |
| `source_suggested_black_box_confirmed` | Взято из эталонного поведения и согласуется с указанным артефактом. |
| `source_suggested` | Взято из эталонного поведения, артефакта пока нет. Уверенность не выше средней, приложен эксперимент. |
| `documentation` | Публичное поведение, описанное в документации для игроков. |
| `design` | Выбор mcrs. Правило объясняет почему. |
| `unresolved` | Не решено. Собрано в разделе в конце файла. |

Kind говорит, насколько точным должно быть правило.

| Kind | Что фиксирует правило |
|---|---|
| `wire` | Байты и id, которые декодирует клиент ванили. |
| `client agreement` | Сервер должен согласоваться с клиентом. |
| `semantic` | Смысл и результат, но не внутренний порядок. |
| `layout` | Позиции и размеры GUI. |
| `deviation` | В эталоне есть дефект, и правило описывает корректное поведение. |
| `unspecified` | Parity-тест не должен это сравнивать. |

Еще в файле есть раздел "Intentional deviations", где записано, чем mcrs намеренно отличается от ванили. В каждой записи указаны id правила, эталонное поведение, видит ли отличие клиент и что с ним делает тест.

В `registry.md` сказано, что ни один из его экспериментов не запускался. Поэтому относитесь к правилу `source_suggested` как к утверждению, за которым пока нет игрового артефакта.
