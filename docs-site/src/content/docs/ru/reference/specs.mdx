<Aside type="note" title="Написано для ИИ-агентов и авторов спецификаций">
Файлы в `docs/spec/` написаны для ИИ-агентов и для людей, которые пишут спецификации. Они следуют правилам ASD-STE100 Simplified Technical English, как сказано в `docs/spec/README.md`. Поэтому они точные и сухие. Найдите нужный файл по этой странице и дальше читайте уже его.
</Aside>

Спецификации доменов в [docs/spec](https://github.com/andreypfau/mcrs/tree/main/docs/spec) описывают поведение в виде данных: входы, выходы, порядок, время и константы. README задает правила оформления. Устройство игрового кода спецификация не описывает никогда. Исполнитель работает по спецификациям, публичной документации для игроков, артефактам игры и разрешенному коду репозитория, как требует [правило clean-room](https://github.com/andreypfau/mcrs/blob/main/docs/clean-room.md).

В заголовке спецификации снапшот не указывают. Проект следует за <code dir="auto">{fact('snapshot')}</code>, эта версия задана в `assets/minecraft/version.json`.

Запись в индексе означает, что спецификация есть. Она не подтверждает готовность к реализации или наличие работающего поведения. В `client-knowledge.md` и `reach.md` еще есть непроведенные эксперименты и правила с меткой `source_suggested`; описанные в них компенсация задержки и проверка дальности действия пока не работают.

Большинство спецификаций перечисляют свои префиксы id в таблице ближе к началу. Если та таблица расходится с этой страницей, полным списком считайте таблицу в файле.

В папке `docs` рядом со спецификациями лежат и заметки, например [docs/command-dimensions.md](https://github.com/andreypfau/mcrs/blob/main/docs/command-dimensions.md) и [docs/entity-render.md](https://github.com/andreypfau/mcrs/blob/main/docs/entity-render.md). Это рабочие заметки, а не спецификации.

## Как читать правило

Правило в спецификации появляется, только если разницу кто-то может увидеть: клиент ванили, игрок в обычной игре, датапак или файл сохранения либо пользователь библиотеки. У правила есть заголовок с id, раздел поведения и строка происхождения (provenance):

```text
Provenance: source_suggested. Kind: semantic. Confidence: medium. Experiment: ...
```

Происхождение говорит, откуда взято правило. Метки определены в разделе 0.3 файла `docs/spec/registry.md`.

| Метка | Значение |
|---|---|
| `black_box_confirmed` | Подтверждено артефактом, который произвела игра, с указанием пути. |
| `source_suggested_black_box_confirmed` | Взято из эталонного поведения и согласуется с указанным артефактом. |
| `source_suggested` | Взято из эталонного поведения, артефакта пока нет. Уверенность не выше средней, приложен эксперимент. |
| `documentation` | Публичное поведение, описанное в документации для игроков. |
| `design` | Выбор mcrs. Правило объясняет почему. |
| `unresolved` | Не решено. Собрано в разделе "Нерешенное" файла. |

Kind говорит, насколько точным должно быть правило.

| Kind | Что фиксирует правило |
|---|---|
| `wire` | Байты и id, которые декодирует клиент ванили. |
| `client agreement` | Сервер должен согласоваться с клиентом. |
| `semantic` | Смысл и результат, но не внутренний порядок. |
| `layout` | Позиции и размеры GUI. |
| `deviation` | mcrs намеренно расходится с дефектом или случайностью эталона, и правило описывает ожидаемое поведение. |
| `quirk` | mcrs сохраняет случайность эталона, потому что от нее зависит клиент ванили, датапак или файл сохранения. Решить, что правило - quirk, может только владелец. |
| `unspecified` | Поведение выбирает реализация, и parity-тест не должен его сравнивать. Правило задает границу, например "не реже раза в 40 тиков". |

Еще в файле есть раздел "Намеренные отклонения", где записано, чем mcrs намеренно отличается от ванили. В каждой записи указаны id правила, эталонное поведение, причина, видит ли отличие клиент, баг-репорт игры, если он есть, и что с отличием делает тест. В разделе "Известные особенности ванили" для каждого quirk указано, кто от него зависит и в каком issue владелец решил его сохранить.

За правилом `source_suggested` пока нет игрового артефакта, это только утверждение. Спецификация готова, когда ее раздел "Нерешенное" пуст и ни одно правило не помечено `source_suggested`. За неготовую спецификацию исполнитель не берется.
