This page is for an admin who wants to point the mcrs server at a world. The server reads a Java Edition world of the same game version, and it saves the world and its players. Changed chunks go back to the region files of the folder, so a block edit survives a restart.

<StatusRows areas="persistence" />

## Pass a world folder to open a Java world

Give the server a folder as the first argument. The [README Quick start](https://github.com/andreypfau/mcrs#quick-start) shows how to build and start the server.

The server has no authentication and listens on all network interfaces. Keep it on your machine or a trusted local network; do not open its port to the internet.

```bash
cargo run --release -- "<path to a world folder>"
```

The folder must exist, or the server prints "not a world folder" and exits. When the folder holds a world, the server takes the seed and the list of dimensions from the world generation settings of the save, and a seed in `MCRS_WORLD_SEED` or a preset in `MCRS_WORLD_PRESET` does not override them. The game mode of a new player then comes from `level.dat`. If `level.dat` is missing and only its backup `level.dat_old` is left, the server opens the world from the backup. The chunks come from the region files of the save, which Java Edition stores in the Anvil format.

A folder with neither `level.dat` nor saved world generation settings, such as an empty one, becomes a new world. The server writes `level.dat` and the world generation settings into it from `MCRS_WORLD_SEED`, `MCRS_WORLD_PRESET` and `MCRS_DEFAULT_GAMEMODE`, so the next start opens the same world with the same seed.[^969]

While the server runs, it holds a lock on `session.lock` in the world folder, as the game does. When another process holds that lock, the server writes nothing to the folder and does not start.[^969]

`level.dat`, every chunk and every player file carry a `DataVersion`, the number of the game version that wrote them. The server accepts a file only when that number matches the game version of this build, which is <code dir="auto">{fact('snapshot')}</code> with world version 5127, as [`version.json`](https://github.com/andreypfau/mcrs/blob/main/assets/minecraft/version.json) states. The server refuses a file from any other version with an error that names the version it found and the version it expected. It also refuses a `level.dat` or a chunk that has no `DataVersion`.

## Older worlds are not converted

mcrs has no converter for saves of older versions and will not get one, because it follows one snapshot at a time and keeps no compatibility chain.[^388] If you have an older world, open it once in a vanilla client of the right snapshot so that the game rewrites it, and then give the folder to mcrs. A field that no type claims also fails the load, so the server does not keep such a field as raw bytes.[^388]

## Without a folder, the server generates a world

When you start the server with no argument, it generates a world from a preset. Nothing of that world reaches the disk, and there is no autosave. It has no player files either, because the server builds the path of a player file from the world folder. Three settings shape the world, and the server reads them once at start. The full list of settings is in [`server_settings.rs`](https://github.com/andreypfau/mcrs/blob/main/crates/mcrs_minecraft_server_settings/src/server_settings.rs).

| Variable | Meaning | Default |
|---|---|---|
| `MCRS_WORLD_SEED` | The seed, as a signed or unsigned 64-bit number | `0` |
| `MCRS_WORLD_PRESET` | The name of a world preset in the loaded data pack, such as `normal`, `minecraft:normal` or `flat` | `normal` |
| `MCRS_DEFAULT_GAMEMODE` | Game mode of a new player | `creative` |

World generation matches vanilla in parity tests on the reference seeds. [Parity](/docs/en/concepts/parity/) says what those tests cover.

## The server saves the world

| Data | State |
|---|---|
| Player files | Saved. The server writes each player to `players/data/<uuid>.dat` in the world folder on disconnect, and an autosave writes them every 6000 ticks, which is vanilla's own interval |
| A clean stop with players | <Status pr={624} state="works" />. On the first SIGINT or SIGTERM the server disconnects every player with the vanilla shutdown reason, saves them and exits. A second signal exits at once |
| Chunks and block edits | Saved. The server writes each changed chunk back to its region file in the world folder, and an autosave does this every 6000 ticks |
| A clean stop with the world | On the first SIGINT or SIGTERM the server also saves every loaded chunk and the world state files before it exits. If a save fails, the exit status shows an error |
| World state files | The server reads the spawn, the weather, the game rules, the world clocks and the world generation settings of the save at start, and writes them back on the autosave |
| Unreadable regions | The server copies a chunk it cannot decode, or a region with a damaged slot, to `<save>/quarantine/` before it replaces it. A file that cannot be read stays as it is on the disk |

The server protects a player file that it cannot parse. The player joins empty, and the server never saves that player over the old file. From a file it can parse, the server reads the inventory, the ender chest, the selected hotbar slot, the equipment and the attributes of the player, and it writes them back on save.[^521] A key of the format that mcrs has no behavior for yet goes back to the file unchanged.[^744]

Player health is also restored on join and written back on save. A new player without a file starts at maximum health.[^1082]

## Data packs load once, at start

The server loads the vanilla data pack and the local packs selected by `ServerCorePlugin::local_packs` into the registries at start. The bundled server selects `mcrs` and `beta`. The vanilla pack comes from the game jar. Local packs live under `mcrs/datapacks/` in the assets root of the build, with namespace folders directly beneath each pack root and no `data/` wrapper. Other directories are not enabled automatically.

The `check_pack` example of `mcrs_minecraft_game_registries` prints registry diagnostics without starting a server and exits with an error if any diagnostic is an error. Its input uses the standard pack layout with `pack.mcmeta` and `data/`. At this commit it only enables an input directory named `mcrs` or `beta`; other names are filtered out, so a successful exit does not validate an arbitrary data pack.

A block drops what its loot table yields, and the server looks the table up by name among the tables of all loaded packs, so a table under the same name in a local pack changes the drop. When each dimension world starts, the server checks the tables and writes every problem to the log as an error, such as an unknown item, a missing table or a table that refers back to itself. The example [`loot_validate`](https://github.com/andreypfau/mcrs/blob/main/examples/loot_validate/README.md) runs the same check without a server and prints each problem on its own line.

The server cannot reload a pack while it runs, so you restart it after you change one. `/reload` and live enabling of packs are planned.[^316] The plan is that a reload replaces the data at a tick boundary and refuses changes that the saved world depends on, such as the height of a dimension type.

There is no source yet for how the server treats a `datapacks` folder inside a world folder, so this page makes no claim about it.
