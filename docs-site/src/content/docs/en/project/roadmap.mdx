## Four directions

The project has no tracking epics in the usual sense. Four open issues with the title "Direction:" play that role. Each carries a `direction:*` label and links to the work under it.

### mcrs as a library, from a proxy to a full server

<Status issue={180} />

A proxy, a bot, a lobby, a minigame, a world map and a full server need different prefixes of the same layers, and none of them should pay for a layer it does not use. The issue defines seven layers, each depending only on those below: data and wire, network, game data, engine, vanilla, rendering, applications. Every `pub` item in layers 1 to 4 is a commitment to users.

What exists today: 122 crates, 100 of them build without Bevy and 9 without `std` in CI, and 11 build for `wasm32` (`xtask/src/checks.rs`). What does not: crates are not published (<Status issue={321} />), and the examples of the library (milestone "Library examples") are open.

There is no facade or API crate and none is planned. The decision <Status issue={437} /> says the public surface is the vocabulary crates, the plugins with their system sets, and the components, resources and messages that those plugins own. A loader for plugins that are not compiled into the server (jar, wasm, scripts) has no decision yet.

### One dimension on many nodes for thousands of players

<Status issue={181} />

The target is ten thousand players in one dimension with the unmodified vanilla client, with a bounded number visible to each client. The shape in the issue: clients talk only to an edge that holds each connection for the whole session. Simulation is split into shards that own related work. Nodes own chunks and their shards. A coordinator owns the map of chunks to nodes and the global state. Results must not depend on thread count or shard layout.

What exists today: worlds that tick as parallel cells behind a muxer thread with a shared data layer on one machine (<Status pr={646} state="works" />). What does not: a setup across more than one machine, and a measured player count. Redstone is not built.

### Vanilla gameplay and behavior tests on that architecture

<Status issue={182} />

Vanilla behavior is the largest body of work. The issue builds it as removable plugins over the engine, and wants each mechanic proved by a behavior test whose expected result comes from a vanilla test server, not from our reading of code. Exact behavior (protocol, saves, player movement, world generation) is compared tick for tick. Semantic behavior (redstone, fluids, neighbor updates) is compared on the outcome.

What exists today is in [Status](/docs/en/start/status/). The gameplay milestones from "Redstone" to "Advancements and statistics" (17 of them) have no closed issue.

### Library code without shared ownership, locks, trait objects or hot-path allocation

<Status issue={566} />

The library crates should run in a proxy, a bot, a web client and a test without an engine. The issue sets a target for layers 1 to 4: no `Arc` or `Rc`, no `Mutex`, `RwLock`, `RefCell` or `Cell` in data types, no `dyn` or `Any`, and no allocation on hot paths. When the issue was written, `Arc` appeared in 119 source files. The README line "no Arc, no Mutex" is this goal, not the current state.
