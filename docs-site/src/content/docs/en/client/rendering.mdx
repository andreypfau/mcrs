This page is a map for a contributor who wants to read the renderer. It gives the idea of each part in a few lines and sends you to the notes that hold the rules and the numbers, so it does not repeat them.

<Aside type="caution" title="WIP">

The restart is a series of tasks, from layouts shared by Rust and WGSL to tinted overlays folded into one sprite.[^16][^37] The result will be measured against the baseline from before the restructure.[^330] Expect this page to change with that work.
</Aside>

Two crates do the drawing. `mcrs_minecraft_render` draws the terrain and the sky, and `mcrs_minecraft_entity_render` draws the mobs. The renderer is layer 6 in the [crate map](/docs/en/crates/overview/), so it works on the data of the layers below and has no network, client or server code.

## Terrain lives in a few large GPU buffers

The renderer writes chunk meshes into three large geometry buffers called arenas, which hold quads, models and faces. An allocator packs blocks toward offset zero, and an arena grows in steps with spare capacity as geometry arrives.

The frame is a chain of render systems that run in a fixed order. They upload the changed geometry, run the cull, draw the sky into the world image, and draw the opaque terrain into a gbuffer, a set of images that keep the surface of each pixel. Then they run the occlusion test with a second opaque pass, draw the mobs, light the gbuffer in one pass, and draw the clouds and the blended terrain in a forward pass. A last pass presents the world image in the window.

## The GPU chooses what to draw

Culling means leaving out geometry that the camera cannot see. On the full path, a compute pass on the GPU tests each group of quads against the view and writes the draw arguments.

This is the full path, which the renderer takes when the device has compute shaders, indirect draws and storage buffers. WebGL2 has none of them, so in that case the renderer takes a minimal path. The shaders stay the same, the arrays they read become textures, and the renderer draws every resident group, because nothing culls them.

## Occlusion is tested against the depth of the last frame

A group can be inside the view and still hidden behind a hill. The occlusion test removes the triangles that are behind the terrain. It works against a depth pyramid built from the last frame, and it runs in two passes.

The first cull hides what the old pyramid hides, and it keeps the groups that only this test hides as candidates. The renderer then rebuilds the pyramid from the depth of the current frame, and a second cull brings back the candidates that are visible after all, in a second set of draws. Because of the second pass, nothing appears one frame late.

The occlusion pass costs time even when there is nothing to draw, so it runs only when groups are resident. You can turn it off with `MCRS_OCCLUSION=0` to see what it buys.

## Mobs are posed and drawn on the GPU

The design in `docs/entity-render.md` aims at 100,000 mobs in one world without a frame drop. That number is the goal of the note and is not a measured result. The note has a section for stress scenes and gates, and the numbers behind each size are in `docs/entity-render-budget.md`.

The ECS holds the state of each mob, and the GPU holds a projection of that state in a persistent slot. The CPU writes a slot only when something changes, which means a packet, a tick or a script input. The GPU does the rest, and only for visible mobs: it culls, computes the poses, expands the faces and draws. The poses come from Molang, the expression language that the client entity definitions use, and `mcrs_molang_wgsl` lowers the Molang channels to WGSL shader code.

The note defines three execution paths of the mobs for graphics adapters of different capabilities.

| Path | What it needs |
|---|---|
| Full | Compute shaders and vertex storage |
| Compatibility | WebGPU compatibility mode |
| Minimal | No compute, for WebGL2 |

Only the full path of the mobs is built. The renderer runs the entity passes when the device takes the full path of the terrain and the passes fit its limits. Each pass binds at most 8 storage buffers, the limit of WebGPU in a browser, so a Chromium browser draws mobs over WebGPU. On WebGL2 the client draws no mobs. The web client has no measured steady frame yet.[^344]

## Far mobs are flat images

A mob that is far away does not need its full rig, the set of bones that poses the model. For each pair of a model and a texture, the renderer bakes a small set of views. A set has 16 yaws and 9 elevations at 64 by 64 texels and takes about 4.7 MB. A far mob is then drawn as an impostor, which is one quad that shows the nearest view. The renderer bakes a set lazily, when a model and a texture first appear on an active mob. Full rigs have a cap, and impostors have none. The note records the cost of each step and the choices that did not help.

A player draws through the same passes. Its skin is a layer of the entity textures that the renderer writes when the skin arrives, so a new skin needs no rebuild. A player with a skin keeps the full rig at each distance, because a baked view would keep an old skin. The server sends the pose of each player, and the client draws another player sneaking, swimming, crawling, sleeping, gliding or in a spin attack with the animations in `assets/mcrs/entity/animations/player.animation.json`. The camera and the ray that finds the target block follow the eye height of the pose of the local player.[^970] A program with no server, such as a world viewer, adds a player with `host_living_entity` from `mcrs_minecraft_entity_visual`, moves it through its `Motion` component, and gives it a model with the `PlayerModel` component and a skin with the `PlayerSkin` component. The rules are in `docs/spec/client-player-render.md`.

The survival inventory screen draws the local player through the same passes. The cull, the pose and the expand run a second time for this figure view, and `FigureDraw` draws its faces into a render pass of the host.

## Name tags and sign text

Name tags face the camera above players and named mobs. A host's `NameTag` takes precedence over the custom name from entity data; a player's profile name is the fallback. A mob also needs `SyncedData.name_visible`. Tags appear at distances below 64 blocks, or below 32 while crouching. Invisible entities and entities marked `CameraEntity` have no tag. A normal tag draws faint text through blocks and opaque text with depth; a crouching tag draws once with depth.[^1062]

`NameTagPlugin` in `mcrs_minecraft_client::name_tag` is included by `ClientTerrainPlugin`. A host can add it after the renderer and entity plugins, set `NameTag` on an entity and mark the camera's entity with `CameraEntity`. The client does not yet supply the crosshair target, hidden-HUD state or passenger state to the visibility check, so those rules do not affect tags yet. Team visibility and a score line below the name are also absent. The text pass works on the minimal WebGL2 path even though that path draws no entity models.[^1062]

Signs share the font and glyph atlas with name tags. Standing and wall signs draw each side's text only toward its viewer, so looking from inside a sign no longer shows the far side mirrored. The fix applies to both rendering paths.[^1056]

## Health and death use GUI plugins

`HealthHudPlugin` derives the hearts and food bar from the local player's `Vitals`, `FoodLevel` and maximum-health attribute each frame. `DeathScreenPlugin` follows `PlayerKilled` and sends `RequestRespawn` from its button. Both are removable GUI plugins, and the native entry point adds them. The browser entry point does not add them yet. [The client today](/docs/en/client/overview/#health-death-and-headless-clients) lists the display limits and the headless API; the HUD rules are in [`docs/spec/client-health-hud.md`](https://github.com/andreypfau/mcrs/blob/main/docs/spec/client-health-hud.md).[^1085]
