<Aside type="note" title="Written for AI agents and spec authors">
The files in `docs/spec/` are written for AI agents and for the people who write specifications. They follow the rules of ASD-STE100 Simplified Technical English, as `docs/spec/README.md` says. That is why they are exact and dry. Use this page to find the right file, then read the file itself.
</Aside>

The domain specifications in [docs/spec](https://github.com/andreypfau/mcrs/tree/main/docs/spec) state behavior as data: inputs, outputs, order, timing and constants. The README defines the writing conventions. A spec never describes the shape of game code. An implementer works from specs, public player-facing documentation, game-produced artifacts and permitted repository code, as the [clean-room rule](https://github.com/andreypfau/mcrs/blob/main/docs/clean-room.md) requires.

A spec does not name a snapshot in its header. The project follows <code dir="auto">{fact('snapshot')}</code>, which is set in `assets/minecraft/version.json`.

An entry here means that a specification exists, not that its behavior is implemented or ready to implement. In particular, `client-knowledge.md` and `reach.md` still have unrun experiments and rules marked `source_suggested`; their lag compensation and reach design is not a working check.

Most specs list their own id prefixes in a table near the top. When that table and this page differ, the table in the file is the full list.

The `docs` folder also has notes next to the specs, for example [docs/command-dimensions.md](https://github.com/andreypfau/mcrs/blob/main/docs/command-dimensions.md) and [docs/entity-render.md](https://github.com/andreypfau/mcrs/blob/main/docs/entity-render.md). Those are working notes, not specs.

## How to read a rule

A spec has a rule only for a difference that someone can observe: the vanilla client, a player in normal play, a data pack or a save file, or a user of the library. A rule has a heading with its id, a behavior section, and a provenance line:

```text
Provenance: source_suggested. Kind: semantic. Confidence: medium. Experiment: ...
```

Provenance says where the rule comes from. Section 0.3 of `docs/spec/registry.md` defines the labels.

| Label | Meaning |
|---|---|
| `black_box_confirmed` | Shown by an artifact that the game produced, cited by path. |
| `source_suggested_black_box_confirmed` | Taken from the reference behavior and consistent with a cited artifact. |
| `source_suggested` | Taken from the reference behavior with no artifact yet. Confidence is at most medium and an experiment is attached. |
| `documentation` | Public, player-facing documented behavior. |
| `design` | An mcrs choice. The rule states why. |
| `unresolved` | Not decided. Collected in the section "Unresolved" of the file. |

Kind says how exact the rule must be.

| Kind | What the rule fixes |
|---|---|
| `wire` | The bytes and ids that the vanilla client decodes. |
| `client agreement` | The server must agree with the client. |
| `semantic` | The meaning and the result, but not the internal order. |
| `layout` | GUI positions and sizes. |
| `deviation` | mcrs differs on purpose from a defect or an accident of the reference, and the rule states the expected behavior. |
| `quirk` | mcrs keeps an accident of the reference, because the vanilla client, a data pack or a save file depends on it. Only the owner decides that a rule is a quirk. |
| `unspecified` | An implementation selects the behavior, and a parity test must not compare it. The rule states a bound, such as "at least once in 40 ticks". |

A file also has an "Intentional deviations" section, which records where mcrs differs from vanilla on purpose. Each entry gives the rule id, the reference behavior, the reason, whether the client sees the difference, the bug report of the game if there is one, and what a test does about it. A "Known vanilla quirks" section lists each quirk with the observer that depends on it and the issue where the owner decided to keep it.

A `source_suggested` rule is a claim that has no game artifact behind it yet. A spec is ready when its "Unresolved" section is empty and no rule carries `source_suggested`, and an implementer does not start on a spec that is not ready.
