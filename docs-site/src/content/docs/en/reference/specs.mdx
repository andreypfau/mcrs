<Aside type="note" title="Written for AI agents and spec authors">
The files in `docs/spec/` are written for AI agents and for the people who write specifications. They follow the rules of ASD-STE100 Simplified Technical English, as `docs/spec/README.md` says. They are exact and dry on purpose. This page is the map. Use it to find the file, then read the file.
</Aside>

Each file in [docs/spec](https://github.com/andreypfau/mcrs/tree/main/docs/spec) states the behavior of one domain: inputs, outputs, order, timing and constants as data. A spec never describes the shape of game code. Specs are the only source of game behavior that an implementer may read for a rule ([Clean-room](https://github.com/andreypfau/mcrs/blob/main/docs/clean-room.md)). Some spec headers still name `26.4-snapshot-4` as the game version. The project follows <code dir="auto">{fact('snapshot')}</code> (`assets/minecraft/version.json`).

## How to read a rule

A rule has a heading with its id, a behavior section, and a provenance line:

```text
Provenance: source_suggested. Kind: semantic. Confidence: medium. Experiment: ...
```

Provenance says where the rule comes from (`docs/spec/registry.md`, section 0.3).

| Label | Meaning |
|---|---|
| `black_box_confirmed` | Shown by an artifact that the game produced, cited by path. |
| `source_suggested_black_box_confirmed` | Taken from the reference behavior and consistent with a cited artifact. |
| `source_suggested` | Taken from the reference behavior with no artifact yet. Confidence is at most medium and an experiment is attached. |
| `documentation` | Public, player-facing documented behavior. |
| `design` | An mcrs choice. The rule states why. |
| `unresolved` | Not decided. Collected in a section at the end of the file. |

Kind says how exact the rule must be: `wire` (bytes and ids the vanilla client decodes), `client agreement` (the server must agree with the client), `semantic` (meaning and result, not internal order), `layout` (GUI positions and sizes), `deviation` (a defect of the reference, where the rule states the correct behavior), `unspecified` (a parity test must not compare it).

The "Intentional deviations" section of a file records where mcrs differs from vanilla on purpose, with the rule id, the reference behavior, whether the client sees it, and what a test does about it.

`registry.md` says that none of its experiments has been run. Treat a `source_suggested` rule as a claim with no game artifact behind it yet.
