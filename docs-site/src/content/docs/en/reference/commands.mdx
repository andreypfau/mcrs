This page lists the commands that the server registers today, their permission levels and their specifications. With the default `locate` feature enabled, the server registers {fact('root_commands')} root commands, or 21 names including the alias `tp`. `VanillaCommandsPlugin` in `crates/mcrs_minecraft_command_vanilla` registers most of them, and `WorldCommandsPlugin` in `crates/mcrs_minecraft_command_world` registers the rest. The list was checked against both registration files and each command's permission calls on commit `9eac02a81`. Commands absent from the list, such as `setblock`, `give`, `say` and `stop`, are not registered.

<Aside type="caution" title="WIP">
This table is maintained by hand. The Java client already receives a command tree filtered by its permission level, and a change of operator level sends a new tree.[^285] A Bedrock command dialect is planned.[^667]
</Aside>

The [`/swing` specification](https://github.com/andreypfau/mcrs/blob/main/docs/spec/command-swing.md) exists, but neither plugin registers that command. The specification index includes behavior that has not been implemented.

## Permission levels

Every command needs a permission level. There are five levels and they are ordered, the same as in vanilla. Rule PERM-LEVEL-001 of the [command-permissions spec](https://github.com/andreypfau/mcrs/blob/main/docs/spec/command-permissions.md) defines them.

| Id | Name |
|---|---|
| 0 | `all` |
| 1 | `moderators` |
| 2 | `gamemasters` |
| 3 | `admins` |
| 4 | `owners` |

A player who is not an operator has level `all`. An operator has the level that `ops.json` gives, from 0 to 4, and the `op` command gives the default level, which is `owners`. In the server binary only `ops.json` and the `op` command make operators, as [Who becomes an operator](/docs/en/server/connections/#who-becomes-an-operator) explains. Every command in the next table needs level 2 or 3, so only operators can run them.

Three more groups of specs cover what all commands share. Parsing is in [command-parser.md](https://github.com/andreypfau/mcrs/blob/main/docs/spec/command-parser.md), argument types are in the `argument-*.md` files, and the command tree that the server sends to the client is in [commands-packet.md](https://github.com/andreypfau/mcrs/blob/main/docs/spec/commands-packet.md). The note [docs/command-dimensions.md](https://github.com/andreypfau/mcrs/blob/main/docs/command-dimensions.md) explains how a command finds players in every dimension.

## Typing commands

A player types commands in chat. The server also reads its standard input, and each line runs in the overworld as a command whose source is the server itself. When many lines arrive at once, the server spreads them over several app updates and sends at most 2000 lines per update. The answers go to the server log. The code is `ConsolePlugin` in `crates/mcrs_minecraft_console`.

## For plugin authors

A command is ordinary Bevy plugin code. A plugin calls `add_command` with a build function and a run function, and both `plugin.rs` files show the pattern. A command can write effects that other systems apply, and commands also raise a `CommandEvent` that can be cancelled. A plugin must be compiled into the server, because there is no loader for other plugins and no decision about one yet. [Commands for plugins](/docs/en/plugins/commands/) has the details.
