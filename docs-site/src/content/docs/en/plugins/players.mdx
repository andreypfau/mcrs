This page shows how a plugin finds players, reads their data, tells their ids apart and changes them. In Paper a `Player` is an object with methods. In mcrs a player is an entity inside the world of a dimension, and its state is a set of components, so you write a query where Paper code would hold on to the object.

The examples come from repository files; this docs update did not run them.

## Find players with a query

Every player entity has the marker component `Player`. A system in a dimension world sees the players of that dimension only, as [Dimensions](/docs/en/plugins/dimensions/) explains. The test harness finds a player with this kind of query:

<Example file="crates/mcrs_minecraft_server/tests/it/host_app/mod.rs" from="pub fn player_in(" title="Find a player entity by its session" />

In a plugin you write the query as a system parameter, for example `Query<(&GameProfile, &PlayerGameMode), With<Player>>`. That line is an illustration and was not compiled. Its type names come from the files in the next section.

## One player has three ids

You cannot use one of these ids in place of another.

| Id | Where | What it is |
|---|---|---|
| `GameProfile::id` | component of the player | the UUID of the profile, as in Paper |
| `PlayerSession` | component `Owner` of the player in a dimension world; also on the host | the name of one connection. The host never hands out a value twice, and a change of dimension keeps it |
| `Entity` | the entity of the player inside one dimension world | a Bevy id that exists in one world only. The host also has an anchor entity for the same player, and it is a different entity |

<Example file="crates/mcrs_minecraft_engine_world/src/session/sessions.rs" from={"#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]\npub struct PlayerSession"} title="PlayerSession" />

Use the session to address a player across worlds and to send packets. Use the UUID for anything that must survive a reconnect.

The client sees one more number, the entity id in packets, and it does not depend on the world. A player gets an odd id made from its `PlayerSession`, so the id stays the same through a change of dimension. Other entities get even ids from ranges that the host hands to each dimension world, and an entity taken into another dimension keeps its id. While the server runs, no two entities share an id.[^158]

## Change a player inside its own world

Inside the world of a player you can insert or edit its components. Do not change a player from a system that runs in a different world. A change that crosses worlds is a message or an effect. The vanilla commands `gamemode` and `teleport` do this with command effects, see [Add a command](/docs/en/plugins/commands/).

## Change an attribute

Max health, movement speed and the two interaction ranges that set the reach are attributes of a player. With `VanillaEntityAttributesPlugin` in the server, every player entity has the component `AttributeInstances` from the crate `mcrs_minecraft_entity_attribute`, and it starts with the bases of the player type, because `PlayerAttributesPlugin` registers it as a required component of `Player`. A system in the world of the player changes an attribute with `apply`. It takes an `Attribute`, such as `Attribute::MaxHealth`, and an `InstanceEdit`: `SetBase` sets the base value, `Put` adds or replaces a modifier, and `Remove` takes a modifier away by its id. The sprint plugin puts its modifier on movement speed while a player sprints and removes it when the player stops:

<Example file="crates/mcrs_minecraft_vanilla_attributes/src/sprint_attribute_plugin.rs" from="fn give_sprint_modifier(" to={"    }\n}"} title="The sprint modifier on movement speed" />

`apply` returns an `InstanceChange`, and the system marks the component changed only when a value changed, so systems that wait for a change of `AttributeInstances` skip a player whose values stayed the same. Your plugin edits the component the same way. A repository test sets the base of `Attribute::MaxHealth` to 30 and reads it back after the player joins again.

The server sends each changed attribute to the client of the player and to the other players whose clients show this player. Only attributes that their definition marks as synced go out. The player file keeps the bases and the modifiers of kind `ModifierKind::Permanent`. A transient modifier, such as the sprint modifier, is not saved, but it stays with the player through a change of dimension.

The sprint modifier and the extra reach in creative mode (0.5 for blocks, 2.0 for entities) come from `VanillaSprintAttributePlugin` and `VanillaCreativeRangePlugin`. Each is a member of the server plugin group, so you can disable one and keep the other, as [Remove and replace vanilla parts](/docs/en/plugins/customize-server/) shows.

## Send an arm swing

Write `SwingPlayer::new(player, hand, animation, duration)` from `mcrs_minecraft_engine::swing` in the player's world, or use `SwingPlayer::default_main(player)` for a six-tick main-hand whack. The engine rejects spectators and dead players and applies a shared cooldown across both hands. Only current tracking observers receive the animation; this message does not deal damage. `VanillaSwingPlugin` supplies punch and piercing-weapon stab inputs, and placement and inventory plugins supply their own triggers.[^pr1064]

This is server packet delivery. The mcrs client does not consume the swing packet or render its animation yet.

## Health, damage and death

`PlayerVitalsPlugin`, installed by `VanillaEntityAttributesPlugin`, gives players the same `Vitals`, `HitRecord` and `Defence` components as mobs. `Vitals` owns current health, absorption and the hurt, cooldown and death counters; maximum health comes from attributes. The persisted registry saves the health state. Food remains in `PlayerFileState` until hunger has its own owner. Creative and spectator players reject hits unless the damage type bypasses invulnerability.[^pr1082]

The built-in player path currently fills only game-mode invulnerability in `Defence`. It does not populate player armour, toughness or resistance from attributes, equipment or effects.

To deal damage, append `DamageRequest::new(target, hit, writer, tick, sequence)` to `PendingHits` in the player's dimension. `/damage` and `/kill` use this path too. `DamageSet` runs `Collect`, `Filter`, `Apply` and `Report` after motion in `FixedUpdate`. A system in `Filter` can edit requests with `requests_mut()` or remove them with `retain()`. The engine sorts and applies the batch in `Apply`; read `Damaged` and `Died` in `Report` for the result.[^pr1078]

The player's client receives health and food updates. Viewers receive health changes and the dying pose; the dying player receives the kill packet. At login, the death-screen flag follows `immediate_respawn`; later rule changes are not sent yet. At death time 20, `HiddenPlayer` removes it from other clients, while its Bevy entity, connection and own view remain. [Inventory](/docs/en/plugins/inventory/#inventory-on-death) describes drops.

`DeathMessage { player, text }` supplies the death-screen text. `VanillaDeathMessagesPlugin` writes it in `PlayerDeathSet::Describe` and broadcasts it in `Announce`, after the engine sends the kill packet in `Notify`. Vanilla text follows `show_death_messages`; turning it off also leaves the kill packet's text empty. To supply your own text, disable that plugin and write `DeathMessage` in `Describe`. Without a writer, the death-screen text is empty.[^pr1084]

## Respawn through a request

The engine restores a dead player only after a `RespawnRequest`:

<Example file="crates/mcrs_minecraft_engine_damage/src/respawn_request.rs" from="pub struct RespawnRequest {" title="Choose the player, target dimension and transform" />

`dimension` is the host's entity id for the target dimension. `VanillaRespawnPlugin` turns the client's respawn command into this request at the adjusted world spawn. Disable that plugin and write requests in the player's world to choose another policy. The engine restores vitals and food, sends the respawn and position packets, and shows the player to viewers again. A request for another dimension starts a dimension change.

The vanilla policy currently treats bed and anchor spawn points as missing. Its surface search ignores the world border and caps the radius at 15. Respawn does not yet reset every effect, pose, motion, item cooldown or attribute modifier, or resend all inventory and experience state. Hunger simulation, melee attacks and environmental hit sources are separate work; the command damage path does not imply that they run.[^pr1082]

## Send a message to a player

mcrs has no `player.sendMessage()`. The low-level way is to write a packet for a session. The chat plugin does this for a player who has chat hidden:

<Example file="crates/mcrs_minecraft_chat_server/src/chat_plugin.rs" from="info.is_some_and(|info| info.chat_mode == ChatMode::Hidden)" title="Write a system chat packet to the session of a player" />

A friendlier layer for this does not exist yet. We know of no issue for it, so we promise nothing.

The server saves player data to the player files of the world folder, as [Worlds and saves](/docs/en/server/worlds/) describes. A component of your plugin goes into the player file only when the plugin registers it with `PersistScope::Persisted`, as the page on [persisted components](/docs/en/plugins/persisted-components/) explains.[^159]
