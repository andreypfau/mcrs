In Paper, a `Player` is an object with methods. In mcrs, a player is an entity inside the world of a dimension, and its state is a set of components. There is no `Player` object to hold on to. You write a query. This page is short on purpose: the set of components grows with the project. Examples come from repository files, and we did not run them outside the repository tests.

## Query players

A player entity has the marker component `Player`. A system in a dimension world sees the players of that dimension only (see [Dimensions](/docs/en/plugins/dimensions/)). The test harness finds a player with the same kind of query:

<Example file="crates/mcrs_minecraft_server/tests/it/host_app/mod.rs" from="pub fn player_in(" title="Find a player entity by its session" />

In a plugin, you write the query as a system parameter: `Query<(&GameProfile, &PlayerGameMode), With<Player>>`. The type names come from the files below. The line is illustrative and was not compiled.

## Three different ids

One player has three names, and they are not interchangeable.

| Id | Where | What it is |
|---|---|---|
| `GameProfile::id` | component of the player | the UUID of the profile, as in Paper |
| `PlayerSession` | component `Owner` of the player in a dimension world; also on the host | the name of one connection. The host never hands out a value twice, and a change of dimension keeps it |
| `Entity` | the entity of the player inside one dimension world | a Bevy id that exists in one world only. The host also has an anchor entity for the same player, and it is a different entity |

<Example file="crates/mcrs_minecraft_engine_world/src/session/sessions.rs" from={"#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]\npub struct PlayerSession"} title="PlayerSession" />

Use the session to address a player across worlds and to send packets. Use the UUID for anything that must survive a reconnect.

<Aside type="caution" title="WIP: the id on the wire">
The entity id that the client receives is today the index of the Bevy `Entity` in the world of the dimension. That has two faults, per <Status issue={158} state="wip" />. Bevy can hand a freed index to a new entity while a client still tracks the old one, and vanilla never reuses an id while the server runs. And two dimension worlds allocate indices on their own, so their ids collide as soon as one connection sees entities of more than one owner. The issue plans a `NetId` component for every networked entity, with ids leased to each world, never reused, and kept when an entity is handed to another node. Until that issue is done, do not store the wire id of an entity and do not assume it stays the same.
</Aside>

## Change a player

Do not change another player from a system that runs in a different world. Inside the world of the player you can insert or edit its components. Across worlds, a change is a message or an effect. The vanilla commands `gamemode` and `teleport` do this with command effects, see [Add a command](/docs/en/plugins/commands/).

## Send a message to a player

There is no `player.sendMessage()`. The low-level way is to write a packet for a session. The chat plugin does this for a player who has chat hidden:

<Example file="crates/mcrs_minecraft_chat_server/src/chat_plugin.rs" from="info.is_some_and(|info| info.chat_mode == ChatMode::Hidden)" title="Write a system chat packet to the session of a player" />

A friendlier layer for this does not exist yet. We know of no issue for it, so we promise nothing.
