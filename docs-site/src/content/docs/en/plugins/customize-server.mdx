This page shows how to build your own server from the same plugins as the stock one, how to leave a plugin out, and how to pass settings to the plugins.

In Paper you start from a finished server and add plugins. In mcrs you start from a group of plugins and take parts out, so a lobby can run without world generation and a test can run without lighting. The examples come from repository files, and we did not run them outside the repository tests.

## The server is a group of plugins

`MinecraftServerPlugins` is a Bevy `PluginGroup`, which is a set of plugins that you add to the app as one value. Its four fields are the parts that take settings:

<Example file="crates/mcrs_minecraft_server/src/lib.rs" from="pub struct MinecraftServerPlugins {" title="The fields of the group" />

`build()` adds the rest of the vanilla server. The members, in the order `build()` adds them, are the server core, world generation registries, the command engine, vanilla commands, world commands, dimension worlds, chat, entity physics, player pose, entity attributes and player vitals, respawn, death drops, death messages, the sprint attribute, creative reach, item entities, falling blocks, block drops and support, mob brains, item and inventory saving, block placement, arm swings, world generation, lighting and the network.[^279]

<Example file="crates/mcrs_minecraft_server/src/lib.rs" from="impl PluginGroup for MinecraftServerPlugins" title="The members of the group" />

You can disable or replace each member without editing the server crate. A member that needs another one panics when the group builds and names the missing plugin. You get the error at start, so you do not have to trace a missing resource at the first tick.

The vanilla gameplay lives in plugins above the engine. Each of them is removable on its own, and most of them reach every dimension world through `add_dimension_plugin`.[^282]

## Disable a member with disable

The binary switches mob AI off like this:

<Example file="src/main.rs" from="if !settings.mob_ai {" title="src/main.rs: switch off mob AI" />

`disable::<T>()` is a method of the Bevy plugin group builder, and `T` is the plugin you leave out. A repository test uses the same method to start a server without world generation and lighting:

<Example file="crates/mcrs_minecraft_server/tests/it/client_join.rs" from="fn a_client_without_an_app_joins_the_embedded_server_offline" to="StopOnDrop(Arc::new(AtomicBool::new(false)))" title="Test: a server without world generation and lighting" />

That test also calls `MinecraftServerPlugins::embedded()`. It gives a server that runs inside another process. Such a server listens on loopback only, takes a port that the OS assigns, and leaves the task pools to the host app.

<Example file="crates/mcrs_minecraft_server/src/lib.rs" from="impl MinecraftServerPlugins {" title="embedded()" />

To host such a server in your own program, pass a closure that builds the app to `ServerThread::start` from `mcrs_minecraft_engine_server`, and the server runs on a thread of its own. `address()` returns the address once the server listens, `request_shutdown()` asks the server to disconnect the players, save the world and exit, and `finish()` asks the same and waits for the thread to end. The client starts its singleplayer server this way, and the field `extend_server` of its `LocalServerPlugin` takes a function that adds your own plugins to that server.

## Replace death, respawn or swing rules

The group exposes these members separately:

| Member | What disabling it removes | Replacement |
|---|---|---|
| `VanillaRespawnPlugin` | the client's respawn command becoming a world-spawn request | write `RespawnRequest` in the player's dimension |
| `VanillaDeathDropsPlugin` | vanilla inventory, cursor and crafting-grid drops on death | read `Died` and choose your own drop policy |
| `VanillaDeathMessagesPlugin` | vanilla death text and its chat broadcast | write `DeathMessage` in `PlayerDeathSet::Describe`; broadcast your text separately if needed |
| `VanillaSwingPlugin` | punch and piercing-weapon stab inputs | write `SwingPlayer`; accepted placements and hand drops have their own producers |

Player vitals remain in `VanillaEntityAttributesPlugin`, which installs `PlayerVitalsPlugin` alongside the attribute plugins. Replacing the respawn policy keeps health, death packets and the engine's restore mechanism.[^pr1082] Death drops and messages are independent members.[^pr1084] Swing requests use the engine cooldown and observer replication even when your own system writes them.[^pr1064]

[Read player data](/docs/en/plugins/players/#health-damage-and-death) explains the damage filter and respawn limits. [Inventory](/docs/en/plugins/inventory/#inventory-on-death) lists what the drop policy does.

## Settings are plugin fields

The binary reads its settings from the environment and turns them into plugin fields in `src/main.rs`:

<Example file="src/main.rs" from="let settings = ServerSettings::read(" to=".build();" title="src/main.rs: from settings to plugin fields" />

Only the binary does this. A library crate does not read an environment variable or a file for its settings, and every setting is a field of the plugin that uses it.[^278]

The environment variables of the binary are the fields of `ServerSettings`. Most variables carry the name of their field in upper case with the prefix `MCRS_`, such as `MCRS_MOB_AI` for `mob_ai`. [Environment variables](/docs/en/reference/env-vars/) has the list with the defaults.

In your own program, skip `ServerSettings` and fill the plugin fields yourself. An embedded server in a test then starts with explicit settings, whatever the shell exported.

## You cannot supply your own chunks yet

<Aside type="caution" title="WIP">
A chunk source of your own does not exist yet. It is planned as a replaceable plugin point, and the plan sets a direction without a promise.[^281]

Today the chunks of a dimension come from a fixed setup inside the server, which is the noise generator of the dimension plus the saved columns of the world folder. A lobby, an arena or a test cannot hand the server its own chunks.

The plan proposes a chunk source per dimension. Given a column position, the source yields a column or says there is none, and it does so off the tick, on the task pool. The server would ship three sources: the generator with the save in front, an empty source, and a flat source built from a list of layers. A source of your own would be a type that implements the same trait. A dimension on the empty source would not pull in the world generation crates.

The plan also names a test. One dimension runs on the empty source and another on the flat source, a client joins each, and the dependency tree has no world generation crates.

Saving chunks to disk is a separate topic.
</Aside>
