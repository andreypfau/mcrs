A component that your plugin puts on a player lives on the player entity in one dimension world. When the player leaves, changes dimension or crosses to another cell, the server despawns that entity, and the component is lost unless you register it. This page shows how to register the component, how to choose whether it reaches the player file, and how to test it. In Paper, `PersistentDataContainer` does this job.

A cell owns a box of a world, and a player who walks out of the box moves to the cell that owns the new place, as [Cells and the road to many nodes](/docs/en/concepts/scaling/) explains. The examples come from repository files, and we did not run them outside the repository tests.

## Register the component and add the plugin to every world

The server moves a player between worlds as a snapshot. When the player leaves a world for another dimension or another cell, the old world captures the registered components of the player and despawns the entity, and the new world applies the snapshot to a new entity. The same registry decides what goes into the player file.[^159]

Register the component in the `build` of your plugin with `register_persisted`, and add the plugin with `add_persistence_plugin`. Both come from the trait `PersistedAppExt` of `mcrs_minecraft_engine`:[^pr744]

<Example file="crates/mcrs_minecraft_engine/src/persisted_registry.rs" from="pub trait PersistedAppExt" title="PersistedAppExt" />

`register_persisted::<T>(keys, scope)` needs a component with `Serialize` and `Deserialize`, because the snapshot keeps it as NBT under the keys you give. The keys are a static list of top-level keys, the same in the snapshot and in the player file. With one key, the whole value sits under that key. With several keys, the component must serialize to a compound, and each field goes under the key of the same name.

`add_persistence_plugin(plugin)` adds the plugin to the main app and builds a clone of it in every dimension world, so the plugin must be `Clone`. The dimension worlds need the registration to capture and apply the component. The main app needs it because it reads the player file when a player joins, and a key of the file that no registered component claims makes the whole file unreadable. The player then joins empty, and the server never writes over that file.

A second registration over the same keys in the same order replaces the first. A registration that shares only some of its keys with an earlier one is refused, and the server logs an error. If the player has no such component when the server captures the snapshot, nothing is stored for it. Applying a snapshot inserts the component and replaces the one the player had.

## Choose whether the component reaches the player file

The second argument is a `PersistScope`. With `PersistScope::Persisted`, the server writes the component to the player file at the moments that [Worlds and saves](/docs/en/server/worlds/) lists, and it also carries the component to another dimension or cell. With `PersistScope::TravelOnly`, the component only moves with the player and never reaches the file. It lasts as long as the session, so after the player leaves, the next join starts without it.

Use `TravelOnly` for state that belongs to the connection and not to the save. The engine registers its own session state this way, such as the client settings and the view distance. The component `ShiftKey` says whether the player is holding the shift key, and the engine carries it under the key `mcrs:shift_key`:[^pr970]

<Example file="crates/mcrs_minecraft_engine/src/persistence.rs" from=".register_persisted::<ShiftKey>(SHIFT_KEY_KEYS, PersistScope::TravelOnly);" title="The shift key travels and never reaches the file" />

The server uses this registry to save and carry player components only.

Player health uses this registry too. The engine's codec saves `Vitals` under the existing `Health`, `AbsorptionAmount`, `HurtTime` and `DeathTime` keys; those values no longer live in `PlayerFileState`. Loading clamps health to the range from zero to the current maximum and replaces a non-finite value with that maximum.[^pr1082]

## Save another shape, or write the codec yourself

`register_persisted` stores the component in the form that serde gives it. When the file needs another form, register a saved form with `register_persisted_as::<T, F>(keys, scope)`. The form `F` has `Serialize` and `Deserialize` and implements `PersistedForm<T>`, which converts it both ways. The engine saves the game mode of a player this way, as the integer `playerGameType` of the player file:

<Example file="crates/mcrs_minecraft_engine/src/persistence.rs" from="impl PersistedForm<PlayerGameMode> for GameType" title="The game mode is saved as an integer" />

`from_value` builds the form from the component when the server captures the snapshot. `into_value` turns the saved form back into the component. An `Err` from it fails the load of the player in the same way as a file that the server cannot parse.

For full control, register two functions with `register_persisted_codec(keys, scope, capture, apply)`. The capture function gets the world, the player entity and a `CaptureCause`, and it returns the NBT tag to store, or `None` to store nothing. The apply function gets the tag back and writes it into the world. Both are plain function pointers, so a closure works only if it captures nothing.[^pr767]

The cause says why the server takes the snapshot: `Autosave`, `Leave`, `DimensionChange` or `CellCrossing`. The enum is `#[non_exhaustive]`, so a `match` on it needs a wildcard arm. The vanilla inventory reads the cause. On a leave or a dimension change it closes the inventory menu of the player before it saves the items, and its travel-only codec carries the item on the cursor and the crafting grid only across a cell crossing.

A repository test registers a codec that records every cause it gets:

<Example file="crates/mcrs_minecraft_server/tests/it/persistence.rs" from="impl Plugin for CauseRecorderPlugin" to={"    Ok(None)\n}"} title="Test: a codec that records its causes" />

The test moves a player from the overworld to the End and then lets the player leave. The overworld records `DimensionChange`, and the End records `Leave`.

## Test that the component comes back

A test can drive the registry directly. It applies a `PersistedSnapshot` that holds your key, which is what the server does with a player file it has read. Then it moves the player and captures the snapshot again in the new world. The repository test of the player inventory works this way. It adds `ItemPersistencePlugin` of `mcrs_minecraft_engine_item` and `InventoryPersistencePlugin` of `mcrs_minecraft_vanilla_inventory`, which registers the inventory, the ender chest, the selected hotbar slot and the worn equipment:[^pr744]

<Example file="crates/mcrs_minecraft_server/tests/it/persistence.rs" from={"#[test]\nfn an_inventory_crosses_a_dimension_change"} title="Test: an inventory crosses a dimension change" />

After the move, the part of the snapshot that goes to the file in the End holds the same items. For your own component, add your plugin with `add_persistence_plugin`, put your key into the snapshot and compare what comes back. Use `capture_file` for a `Persisted` component and `capture` for a `TravelOnly` one, because only `capture` includes the travel-only keys. The harness `PlayServer` lives in the integration tests of the server crate, as [Test a plugin without a client](/docs/en/plugins/testing/) explains.
