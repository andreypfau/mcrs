This tutorial shows how a plugin locks a slot of the player inventory, denies an inventory request of a player and opens a menu of its own. Most of the code comes from the example crate `examples/inventory_minigame`, and we did not run it outside the tests of the repository. The example runs in one world, while a server keeps the inventory in each dimension world, so read the section about the example before you register a plugin.

## Every inventory packet becomes one InventoryInput

The packet edge of the inventory, `InventoryServerPlugin`, has one observer for each of the five inventory packets of a client: a click, a close, a hand action, a creative set and a change of the hotbar slot. Each observer writes one `InventoryInput` message.[^pr767]

<Example file="crates/mcrs_minecraft_inventory_server/src/inventory_input.rs" from="pub enum InventoryInput" title="InventoryInput" />

The system `apply_inventory_input` of the same crate applies these messages in the client input phase of the tick, in the set `InventorySet::Input` of `VanillaInventoryPlugin`. A click becomes a `Request`, a list of slot operations with an id, which carries the request source of the vanilla plugin. A hand action goes to a command of the vanilla plugin and becomes a request there. A pick-up click on a button entry of a menu moves no stack and writes `EntryPressed` instead.[^pr977]

A request meets two checks, and each is a place where your plugin can say no. First the engine raises `RequestCheck` on the player, and an observer can deny the request. Then it plans the operations against the `SlotPolicy` of each holder, the entity that owns the slots, and one refused take or place rejects the whole request. Either way no slot changes. At the end the engine writes and triggers `RequestResult`, whose `outcome` is `Ok(())`, `Refusal::Denied` or `Refusal::Rejected`.

The close request, which moves the stacks of the cursor and the crafting grid back when a menu closes, skips `RequestCheck`, and take gates do not apply to it.

## Lock a slot with the slot policy

A `SlotPolicy` component on a holder gives each slot a `SlotAccess`: the largest count the slot holds (`limit`), a gate for a take and a gate for a place. A `Gate` permits, refuses or asks a function. `PlayerHoldersPlugin`, which `VanillaInventoryPlugin` adds, gives each new `Player` its holders with their policies. The armour slots ask the armour gates, and the crafting result refuses a place.[^pr846]

The arena plugin of the example locks slot 8, the last slot of the hotbar, while the player is in its game. Both gates of the locked access refuse.

<Example file="examples/inventory_minigame/src/arena_rules_plugin.rs" from="const LOCKED_SLOT: u16 = 8;" to="};" title="The locked access of slot 8" />

<Example file="examples/inventory_minigame/src/arena_rules_plugin.rs" from="fn lock_slot(" title="Lock the slot at EnterGame" />

`lock_slot` observes `EnterGame`, an event of the example. It keeps the old access in `UnlockedAccess`, and `unlock_slot` puts it back at `LeaveGame`.

To decide for each stack, register a function with `register_slot_gate` of `ItemAppExt` and put the returned id into `Gate::Ask(id)`. The function is `fn(&World, &GateQuery) -> Filter`, with `Filter` from `mcrs_minecraft_inventory_transaction`. It reads the world without changing it, and `GateQuery` names the slot, the acting player and the stack. A take gate is asked only when the slot holds a stack, and an unknown id refuses. The armour take gate in `armour_take.rs` works this way: it refuses a stack with an enchantment that locks armour, unless the player is in creative mode.[^pr988]

The policy guards requests only. `give` and `give_or_drop` of `HolderCommandsExt` make no request, so they ignore the policy and can put a stack into a locked slot.

## Deny a request with RequestCheck

In Paper you cancel an `InventoryClickEvent`. Here you write an observer of `RequestCheck`, an entity event that the engine raises on the player before it plans a request. `check.request()` returns the request with its id, its kind and its operations, and `check.deny(denial)` denies it. The first denial counts, and a later `deny` changes nothing.[^pr846]

<Example file="examples/inventory_minigame/src/arena_rules_plugin.rs" from="fn veto_frozen(" to={"    }\n}"} title="Deny each request of a frozen player" />

A `Denial` has a `code` that your plugin chooses and the `source` of your plugin. A request source is an opaque value that the world hands out to each plugin that asks, and `app.allocate_request_source()` of `ItemAppExt` is the only way to get one. It fails with `RegisterError::SourcesExhausted` when no source is left. Your plugin puts its source into each `Denial` and into the `RequestId { source, serial }` of each request it makes, so a reader of `RequestResult` can tell its results from the others. The vanilla plugin keeps its own source in `VanillaInventoryRequests` and launches the drops of a request only when the request carries that source.[^pr988]

<Example file="examples/inventory_minigame/src/arena_rules_plugin.rs" from="impl Plugin for ArenaRulesPlugin" title="Allocate the source in build, then add the observers" />

The plugin allocates its source in `build`, keeps it in the resource `ArenaRules` and adds nothing when no source is left. Its observer of `RequestResult` counts the denials with its own source in `Frozen::denied`.

## Open a menu of your own

A menu is data. `MenuLayout` in `mcrs_minecraft_inventory_menu`, a crate without Bevy, lists the entries of a menu, and each entry points to a slot of one part. `MenuType` comes from `mcrs_minecraft_menu_key::menu_keys`. `MenuLayout::of(MenuType::Generic9x3)` returns `Some(layout)` for a chest with three rows: 27 entries of part 0 (`GENERIC_CONTAINER`), then the 36 player slots as part 1 (`GENERIC_PLAYER`). `MenuLayout::new(kind, entries, routes)` builds any other layout, where a route says where a shift-click moves a stack. It returns `None` above 128 entries or for a route outside the menu.[^pr977]

`MenuCommandsExt` opens a menu on the player with `open_menu` or `open_titled_menu`. Both take the layout, the holders of the parts in `MenuParts` and the button entries in `MenuButtons`. The shop of the example opens over a new holder with 27 slots and one offer.

<Example file="examples/inventory_minigame/src/shop_plugin.rs" from="fn open_shop(" title="Open the shop with a title and one button entry" />

The holder of the shop has `SlotPolicy::locked()`. A click on a button entry moves no stack, and a pick-up click writes the message `EntryPressed { viewer, menu, entry, button }`. Other clicks can still reach the shop slots, such as a shift-click from the player slots, and the locked policy refuses them. The shop system `give_offers` reads `EntryPressed` and gives the player the stack of the pressed offer. On a server, the packet edge sends the menu with its type and title to the client.

`close_menu` closes the open menu, and opening a menu first closes any menu above the inventory. Each open and close triggers `MenuOpened` or `MenuClosed` on the player and writes it as a message. A menu whose holder loses its `Slots` closes by itself, and the shop despawns its holder when its menu goes away.

## The example runs in one world, a server in many

`examples/inventory_minigame` is one headless app. Its `main.rs` adds `ItemPlugin`, `VanillaInventoryPlugin`, `KitPlugin`, `ArenaRulesPlugin` and `ShopPlugin` to one `App` with `add_plugins`. The crate links no packet edge, so there is no client and no packet. The integration test stands in for them. It spawns a `Player`, triggers `EnterGame` and `OpenShop`, sends requests with `HolderCommandsExt::request` and writes `EntryPressed` by hand.

A take from the locked slot fails with `Reason::TakeDenied`, and a take from slot 10 commits. A frozen player gets `Refusal::Denied` with the source of the arena plugin, which differs from the vanilla source. Pressing the offer gives the stack, and the shop holder goes away with the shop menu. The [README of the example](https://github.com/andreypfau/mcrs/blob/main/examples/inventory_minigame/README.md) lists the commands that run the app and the test.

A server has no such single world. Its plugin `VanillaItemEntityPlugin` adds a dimension builder that puts the item engine, `VanillaInventoryPlugin` and the packet edge into every dimension world.

<Example file="crates/mcrs_minecraft_server/src/item_entities.rs" from="fn build_dimension_items(" to="    ));" title="The inventory plugins go into each dimension world" />

So the players, their slot policies, `RequestCheck` and `EntryPressed` live in the dimension world of each player. Register your plugin with `app.add_dimension_plugin(ArenaRulesPlugin)`. Every dimension world builds a clone of it after the dimension builders, so its `build` allocates a source and adds the observers in that world. The plugin must be `Clone`, as both plugins of the example are. With `add_plugins` it lands in the main app, where its observers never see a player. Trigger your own events, such as `EnterGame`, in the world of the player too. [Dimensions are separate worlds](/docs/en/plugins/dimensions/) explains `add_dimension_plugin`. No test of the repository runs these plugins in a server yet.

## Inventory on death

`VanillaDeathDropsPlugin` reads `Died` and drops the main inventory, then the off hand and armour from feet to head. Stacks with a vanishing enchantment effect are deleted. `keep_inventory` or spectator mode preserves these slots. The plugin reads the dimension's current game rules; disable it to replace this policy.[^pr1084]

Cursor and crafting-grid stacks drop later, when the dead player is hidden after the death delay, leaves, or respawns, whichever happens first. This also happens with `keep_inventory` enabled. These drops do not go through an inventory click request, so `RequestCheck` is not their cancellation hook. [Read player data](/docs/en/plugins/players/#health-damage-and-death) covers the death and respawn messages.

## Hand drops and arm swings

A successful vanilla hand-drop request emits `SwingPlayer` for the main hand, with the default whack animation and a base duration of 6 ticks. Tracking observers receive the swing packet; late viewers receive no replay.[^pr1064] The [player guide](/docs/en/plugins/players/#send-an-arm-swing) explains the mcrs client's current limitation. Item stacks also have typed `AttackAnimation`, `InteractAnimation` and `PiercingWeapon` components. Their codecs and predicates work without an engine; the swing cooldown kernel is `mcrs_minecraft_swing`.[^pr1063]

## The client and what is left

The mcrs client takes clicks in its inventory screen.[^129] It draws the eight generic container screens with item tooltips, drag previews and double clicks, so a player sees a menu your plugin opens.[^130] In creative mode the inventory key opens the creative screen with tabs, scrolling, search and stack clicks.[^131] The remaining screen limits are on [The client today](/docs/en/client/overview/#what-is-missing). The player inventory issue still covers agreement with a vanilla client and persistence across a rejoin.[^521]

Next: [Paper to mcrs](/docs/en/plugins/paper-to-mcrs/) has the table of Paper events and what mcrs has for them. [Intercept chat](/docs/en/plugins/chat-event/) shows the other events a plugin can cancel.
