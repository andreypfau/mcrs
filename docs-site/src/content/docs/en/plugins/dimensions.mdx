This page explains where your code has to run to see players and blocks, who is allowed to write state that all dimensions share, and how a player gets from one dimension to another.

In Paper, a `World` is an object that your plugin can reach from anywhere. In mcrs, a dimension is a separate simulation, and code in the main app cannot touch it directly. The examples come from repository files, and we did not run them outside the repository tests.

## One main app, one sub-app per dimension

The server has one main Bevy `App`. Each dimension runs as a `SubApp`, which is a Bevy app nested in the main one, and it has its own `World` with its own entities and resources.[^362] In one shared world, every system would visit the entities of all dimensions and filter them by a dimension component. The dimensions also could not tick in parallel or move to another machine later.

This has consequences for your code. A system of a dimension world sees only the entities of that dimension. Immutable registries are shared with the dimensions as `Arc` values, and mutable state is not shared.

A dimension world also has no `Time` resource and does not run the stock `Main` schedule. It runs `First`, `PreUpdate`, the `Fixed*` schedules, `Update`, `PostUpdate` and `Last` once per host tick. A dimension therefore counts ticks and cannot depend on the wall clock, as the doc comment in `sub_app.rs` says.

## A plugin gets into a dimension through add_dimension_plugin

A plugin added with `add_plugins` goes to the main app only, where it sees no players and no blocks. To put a plugin into the dimensions, use the `AddDimensionPlugins` trait:[^280]

<Example file="crates/mcrs_minecraft_engine_world/src/world/sub_app.rs" from="pub trait AddDimensionPlugins" title="The two methods" />

- `add_dimension_plugin(plugin)` builds a copy of the plugin in every dimension world.
- `add_dimension_plugin_to(key, plugin)` builds it only in the dimension with that key, for example `OVERWORLD`.

The plugin must be `Clone`, because each world builds its own clone. The worlds build the clones in the order the plugins were added. Add your plugin before the dimensions spawn, because a dimension that is already live does not get a later plugin.

One more rule applies to unique plugins, which is the Bevy name for a plugin that an app can hold only once. A unique plugin that you add for one dimension replaces, in that world, the unique plugins with the same name that were added for all dimensions. Any other unique plugin whose name the world already has is skipped, and the server logs an error.

The repository test checks each rule. It adds one counter to every world and another counter only to the overworld. Then it asserts that the nether has no second counter and that the overworld got the value of the plugin added for its key.

## Global state has one writer

Every dimension reads game time, world clocks, weather, game rules, the world border and scoreboards. Each piece of such state has one owner, and only the owner writes it.[^357] In one process the owner is the main app.

A dimension holds a read-only snapshot with a version, and it gets a new snapshot only when the version changes. When a dimension wants a change, for example because of a command or a weather cycle, it sends a message to the owner.

For a plugin this means that you do not keep your own copy of the game clock inside a dimension and advance it, because the copies would drift apart. The same holds for a test setup. When it sets game rules, weather or clocks, it writes through the owner and never into a dimension world.

## A player moves between dimensions as a message

A system of one dimension cannot reach another world, so the server cannot move the entity of a player from one world to the other. A portal, or any other move decided inside a tick, writes a request:[^362]

<Example file="crates/mcrs_minecraft_engine_world/src/entity/player/mod.rs" from={"#[derive(Message, Clone, Debug)]\npub struct ChangeDimensionRequest"} title="ChangeDimensionRequest" />

At the end of the tick, the old world takes the carried state of the player, despawns the player and hands a departure to the host. The player arrives in the new world on the next tick. The rules are in the section "Change of dimension" of [docs/command-dimensions.md](https://github.com/andreypfau/mcrs/blob/main/docs/command-dimensions.md).

<Aside type="caution" title="Your player components stay behind">
The carried state is a plain struct of the components that go with the player. A component that is not in it stays in the old world and is despawned with the old entity, as docs/command-dimensions.md says. If your plugin adds a component to players, check whether it needs to travel. No public way to add your own data to the carried state is documented yet, so for now this is a question for the issue tracker.
</Aside>

The same document describes how commands work across worlds. A command runs in one world. Its effects on other worlds are messages, and the host forwards them between ticks. The page [Add a command](/docs/en/plugins/commands/) shows how a handler writes such an effect.

## You cannot create a dimension at run time yet

<Aside type="caution" title="WIP">
The dimension list is fixed when the server starts. A lobby or a minigame cannot create a world for a match and remove it afterwards.

The plan has three messages:[^546]

- A public message adds a dimension world with a name, a dimension type, a chunk source and its plugins.[^281]
- One message removes a dimension world and moves its players first.
- One message moves a player to a named world and position, and a plugin can cancel it.[^283]

The plan needs players that arrive in the target dimension as full players, user plugins inside every dimension world and the chunk source above.[^142][^280] It sets a direction without a promise.
</Aside>
