This page shows how mcrs lays out a world in memory: blocks in sections and columns, and mobs as ECS entities. The layout is settled for blocks and still moving for entities and for the world-access API. If you know Paper, expect two changes. A "chunk" is two different things here, and a mob is not an object.

## A dimension holds columns, and a column holds sections

| Level | Size | What it is for |
|---|---|---|
| Section | 16 x 16 x 16 blocks | the unit of block storage, light and palette compression |
| Column | 16 x height x 16 blocks | a vertical stack of sections; it owns the heightmaps |
| Dimension | unbounded | the top container; it owns the column index and the section index |

mcrs says "section" and "column" and avoids a bare "chunk", because "chunk" does not say which of the two it means. The [glossary](/docs/en/reference/glossary/) defines both terms.

In the engine, each of the three levels is an ECS entity with a marker component that tags what the entity is. The markers are `Section`, `Column` and `Dimension` in `mcrs_minecraft_engine_world`. The position types `BlockPos`, `SectionPos` and `ColumnPos` are plain coordinate math in `mcrs_minecraft_core` and carry no ECS state. Block data inside a section is a `PalettedContainer`-style palette, as in the game.

Each dimension is a separate Bevy world and has its own tick. [Cells and the road to many nodes](/docs/en/concepts/scaling/) builds on this, and so do the dimension plugins you write in [Dimensions are separate worlds](/docs/en/plugins/dimensions/).

## Tickets decide what is hot

Space ticks only when a ticket covers it. A ticket comes from a player's simulation area, the spawn area or a chunk loader. The code keeps the loading tickets on columns, the 3D simulation areas of players and the stage of each section in `lifecycle/` in the world module. Cold space is data that does not tick. This split is what lets an untouched section cost nothing.

## Volumes become the one API for reading the world

Several code paths read blocks: the chunk crate, the world generator, the light engine, the mesher and the client. Each of them had a view of its own and answered "section not loaded" in its own way. One layer-3 crate called `mcrs_minecraft_volume` now gives them one API.[^486]

A volume has bounds. For each section it says whether the section may be written, is read-only, belongs to another owner, is not loaded, or is outside. Nothing loads on access, and errors are types you can match.

Capabilities are separate traits for blocks, biomes, heights, light and block entities, plus mutable forms of them. The traits are generic, so there is no dynamic dispatch per block. The main path works per section and per palette, and access per block is a cursor over that path.

The engine dimension view, heights and biomes, snapshots and light, meshing and the client store have moved to it. A saved Anvil chunk is not read as a volume, and structure templates keep their own placement, block by block in the order of the template.

## Mobs are ECS entities

Each mob, item, falling block and experience orb that the server simulates is a Bevy entity. Its motion is in components of the crate `mcrs_minecraft_engine_entity_motion` (`MotionState`, `MotionKind`, `MotionId`), and the attributes and the brain of a mob are components too. Players are the exception: they stay rows by tile. Each tick, one pass steps every moving entity in parallel against a frozen snapshot of the previous tick. Effects on another entity go into a queue that one system applies in a fixed order. [How a tick runs in parallel](/docs/en/concepts/parallel-tick/) explains why that gives one result on any thread count.

An earlier design kept mobs as rows in a store by tile. The rows were deleted, so a mob is a normal entity that your own system can query.

The exact shape of the API for reading and changing mobs from your own plugin is not settled. There is no decision on it yet, so no stable page can describe it. The memory cost per section and per entity component is not measured either.[^324]
