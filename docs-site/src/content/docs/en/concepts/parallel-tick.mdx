mcrs runs work in parallel according to the data it reads and writes. This page explains how systems share the tick, how the entity motion pass uses a frozen body grid, and which guarantees the tests check today.

## Systems that touch different data run together

mcrs is built on Bevy ECS, short for entity component system. In an ECS, behaviour is a set of functions called systems, and each system is one transformation over every entity that has the data it names. Bevy runs two systems at the same time when their data access does not overlap, so you write no lock for this. The Bevy scheduler finds the conflicts when it builds the schedule graph. The compiler does not check them.

System sets, which are named groups of systems, fix the order between the groups. The project also checks the schedule for ambiguity, as section 13 of [the sharding design note](https://github.com/andreypfau/mcrs/blob/main/docs/minecraft-bevy-sharding-architecture.md) describes. The tick is split into a few phases with few sync points.[^364]

## Entities read a frozen grid and write their own components

One system can still have many entities to process. The motion pass splits its Bevy query into parallel batches:

1. Before the pass, one owner system updates `BodyGrid`, the spatial lookup of bodies grouped by tile. It applies the changes from the previous pass and edits made outside it.
2. `MotionStep` uses `par_iter_mut` to step mobs, items and falling blocks. Each entity reads the grid and the blocks without changing them, and writes its own motion components.
3. The pass collects movers, grid edits, crowd damage candidates and expiries. Later systems consume these results; damage applies after the motion pass.

No entity reads another entity's new motion state during the pass. The design note calls this Jacobi: all entities read the same frozen grid while computing their own next state. Tiles group spatial data and replication interest; they do not hold authoritative mob rows.

Players are Bevy entities too. The AI builds a player table from their components, and the player publisher queries those components to produce tile events. Such tables and body rows are projections for a consumer, not another player entity or another health model. Player movement uses a separate path from `MotionStep`.

## Hits apply after motion in a fixed order

`DamagePlugin` chains `DamageSet::Collect`, `Filter`, `Apply` and `Report` in `TickSet::WorldWrite`, after the motion pass. Hit sources append `DamageRequest` values to `PendingHits`. A plugin can change or remove requests in `Filter`, before the engine sorts them by the target's `EntityUuid`, `WriterKey`, write tick and sequence and applies them in `Apply`.

Players and mobs share the same `Vitals` component and damage kernel. Accepted hits produce `Damaged`, and a death also produces `Died`. The next tick advances the hurt and damage cooldown counters. [Read player data](/docs/en/plugins/players/#health-damage-and-death) describes the plugin hooks and the current limits.

Mob defence includes armour, toughness and fire or fall immunities derived from attributes and entity data. A hit that lowers a resting mob's health is replicated even when the mob does not move. The kernel can calculate resistance, but no effect system fills it on the server yet.[^pr1078]

## The result is the same on any thread count

Damage ordering uses the entity UUID, not a network id or the order in which worker threads finish. The checks below compare runs of the same scene with different thread counts; they do not prove that every subsystem is identical across architectures.

The project sorts determinism into three tiers:[^367]

| Tier | Guarantee | Where it applies |
|---|---|---|
| Exact | The result equals the reference | World generation, the arithmetic of player movement, anything rolled from a seed stored in the save |
| Independent of the scheduler | The same inputs give the same tick regardless of thread order | Everything else |
| Free | Any order is allowed | Entities and systems that share no written data |

Two checks hold this today. The first is the test `tick_determinism.rs`. It ticks a world of two cells for 46 ticks, or for 60 ticks in the `full` test profile, once with every world inline on one thread and once with threads. It hashes selected section, column, light, block-entity and player-position state after every tick and fails at the first tick where the hashes differ.

## Run the hash check yourself

The second check is an example in the physics crate. It builds a benchmark scene of 50 000 walkers and 50 000 items on 32 x 32 tiles and prints a hash of the scene after N ticks:

```sh
cargo run --release -p mcrs_minecraft_engine_physics --example state_hash -- <threads> <ticks>
```

Run it with 1 thread and then with 8 threads, and the hash at the end of the line is the same. The example also prints the architecture, so you can compare two machines. The code is short:

## What is parallel today and what is a goal

| Area | State |
|---|---|
| Parallel motion query with a frozen body grid, hash equal across thread counts | in the code, covered by the example above |
| Cells of one world ticking at the same time with halo exchange | in the code, covered by `tick_determinism.rs` |
| Lighting and world generation on threads of their own, applied at a tick boundary | in the code |
| Block simulation: scheduled ticks, block updates, shards | partly: kernels exist, shards that merge and split are <Status issue={160} /> |
| Redstone | not started: <Status issue={190} /> |
| One dimension on many machines | goal: <Status issue={181} /> |

<Aside type="caution" title="WIP">
Redstone and the many-node layout are directions and do not exist yet. Redstone will be semantic first, which means the results and delays match vanilla and the order inside a tick may differ.[^190] The exact order would come later as a change of one ordering policy. Do not plan a farm around it yet. Today the project has no redstone at all.
</Aside>

## Rest skips the full physics step

The project's direction is work proportional to change.[^365] The motion query still visits its entities, but rest can skip the full physics step until motion or nearby blocks change. A hit or an attribute edit can wake a resting mob. Mob AI uses waits for decisions, and damage counters have an explicit work set. These skips reduce work; they do not make every resting entity free.

Two costs are not measured yet: an idle server tick and the memory per section.[^320][^324]
