The vanilla server runs one game tick on one thread: it walks the world and every entity in turn. Java forks move single jobs off that thread. mcrs asks a different question for each piece of work: what does it read, and what does it write? Work that does not touch the same data runs at the same time. This page explains how that is built and what runs in parallel today.

## One loop against systems over data

In an ECS, behaviour is a set of systems. Each system is one transformation over every entity that has the data it names. Bevy runs two systems at the same time when their data access does not overlap. The Bevy scheduler checks those conflicts when it builds the schedule graph, not the compiler. So you do not write a lock for this.

The order between groups of systems is fixed by system sets, and the project checks the schedule for ambiguity (the sharding note, section 13). The tick is split into a few phases with few sync points ([#364](https://github.com/andreypfau/mcrs/issues/364)).

## Tiles and a frozen snapshot

Inside one system, a domain still has a lot of entities. For entities, mcrs uses this model (`docs/physics-architecture.md`, section 3):

1. At the start of the tick, the engine freezes a snapshot of the state that other entities can see: the blocks as they were at the end of the previous tick, a grid of the bodies, and a table of positions.
2. Space is cut into tiles of columns. Each tile is a task over the rows of the entities in it.
3. Every entity reads only the snapshot and writes only its own row. Effects on other entities (a push, a pickup) are collected and applied later, in a fixed order.

Because no entity reads another entity's new state in the same pass, the tasks do not wait for each other and no lock is needed. This is the design called Jacobi in the note: every row is computed from the old state. A task starts when the tasks it reads from are done, tracked by small dependency counters, on the Bevy compute pool.

## One result on any thread count

A fixed order makes the result independent of the machine. The merge of effects goes by a stable key: the persisted UUID of the entity, never a network id. Ties between entities are broken by that key. The rule is written in [#367](https://github.com/andreypfau/mcrs/issues/367), which sorts determinism into three tiers:

- exact, as the reference: world generation, the arithmetic of player movement, anything rolled from a seed stored in the save;
- independent of the scheduler: everything else. The same inputs give the same tick regardless of thread order;
- free: entities and systems that share no written data can run in any order.

Two checks hold this today. The test `tick_determinism.rs` ticks a world of two cells for 60 ticks, once with every world inline on one thread and once with threads, hashes the whole simulation state after every tick, and fails at the first tick where the hashes differ.

## Try it yourself

The physics crate has an example that prints a hash of a benchmark scene (50 000 walkers and 50 000 items on 32 x 32 tiles) after N ticks:

```sh
cargo run --release -p mcrs_minecraft_engine_physics --example state_hash -- <threads> <ticks>
```

Run it with 1 thread and with 8 threads: the hash at the end of the line is the same. It also prints the architecture, so you can compare two machines. The code is short:

## What is parallel today, and what is the goal

| Area | State |
|---|---|
| Entity pass over tiles with a frozen snapshot, hash equal across thread counts | in the code, covered by the example and tests above |
| Cells of one world ticking at the same time with halo exchange | in the code, covered by `tick_determinism.rs` |
| Lighting and world generation on threads of their own, applied at a tick boundary | in the code |
| Block simulation: scheduled ticks, block updates, shards | partly: kernels exist, shards that merge and split are <Status issue={160} state="wip" /> |
| Redstone | not started: <Status issue={190} state="wip" /> |
| One dimension on many machines | goal: <Status issue={181} state="wip" /> |

Do not plan a farm around it yet. Today the project has no redstone at all.

## Work proportional to change

The second idea next to parallelism is that a thing that does not change costs nothing. A resting entity waits for an event instead of being checked every tick, and a cell that has nothing to tick is skipped. This is a decision in [#365](https://github.com/andreypfau/mcrs/issues/365): sparse changes over a large population go through an explicit work queue. Mob AI uses waits instead of per-tick checks.

What is not measured yet: the cost of an idle server tick ([#320](https://github.com/andreypfau/mcrs/issues/320)) and the memory per section ([#324](https://github.com/andreypfau/mcrs/issues/324)). The project publishes no mob benchmark numbers on this page. See [Performance](/docs/en/project/performance/) for what PERF.md holds, with the machine and the scenario next to each number.
