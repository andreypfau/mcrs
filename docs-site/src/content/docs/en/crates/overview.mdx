mcrs is {fact('crates')} crates under `crates/`, and you can take them one at a time. This page lists all of them by layer and marks the ones that CI builds without Bevy, without `std` or for wasm32. Use it to find the crate you need and to see what it brings with it.

<Aside type="caution" title="WIP">
The crate tables are maintained by hand from the package manifests and the three lists in [`xtask/src/checks.rs`](https://github.com/andreypfau/mcrs/blob/main/xtask/src/checks.rs). A generator that rebuilds them on every docs build is planned. Until it exists the tables can be out of date, so check the verified date at the bottom of the page.
</Aside>

## How to read the tables

The crates are grouped by the layers in [AGENTS.md](https://github.com/andreypfau/mcrs/blob/main/AGENTS.md#layers). CI checks only some parts of the layer rule. The wire and network crates must not link game data. The crates that bake models, resolve item icons or draw entities must not link the network, a client or a server, so that a viewer works without a connection. The play-state packets in `mcrs_minecraft_protocol_game` must not link the inventory layout or click, player-slot and transaction rules; their menu keys come from `mcrs_minecraft_menu_key`. `mcrs_minecraft_vanilla_inventory` must not depend on the packet edge of the inventory. `mcrs_minecraft_engine_item`, `mcrs_minecraft_player_holders` and `mcrs_minecraft_inventory_client` must not link the server-only crates `mcrs_minecraft_engine`, `mcrs_minecraft_engine_server`, `mcrs_minecraft_save` and `mcrs_minecraft_server`, so that a client can use them.

The layer of a crate is not stored anywhere in the code. It was assigned by hand from the layer list in AGENTS.md and the crate description, and no check confirms it, so use it as a guide.

Each table has the same five columns. The crate name is the package name, and the other four come from these places:

| Column | Where it comes from |
|---|---|
| Description | Based on `description` in each crate's `Cargo.toml`, checked and supplemented from the source files. Five manifests have no description or only the crate name |
| No Bevy | `NO_BEVY_PACKAGES` in [`checks.rs`](https://github.com/andreypfau/mcrs/blob/main/xtask/src/checks.rs). CI runs `cargo check --no-default-features` on these crates and fails if one requires Bevy |
| no_std | `NO_STD_PACKAGES` in the same file. CI builds these crates for `wasm32v1-none` without `std` |
| wasm32 | `WASM32_PACKAGES` in the same file. CI builds these crates for `wasm32-unknown-unknown` |

The no-Bevy list has {fact('crates_no_bevy')} names. The no_std list has {fact('crates_no_std')} crates and the wasm32 list has {fact('crates_wasm32')}. A dash means only that the crate is not on the CI list. The crate may still build that way.

## Which crates to start with

The table below names the crates to start with for five kinds of project. Use a git dependency for the repository version, as [Use the crates in your project](/docs/en/crates/use-as-library/) describes. Six small programs under [`examples/`](https://github.com/andreypfau/mcrs/tree/main/examples) use the crates. `status_ping` queries a server with the protocol and network crates and no Bevy, `inventory_save_viewer` and `player_attributes` read a player file, `loot_validate` checks the loot tables of a data pack, `inventory_minigame` runs the inventory plugins without their packet edge, and `inventory_bot_click` is a bot without a window or a renderer that joins a server and clicks in its inventory menu. CI checks that the dependency tree of each example has none of the crates it forbids.[^288] The first tutorial is [parsing SNBT](/docs/en/crates/hello-nbt/). Minimal server, lobby and arena examples are planned.[^287]

| You build | Start with | State |
|---|---|---|
| A proxy | `mcrs_minecraft_protocol` and `mcrs_minecraft_network`. Both are on the no-Bevy list, and `xtask` checks that they do not link game data | The crates exist. The proxy library itself, with routing and forwarding, is tracked in <Status issue={296} />, and online mode in <Status issue={82} /> |
| A bot | The same two crates, plus `mcrs_minecraft_client_world`, which keeps the world state of a client without a window or a renderer. It is not on the no-Bevy list. For the inventory add `mcrs_minecraft_inventory_client`, which applies the inventory packets and predicts and sends clicks, and `mcrs_minecraft_container_click`, which represents the click kind, button and menu entry | The client state is split from rendering (<Status issue={301} />). The walker bot is tracked in <Status issue={302} /> |
| A map or a world viewer | `mcrs_minecraft_anvil` for regions (also on the wasm32 list), `mcrs_minecraft_chunk` and `mcrs_minecraft_block` for the data, `mcrs_minecraft_mesh` for meshes | The crates exist. Top-down tiles without a window are tracked in <Status issue={297} />, and a model viewer in <Status issue={298} /> |
| A tool for NBT, commands or data packs | `mcrs_minecraft_nbt`, `mcrs_minecraft_snbt`, `mcrs_minecraft_nbt_path`, `mcrs_command`, `mcrs_minecraft_datapack` | The crates exist. `mcrs_command` and `mcrs_minecraft_snbt` read and write what the game reads and writes. `mcrs_minecraft_nbt_path` parses an NBT path and selects, creates and sets tags, but no test compares it with the game yet |
| A world generator preview | `mcrs_minecraft_worldgen_generator` and the `mcrs_minecraft_worldgen_*` crates | A preview by seed through the public API is tracked in <Status issue={299} />. The generator itself matches vanilla in parity tests on reference seeds |

"The crates exist" means that they build in this repository. None of them promises a stable API, and only four crates have a README.

For a GUI of your own, `CreativeContent::build` in `mcrs_minecraft_creative_content` builds the tab and search lists without Bevy, and `SearchQuery` filters them. `append_tooltip_parts` in `mcrs_minecraft_item_tooltip` appends text parts to your buffer. In the rendering layer, `resolve` in `mcrs_minecraft_item_icon` returns an `ItemIcon` value from a stack, and `IconMeshes` holds the meshes for drawing it. These crates use no client or server crate.

## Why some crates need Bevy

The layer rules make Bevy optional below layer 4 and tokio optional below layer 2. The engine adapters, vanilla plugins, client and server use Bevy, while the generic engine crates can run without it. For data types and pure rules, start with layers 1 to 3 and check the manifest and the CI columns for the features you need. [Layers](/docs/en/concepts/layers/) covers layers 4 and 5.
