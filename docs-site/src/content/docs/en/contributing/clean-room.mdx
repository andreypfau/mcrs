This page retells [docs/clean-room.md](https://github.com/andreypfau/mcrs/blob/main/docs/clean-room.md) in plain words. That file is the rule. If this page and the file differ, the file is right.

The idea is simple. mcrs builds the behavior of the game from descriptions of that behavior, not from the game's code. Two kinds of people do the two jobs, so the code never grows out of the game's code.

## Two roles

| | Specification author | Implementer |
|---|---|---|
| Output | a file in `docs/spec/` | code, tests, design notes |
| May read | any source, the game's code included | `docs/spec/`, public player-facing documentation, artifacts the game produced, this repository's code that the rules allow |
| Must not | write the shape of the game's code into the spec | read decompiled, deobfuscated or mapped game code |

"Artifacts the game produced" means the data pack, the reports in `assets/mcrs/reports/`, captured packets, saves, and the output of `tools/vanilla-oracle`. This output is evidence, and a parity test compares our output with it.

A specification states behavior: inputs, outputs, order, timing and constants as data. It does not state class, method, field or variable names, or the structure of a function.

One person does not take both roles for the same behavior. You can be an author for one behavior and an implementer for another.

## What the repository does not contain

- Names of classes, methods or fields of the game's code, in code, comments, tests, design notes, commit messages and issues.
- Text that calls code a port, a transcription or a mirror of the game's code. Do not write "port of" in a commit or a doc.
- A test, tool or script that reads the game's code.

The community uses a few names of the game's code as common terms. They are allowed everywhere: `ResourceKey`, `TagKey`, `BlockPos`, `SectionPos`, `ColumnPos` and `PalettedContainer`. A new name joins this list only after a review.

Public APIs of other projects, such as Paper, Bukkit, Velocity and Minestom, can be named. They are not the game's code.

## Provenance of a rule

Each rule in a spec carries a label (`docs/spec/registry.md`, section 0.3). `source_suggested` means the author read the reference behavior and states only behavior. When an experiment against the game confirms the rule, the label changes to a confirmed one. The label is how a reader knows how much to trust a rule.

## The exception: world generation

The world generation code keeps its history. The exception covers the crates `mcrs_minecraft_worldgen*`, `mcrs_minecraft_biome` and `crates/mcrs_minecraft_vanilla_worldgen/`, with their design notes. New work in these places follows the normal rules, and a change that touches a game name there removes the name.

Old commit messages may name the game's code. History is not rewritten, because it would break every clone. New commit messages follow the rules.

## If you have read the game's code

<Aside type="caution" title="Paper and Fabric developers">
If you read the game's code about some behavior, you cannot implement that behavior here. Write the specification instead, or pick another behavior. Say it in the issue when you are unsure. A second person then writes the code from your spec.
</Aside>

## A new behavior, step by step

1. An issue asks for a specification, and the author writes it under `docs/spec/`.
2. A second issue asks for the implementation and cites the rule IDs.
3. The implementer works from the spec. A question goes back to the author, and the answer goes into the spec, not into a chat.

More on the spec format: [Specs and parity](/docs/en/contributing/specs-and-parity/).
