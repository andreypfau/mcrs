## Run the tests

```bash
cargo nextest run -p <crate>        # one crate
cargo nextest run --workspace       # everything, before a commit
cargo nextest run --profile full    # plus the exhaustive sweeps
```

The runner is [cargo-nextest](https://nexte.st). The repository pins the Rust toolchain in `rust-toolchain.toml`, and `.config/nextest.toml` pins the minimum runner version.

Every profile first runs a setup script that installs the game's client jar and unpacks its data pack into your cache directory. You do not download anything by hand. The first run needs network access to Mojang.

Test names carry a tier prefix, and the profiles filter by it:

| Profile | What it runs |
|---|---|
| `default` | everything except `exhaustive::`, `gpu::`, `online::` and `vanilla_server::` tests |
| `ci` | the same filter as `default`, and it does not stop at the first failure |
| `full` | the default tier plus `exhaustive::` and `online::`. The scheduled CI job uses it |
| `gpu` | only `gpu::` tests. They need a machine with a Metal GPU |
| `vanilla-server` | only `vanilla_server::` tests. They run through [`vanilla-server/run.sh`](https://github.com/andreypfau/mcrs/blob/main/tools/vanilla-server/run.sh) |

No test run may take longer than five minutes. A test that is slower belongs in the `exhaustive::` tier.

## The checks of xtask

The CI and the local hooks call one runner: `scripts/hooks/run-checks <trigger>`. It builds `xtask` and runs the checks of that trigger. Run it yourself before a push:

```bash
scripts/hooks/run-checks commit
```

| Trigger | Checks |
|---|---|
| `commit`, `push` | `parity`, `fmt` |
| `lint` | `parity`, `fmt`, `keys` |
| `clippy` | `clippy` |
| `test` | the tests of the changed crates and their dependents |
| `portability` | `no-bevy`, `layers`, `wasm32`, `no-std` |

What the checks mean:

- `parity`: a test that claims vanilla behavior must load a fixture the game produced. A claim against a literal gives a warning. See [Specs and parity](/docs/en/contributing/specs-and-parity/).
- `keys`: the generated registry key sources must match what the generator writes from the stored reports. Never edit a generated file by hand.
- `no-bevy`: 99 packages must build without Bevy. `no-std`: 9 packages must build for a target without std. `wasm32`: 11 packages must build for wasm32. The lists are in `xtask/src/checks.rs`.
- `layers`: the wire and network crates must not link game data, so a proxy or a bot can use them alone.

Run `scripts/hooks/run-checks` with no argument to see all triggers.

## MCRS_BLESS

Some tests compare a generated file with a checked-in copy, for example the baked entity assets and a shader field table. When the copy is stale the test fails and says so. Rewrite the copy with the environment variable the message names:

```bash
MCRS_BLESS=1 cargo nextest run -p <crate>
```

Read the diff before you commit it. A blessed file that changed without a reason is a bug in your change, not in the test. The tests that read the variable are in `crates/mcrs_minecraft_mesh/src/pack.rs` and `crates/mcrs_minecraft_entity_model/tests/it/mob_assets.rs`.

## CI

The workflow `.github/workflows/checks.yml` runs four jobs on every pull request to `main`: `lint`, `clippy`, `test` and `portability`. A final job `checks` fails unless all four passed.

- The `test` job of a pull request from a fork runs on a GitHub-hosted `ubuntu-24.04` machine. It skips every crate that depends on wgpu and everything above it. Those tests run locally only, so run them yourself when you touch the client or the renderer.
- Pull requests from the same repository run on the project's own runner.
- A second workflow, `docs`, warns about pages of this site whose sources changed. See [Write these docs](/docs/en/contributing/docs/).
