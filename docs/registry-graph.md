# Registry references: which registries a value refers to

A specification of the reference graph between the values of the registries. It states which registries each value refers to, which values and crates refer to each registry, and the crate each value lives in.

The document deliberately does not describe how registries are loaded, sent to a client or tagged, and it does not say which type names a registry: the generated keys crate does. The names of the registries are the ones the generated reports give them: `assets/mcrs/reports/registries.json` for the static registries and the `registries` map of `assets/mcrs/reports/datapack.json` for the data pack. At the target version the registry of configured carvers is `worldgen/carver` and that of configured features is `worldgen/feature`.

**What counts as a reference.** A value refers to a registry when it holds the name, the numeric id or a tag of an entry of that registry as data. That is the case in a field typed by a key, a holder, a holder set, a tag key or an asset handle, and equally in a field that is an untyped name or a raw id standing for an entry: a resource location, a string, an integer. A crate that holds such a field is a referrer, whether or not anything types the field today. A field that holds an entry of a registry as data through an enumeration that stands for the registry counts as well.

A discriminator that selects the shape of the value itself, and that the tree models as a variant of an enumeration or a slot of a table, is not a reference: the `type` of a feature, of a density function or of a placement modifier, and the id that keys a data component in a component map. The registries that are named only that way are listed in one sentence under the table of the next section, so that the exclusion can be reviewed.

**Where the references come from.** Each row was written from the definition of the value type: the fields of the type, the types nested in it, and the loaders and built-in builders that fill it. The crates that refer to each registry were found the same way, in the value types of the world, item, entity, environment, dimension, biome, worldgen and anvil crates, in the text crate, in the protocol's particle options and in its packets that carry a raw registry id, and in the built-in worldgen builders.

Notes on rows that depart from the plain reading of the table:

- **Enumerations that stand for a registry.** `data_component_type`, `recipe_book_category` and `chunk_status` have rows although the tree models each as an enumeration: a value holds an entry of each as data (the hidden components of a tooltip, the category of a recipe book entry, the status of a stored chunk), so the enumeration stands for the registry. The id that keys a component in a component map is the discriminator excluded above; the hidden components are not.
- **Strings that stand for a registry.** The type of a test instance, the type of a test environment, the function and the environment of a test instance, and the type of a loot table are strings in the tree. They are references by untyped name and have rows.
- **The dialog.** The dialog value is a raw JSON map in the tree, so the registries its entries would name (`dialog_type`, `dialog_body_type`, `dialog_action_type`, `input_control_type`) are named by no field and have no row until the dialog is typed. The inline dialog of a click event is an opaque compound for the same reason.
- **The parameter list.** The climate parameter list of the multi-noise biome source is a generic container in the biome crate, instantiated with names; it is not the value of one registry.

## Names

The rules below say how code names an entry of a registry and how it looks one up. They are listed in the order a reader applies them.

1. A type is imported under the name it is declared with, so `use mcrs_minecraft_keys::Block` and never an alias such as `Block as VanillaBlock`.
2. `get`, `require`, `name(id)` and indexing take only a key or an id of the same registry or set: `biomes.require(&keys::biome::PLAINS)` compiles, and the same key against the block registry does not.
3. `by_name` and `require_by_name` read a name that is data, such as the world preset name an operator supplies or a name in a data pack file, and never a name written in code.
4. The entries and tags of a loaded registry that code names are resolved once after the load, by a resolver the crate registers in its plugin, into one `<Consumer>Ids` value per consumer such as `SurfaceIds`, which every dimension shares; a consumer that names nothing loaded has no such value, and nothing is resolved when a dimension spawns.
5. A value type that names its registry takes the registry's name when its file is rewritten, as `WolfVariant` holds the values of the `wolf_variant` registry.
