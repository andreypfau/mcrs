# Registry references: which type names a registry, and where it lives

A specification of the reference graph between the value types of the registries. It states which type names each registry, meaning the type that keys its ids, its tags and the references to its entries, which crate that type lives in, which registries each value refers to, and which crates refer to each registry. It records the cycles between crates that naming would otherwise form and the placement that breaks each one.

The document deliberately does not describe how registries are loaded, sent to a client or tagged. The names of the registries are the ones the generated reports give them: `assets/mcrs/reports/registries.json` for the static registries and the `registries` map of `assets/mcrs/reports/datapack.json` for the data pack. At the target version the registry of configured carvers is `worldgen/carver` and that of configured features is `worldgen/feature`.

## The placement rule

1. A registry has one type that names it. It is the value type when the value can live at or below every crate that refers to the registry.
2. Otherwise the type is an empty key: a type with no value of its own, placed at or below every crate that refers to the registry. The value lives higher, as a column indexed by the key's id.
3. A value moves below the protocol crate only where a wire codec embeds it inline or an item component holds it by value.

A cycle is never resolved by an exception to these rules. Every cycle in the "Cycles" section is broken by placing a key at or below the referrers and leaving the value above.

**At or below.** A type is at or below a referring crate when it is defined in that crate, in a crate the referrer already depends on, or in a crate the referrer could depend on without a dependency loop, that is, a crate whose own dependencies never lead back to the referrer. The last case is a future dependency: the row of the registry names it, because the referrer needs the dependency once its field is typed. A crate that must build without Bevy, the protocol crate, cannot depend on a crate that needs Bevy, so a registry the protocol refers to is named by a type of a crate that is free of Bevy.

**What counts as a reference.** A value refers to a registry when it holds the name, the numeric id or a tag of an entry of that registry as data. That is the case in a field typed by a key, a holder, a holder set, a tag key or an asset handle, and equally in a field that is an untyped name or a raw id standing for an entry: a resource location, a string, an integer. A crate that holds such a field is a referrer, whether or not anything types the field today. A field that holds an entry of a registry as data through an enumeration that stands for the registry counts as well.

A discriminator that selects the shape of the value itself, and that the tree models as a variant of an enumeration or a slot of a table, is not a reference: the `type` of a feature, of a density function or of a placement modifier, and the id that keys a data component in a component map. The registries that are named only that way are listed in one sentence under the table of the next section, so that the exclusion can be reviewed.

**Where the references come from.** Each row was written from the definition of the value type: the fields of the type, the types nested in it, and the loaders and built-in builders that fill it. The crates that refer to each registry were found the same way, in the value types of the world, item, entity, environment, dimension, biome, worldgen and anvil crates, in the text crate, in the protocol's particle options and in its packets that carry a raw registry id, and in the built-in worldgen builders.

**Dependencies the placement is checked against.** The dependency edges are those of `cargo metadata` for normal dependencies; test-only dependencies are left out. Two sets of edges follow from the moves that give the key types their homes. The item crate is the merged crate of the item components and the item table, and it depends on the core, nbt, profile, registry, text and entity crates; it no longer depends on the block, assets or protocol crates. The new entity crate depends on the core crate only and sits below the text crate, which depends on it. The protocol crate depends on the item crate and on the entity crate. For every row, the home of the naming type does not depend, directly or through any crate it depends on, on any crate that refers to the registry.

## Registries

The table below has one row per registry and six cells in this order: the registry, the type that names it, what its value refers to, who refers to it, the crate the naming type lives in, and the crate the value lives in. The first cell holds the registry's path in backticks, without the namespace, and nothing else in backticks. The cell on what the value refers to names each registry referred to by its path in backticks and uses backticks for nothing else. The cell on who refers to the registry holds the single word nothing, without backticks, when no value refers to it; in every other row it names the referring values and, in backticks, the crates they live in. A test reads this table: a registry is referred to by a value exactly when the cell on who refers to it is not that word, and every such registry must have a key type. A row that is edited must keep this form.

Where a referring crate does not depend on the home of the naming type today, and would have to once its field is typed, the cell on who refers to the registry ends with the sentence that begins "Would depend on the home once typed" and lists those crates. Fields that hold names stay untyped until a later change types them.

Notes on rows that depart from the plain reading of the table:

- **Enumerations that stand for a registry.** `data_component_type`, `recipe_book_category` and `chunk_status` have rows although the tree models each as an enumeration: a value holds an entry of each as data (the hidden components of a tooltip, the category of a recipe book entry, the status of a stored chunk), so the enumeration is the type that names the registry and gains the key. The id that keys a component in a component map is the discriminator excluded above; the hidden components are not.
- **Strings that stand for a registry.** The type of a test instance, the type of a test environment, the function and the environment of a test instance, and the type of a loot table are strings in the tree. They are references by untyped name and have rows, each with an empty key.
- **The dimension type.** The protocol crate refers to this registry by a raw id in the spawn info of the login packet, and it must build without Bevy. The value is a Bevy asset in the dimension crate, so it cannot name the registry for the protocol; the empty key in the registry crate can.
- **The carver registry.** The carver configuration is defined in `mcrs_minecraft_worldgen_carver`, a crate that depends on the core and random crates only and that the biome crate does not depend on today. The registry is named by the empty key `Carver` of the registry crate, and the configuration is the value.
- **The dialog.** The dialog value is a raw JSON map in the tree, so the registries its entries would name (`dialog_type`, `dialog_body_type`, `dialog_action_type`, `input_control_type`) are named by no field and have no row until the dialog is typed. The inline dialog of a click event is an opaque compound for the same reason.
- **The processor list.** The value type of `worldgen/processor_list` wraps a choice type of the density crate. A key implementation needs a type that the feature crate defines, so `StructureProcessorList` is a transparent newtype over that choice, and the wrapped and the bare forms read and write as before.
- **The parameter list.** The climate parameter list of the multi-noise biome source is a generic container in the biome crate, instantiated with names; it is not a type of one registry, so the registry has an empty key and the list is its value.

## Homes of key types

A home is a crate; the Registries table names the home of every type.

`Biome` and `Structure` are empty keys although each registry has a value type, because neither value can live at or below every referrer. A structure holds a set of biomes while the biome crate depends on the structure crate, and a spawn condition of the feature crate holds a set of biomes and a set of structures while both value crates depend on the feature crate. Those references are untyped names today, and an untyped name is a reference. The key of each registry therefore lives in the registry crate's `key` module, below the feature, structure, surface and biome crates, and the value stays in its own crate as the column the key indexes. The fields that hold the names stay untyped.

A registry the Registries table does not name gets its home by the same rule. Where the tree has a value type for it at or below every referrer, that value type names the registry in its own crate. Where it has none there, or where the values of the registry are not one concrete type, an empty key named after the registry lives in the registry crate's `key` module.

## Names

A key takes the name of its registry, because that is what an id and a registry are spelled with. For a registry whose path has a prefix, the name is the last segment in upper camel case: `worldgen/carver` gives `Carver`, `worldgen/template_pool` gives `TemplatePool`. Nothing is renamed: a value type that names its registry keeps its name, and an empty key may share a name with a value that lives in another crate.

Names shared that way are `DamageType`, the twelve mob variants, `BlockTransformer`, `DecoratedPotPattern`, `Dialog`, `LootTable`, `DimensionType`, `Biome`, `Structure`, `TemplatePool`, `MaterialRule`, `VillagerProfession`, `Carver` and `BlockStateProvider`. Nothing at the home of a key has the name of a key placed there, so no name is changed. Where one was taken at a home, this section would record the registry and the name chosen.
